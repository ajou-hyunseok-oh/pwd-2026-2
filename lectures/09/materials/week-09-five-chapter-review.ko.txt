번호 · 현행 49장 덱의 실제 화면 번호

총평

기계의 판단에서 데이터 학습으로, 언어 생성에서 도구 실행으로, 다시 개발 작업의 검증으로 이어지는 다섯 챕터의 구성은 성립한다. 전체 순서보다 기존 자료를 가져오면서 생긴 몇 가지 범위 차이를 먼저 보완할 필요가 있다. 특히 13쪽의 그림 연도, 25·39쪽의 실행 경계, 34·36~38쪽의 게시글 검증 근거가 그렇다.

게시글 사례는 앞에서 제목 검사 함수의 문제를 다루고 뒤에서 전체 등록 동작을 검증할 때 가장 힘이 있다. 45쪽 이후에도 같은 변경의 코드 차이·CI 실패·운영 관찰을 이어 쓰면, 마지막 챕터가 새 용어의 나열로 흩어지는 것을 줄일 수 있다.

01~14 · 표지와 인공지능의 출발과 데이터 학습

03~04쪽은 관찰할 질문을 만들고 연구 의제로 조직한 과정을 보여준다. 05~07쪽은 두 초기 접근을 번갈아 소개한다. 07쪽이 05쪽의 기호·규칙 갈래를 이어받는다는 표지가 있으면, 전문가 시스템이 퍼셉트론의 후속 단계처럼 읽히는 일을 줄일 수 있다. 08쪽의 지원 위축에서 09쪽의 데이터 학습으로 넘어갈 때도, 데이터 학습이 이미 병행된 접근이라는 설명을 유지한다.

| 화면 | 장의 역할과 평가 |
| --- | --- |
| 01 | 회차 제목과 부제가 역사부터 웹 개발까지의 범위를 잘 나타낸다. 주차형 표지의 과목명·학기·회차 대응 적절. |
| 02 | 첫 챕터 표지. 기계 지능 연구의 출발과 데이터 학습을 한 구간으로 묶기에 적합하다. 번호와 제목만 표시하는 형식 적합. |
| 03 | 관찰할 수 있는 평가 문제의 도입. ‘생각한다’의 뜻을 먼저 정하기 어렵다는 문제에서 출발하고, 사람끼리 하는 게임을 비교 기준으로 소개한 뒤 판별 규칙을 설명한다. 도식은 같은 역할을 사람이 맡을 때와 기계가 맡을 때의 오답 빈도를 비교하며, 게임 속 예시 질문은 원문 1절에서 인용했다. [A] |

| 05 | 다트머스의 문제 해결 과제에서 초기 AI의 한 접근인 지식 표현과 추론으로 연결한다. 어떤 사실과 규칙이 결론의 근거인지 확인할 수 있는 방식이다. 도형 A의 이름·분류·변의 수를 기호 표현과 짝지어 읽고, 규칙 작성 → 두 조건 확인 → 결론 도출을 따라간다. |
| 06 | 가중합과 임곗값을 이용한 이진 판단. 그림의 두 입력이 본문과 직접 대응한다. 05쪽과 병행했던 접근임을 구두 연결하거나 본문에 짧게 표시할 수 있다. |
| 07 | 05쪽의 기호 기반 추론을 전문가 시스템에 적용한다. MYCIN 규칙 036의 세 조건과 확신도를 개발진의 4장 그림 4-3과 대조했다. 조건을 충족하는 설명용 입력으로 지식 기반에 저장한 규칙과 추론 엔진의 조건 확인을 구분한다. |
| 08 | MYCIN에 이어 XCON의 기업 도입과 규칙 관리 부담을 설명한다. 1987년 연구에서 보고한 규칙 수와 변경 규모로 유지 부담을 구체화했다. 시간선은 1970년대 일부 위축, 1980년대 전문가 시스템 도입과 기대 회복, 후반의 지원·투자 감소를 보여주며 분야·지역별 차이를 적는다. |
| 09 | 데이터에서 분류 기준을 학습하는 방법을 소개한다. 강의자의 개발 경험을 바탕으로 우하단 팜 노이즈 수집, 노이즈 영역 레이블링, SVM 학습을 보여준다. |
| 10 | 같은 팜 노이즈 사례에서 새 터치 입력을 학습된 SVM으로 분류하고, 팜 노이즈로 판정한 입력을 제외한다. 09쪽의 학습을 10쪽의 추론과 연결한다. |
| 11 | 원본 자료 I09의 층 구조를 단순화한 신경망에서 가중치가 앞 뉴런의 출력을 다음 뉴런의 계산에 얼마나 반영할지 정하는 값임을 설명한다. |
| 12 | 입력에서 출력으로 이어진 신경망을 다시 짚고, 학습할 때는 출력 쪽에서 앞쪽으로 거슬러 계산함을 보여준다. 표범을 재규어로 분류한 예시에서 손실 계산, 역전파, 가중치 갱신을 구분한다. 도식 아래 힌튼의 공동 연구를 1986년 역전파, 2006년 층별 학습, 2012년 AlexNet 순으로 소개한다. [J, K, B] |
| 13 | 12쪽의 역전파와 가중치 학습을 평가용 사진의 범주별 예측으로 연결했다. 2012년 이미지 분류 부문은 같은 평가 사진마다 1,000개 범주에서 최대 5개를 제출하고, 정답을 포함하지 못한 비율로 순위를 매겼다. 신경망 일곱 개를 결합한 AlexNet 연구팀의 제출 결과는 15.3%로 1위, 2위는 26.2%였다. 그림 4의 2010년 표범 사진은 후보에 정답이 포함되어 정답으로 집계되는 예시로 사용했다. [B, H18] |
| 14 | AlexNet의 범주 후보 평가를 AlphaGo의 수 후보 평가로 연결했다. 현재 바둑판에서 후보 A·B를 따라 상대의 응수 이후 바둑판을 비교하는 도식에 정책 신경망의 후보별 확률과 가치 신경망의 승리 가능성 추정을 표시했다. 후보 A·B는 논문 그림 3·5를 참고해 단순화한 설명용 예시다. [H09, H19] |

챕터 연결 평가 · 13~14쪽의 이미지 후보와 바둑 수 후보에서 16쪽의 이어질 표현 후보로 옮기면 학습 흐름이 자연스럽다. 이 연결은 서로 다른 과제의 비교이며, AlphaGo가 언어 모델의 직접 전신이라는 역사적 설명으로 확장할 이유는 없다.


15~27 · 언어 모델에서 코딩 에이전트로

16~20쪽은 문맥에서 표현을 계산하는 원리, 21~24쪽은 개발자가 코드 제안을 사용하는 과정, 25~27쪽은 모델의 요청을 실제 실행에 연결하는 과정이다. 24쪽과 26쪽이 같은 공백 오류를 유지하여 실행 주체의 변화가 선명하다.

| 화면 | 장의 역할과 평가 |
| --- | --- |
| 15 | 언어 모델의 생성과 코딩 에이전트의 실행을 한 챕터로 묶는다. 번호·제목만 표시한 표지 형식 적합. |
| 16 | 14쪽의 AlphaGo가 바둑판을 보고 다음 수의 후보를 평가하는 과정을 문장 앞부분에서 이어질 표현의 가능성을 계산하는 과정과 연결했다. 같은 두 후보를 ‘오늘 수업에서는…’과 ‘오늘 자바스크립트 실습에서는…’에 각각 이어 보며 문맥에 따른 어울림을 정성적으로 비교한다. 20쪽 도식의 LLM은 별도 풀이 없이 등장하므로, 20쪽에서 ‘언어 모델 계산’으로 풀어 쓸 수 있다. |
| 17 | 16쪽의 후속 표현 예측을 위한 입력 처리부터 설명한다. cl100k_base에서 unhappy!가 un(359), happy(57621), !(0)으로 나뉜다. 예시 아래에 ‘un → ID 359 → un의 임베딩 → 모델 계산’을 배치해 토큰의 식별 번호와 모델이 학습한 숫자 배열의 역할을 설명한다. 토큰 기준 과금에서는 입력·출력 토큰 수에 각각의 단가를 적용한다. [L03, L09, L10, L11] |
| 18 | 17쪽의 임베딩으로부터 위치별 표현을 만든 뒤, 관련도에 따라 가중치를 정하는 과정으로 연결했다. 우산과 민수의 정보를 다른 굵기의 화살표로 ‘그’의 새 표현에 모으고, 각 정보에 가중치를 곱한 뒤 합산한다고 표시했다. 굵기는 설명용 예시다. [L03] |
| 19 | 18쪽의 우산 예시를 트랜스포머 층 안의 어텐션에 연결했다. 1층의 출력이 2층의 입력이 되는 도식을 제시하고, 층의 반복 항목에서 학습 중 같은 층 안의 토큰 위치는 병렬 처리한다고 설명한다. 하단에는 GPU가 행렬 계산을 병렬 처리할 수 있다는 점을 적었다. [L03] |
| 20 | 19쪽의 문맥 표현으로 다음 토큰 후보의 확률을 계산한다는 설명을 추가했다. I like에 앞 공백을 포함한 cats를 붙인 결과인 I like cats가 다음 입력이 되고, 다시 마침표를 골라 붙이는 두 차례의 예측을 화살표로 연결했다. 설명용 예시의 선택 토큰은 cl100k_base에서 각각 한 토큰이다. 도식에는 ‘언어 모델’과 ‘다음 토큰 확률 계산’을 표시했다. [L01, L03, L09] |
| 21 | 20쪽의 다음 토큰 예측에서 커서 위치의 코드 토큰 예측으로 연결했다. hasTitle, 매개변수 title, 빈 문자열 검사 주석을 이미 작성한 문맥으로 표시하고, 흰 커서와 회색 return 줄을 통해 제안의 위치를 보여준다. 제안은 문자열에 대한 단순 빈 문자열 검사를 보여준다. [L04] |
| 22 | 21쪽의 hasTitle을 이어받아 첫 요청과 첫 제안, 길이가 20을 넘으면 false를 반환하라는 후속 요청, 수정 제안을 배치했다. 수정 줄에는 && title.length <= 20만 강조했다. 길이 비교는 JavaScript의 String.length를 사용하며 23쪽에서 다른 조건을 더 구체화한다. [L05] |
| 23 | 22쪽의 hasTitle 후속 요청을 목표·제약·기대 결과·예시가 포함된 하나의 프롬프트로 정리했다. 표의 오른쪽 열은 실제 요청 문장이다. 제목의 앞뒤 공백을 제거한 뒤 String.length 범위 1~20을 적용하고, 정상 제목과 공백만 있는 제목의 기대 반환값을 함께 제시한다. [L06] |
| 24 | 22쪽의 hasTitle 수정 제안과 23쪽의 공백 3개 입력을 한 화면에 보여준다. 실행할 코드와 실제값·기대값의 비교표, 그 차이를 전달하는 수정 요청을 배치했다. 수정 후 공백 3개와 앞뒤에 공백이 있는 정상 제목을 재실행해 반환값을 확인한다. [X01] |
| 25 | 24쪽의 제목 검사 수정분을 커밋하는 예시로 코드 수정 이후의 도구 사용을 보여준다. 모델이 터미널에 명령을 요청하고, 실행 환경이 허용 여부를 확인해 준비된 변경분을 커밋한 뒤 실행 결과를 모델에 전달한다. 요청과 성공 응답은 역할을 설명하기 위한 예시 형식이다. [L07, L12] |
| 26 | 25쪽의 도구 결과 반환을 다음 행동의 근거로 연결했다. 결과 관찰에서 기대값과 다르면 코드 수정 후 재실행으로, 두 검사 기준을 충족하면 완료 보고로 갈라진다. 공백 3개와 정상 제목의 기대값 및 수정 전후 실제 반환값은 24쪽 예제를 바탕으로 제시했다. [L07, X01] |
| 27 | 26쪽의 제목 검사에 필요한 파일 읽기와 검사 실행을 두 연결로 표시했다. 호스트는 연결을 관리하고, 클라이언트 A와 B는 각각 파일 서버와 검사 서버로 요청을 보내고 결과를 받는다. 두 연결에 동일한 MCP 규약을 적용하는 수업용 예시다. [M01, M15] |


28~34 · 에이전트에 맥락과 작업 기준을 주는 방법

29~32쪽은 작업할 때 무엇을 읽고 활용하는지, 33~34쪽은 무엇을 만들고 어떤 결과로 완료를 판단하는지 설명한다. 이 둘을 연결하는 질문은 현재 코드를 파악한 뒤 목표 동작을 어떻게 정하느냐다. 31쪽 지침과 32쪽 스킬은 서로 다른 자료를 보여주므로 각각의 장이 필요하다.

| 화면 | 장의 역할과 평가 |
| --- | --- |
| 28 | 정보와 목표를 함께 다루는 제목이 29~34쪽을 포괄한다. 번호와 제목만 표시하는 표지 형식 적합. |
| 29 | 지침·대화·문서·현재 질문·출력 공간 도식이 한도와 현재 참조 범위를 같이 보여준다. 비율이 개략적이라는 캡션이 수치 해석을 막는다. |
| 30 | 전체 프로젝트에서 관련 정보를 골라 현재 문맥을 만드는 그림이 컨텍스트 엔지니어링의 핵심을 보여준다. 예시에서 관련 코드가 제목 규칙과 실제 호출 위치라는 점을 구체화하면 이어지는 저장소 지침과 명세도 같은 프로젝트로 읽힌다. |
| 31 | 저장소 지침의 공통 규칙과 운영상 적용 범위가 표와 맞는다. AGENTS.md는 지원하는 도구의 예라는 설명도 있다. 25쪽에 허용 판단을 보완하면 이 장에서는 규칙 파일의 역할에 집중할 수 있다. |
| 32 | SKILL.md 폴더와 선택·읽기·참고 자료 사용의 도식을 같이 두어 형태와 사용법이 구분된다. 31쪽에 이어 프로젝트 상시 지침에서 작업별 절차로 자연스럽게 넘어간다. |
| 33 | 명세 주도 개발의 정의와 Spec Kit 역사 사례가 한 주제를 뒷받침한다. 예시 표에서 앞뒤 공백을 제거한 뒤 검사하고, 성공 시 정리한 제목을 저장한다는 점을 함께 명시하면 34·38쪽의 저장 근거가 명세에서 직접 나온다. |
| 34 | 정상 저장·공백 거부·서버 실패의 세 조건을 입력·동작·근거로 구체화한 표가 적합하다. 이 세 조건이 38쪽에서 어떤 검사로 확인되는지 연결하면 완료 기준이 이후 장의 기준으로 기능한다. |


35~43 · 에이전트가 구현하고 검증하는 환경

36~38쪽은 34쪽의 완료 기준을 작업과 검사로 옮기고, 39~43쪽은 이를 반복·재개하거나 여러 실행 주체로 나누는 방법을 설명한다. 사용자 사례의 흐름을 따라갈 때 가장 먼저 맞춰야 하는 구간은 36쪽의 서버 입력과 38쪽의 검증 범위다.

| 화면 | 장의 역할과 평가 |
| --- | --- |
| 35 | 구현과 검증을 수행하는 환경이라는 제목이 작업 분해·검사와 하네스·협업을 포괄한다. 번호·제목만 표시하는 형식 적합. |
| 36 | 작업 분해의 네 열이 입력·전제, 산출물, 확인 방법을 잘 구분한다. 서버 처리 행의 ‘제목 검사 결과 / 저장 요청’은 서버에 실제로 들어오는 요청을 보여주지 않는다. ‘등록 요청의 제목 → 서버에서 검사 → 유효한 정리된 제목 저장’으로 요청과 서버 내부 처리의 위치를 구분하면 38쪽과 연결된다. |
| 37 | 코드 발췌는 5개 단언이며 표의 8건은 별도 실행 결과라는 주석이 있다. 새로 실행한 기존 스크립트도 수정 함수 8/8 통과를 재현했다. 표의 ‘1·20글자’는 코드의 String.length 단위와 다르게 읽힌다. ‘ASCII 1·20·21자 예시’ 또는 ‘코드 단위’로 맞춘다. [D] |
| 38 | 응답의 새 ID로 재조회하는 표가 화면 성공과 자료 저장을 구분하며 ‘설계 예’로 표시된 점이 적절하다. 본문은 성공·거부·저장 실패를 모두 확인한다고 설명하지만, 그림 자료는 성공 경로 하나다. 성공 표의 이름을 명시하고 34쪽의 거부·실패를 각 한 줄로 대응시키면 전체 검증 범위가 보인다. |
| 39 | 본문의 하네스 정의와 2026년 사례가 부제의 실행·검증 설계를 설명한다. 그림에는 하네스의 외곽이나 이름이 없고 모델에서 ‘한도·중단 조건’으로 화살표가 향한다. 도식 안에 하네스의 경계를 표시하고 설정된 제약을 실행 환경이 적용함을 표현하면 본문과 맞는다. [E] |
| 40 | 상태 기록 → 현재 환경 대조 → 남은 작업이라는 도식이 하네스의 장기 실행 문제를 구체화한다. 본문과 순서가 맞는다. |
| 41 | 같은 출발점에서 여러 번 시도한다는 표가 자동화 테스트와 에이전트 평가의 차이를 보여준다. 40쪽에서 41쪽으로 넘어갈 때 ‘작업을 재개할 수 있음’과 ‘여러 시도에서 안정적인 결과를 냄’의 두 질문을 이어 주면 전환이 선명해진다. |
| 42 | 계획·구현·평가 역할을 각 칸에 둔 점은 적절하다. 그림은 한 방향이어서 평가 실패가 구현 단계에 되돌아가는 관계가 빠졌다. 사례의 역할만 그린 도식이라면 그 범위를 밝혀도 되며, 상호 조정을 설명하려면 평가 → 수정 경로가 더 잘 맞는다. 43쪽의 화면·서버 병렬화는 별도의 작업 분할 예로 연결한다. [F] |
| 43 | UI는 200만 성공으로 보고 서버는 201을 반환하는 표가 통합 문제를 구체적으로 보여준다. 38쪽의 성공 응답이 201이므로, 이 장에서는 앞서 합의한 계약을 UI가 어긴 상황이라고 짚으면 오류의 원인이 선명하다. |


44~49 · 저장소 개발 흐름으로 들어온 에이전트

리뷰 → 반복 실행 → 실패 조사 → 개발 수명 주기로 확대하는 순서는 자연스럽다. 43쪽까지 게시글 전체를 따라왔는데 45쪽에서 함수 수정으로 돌아가고 47쪽에서 일반 CI 사례를 쓰므로, 같은 게시글 변경이 팀의 개발 흐름에 들어오는 장면을 끝까지 유지할 여지가 있다.

| 화면 | 장의 역할과 평가 |
| --- | --- |
| 44 | 저장소의 검토·자동화·판단으로 관점을 넓히는 챕터 표지로 적합하다. 번호와 제목만 표시하는 형식 적합. |
| 45 | 전후 코드와 검토 기준 표가 함수 변경의 리뷰를 보여준다. 본문의 저장 로직 언급과 직전 장의 전체 기능 범위를 감안하면, ‘제목 검사 함수 수정만 다루는 리뷰’라는 자료 라벨을 붙이고 37쪽 실행 결과를 가리키는 편이 명확하다. |
| 46 | 변경 제출 → 빌드·테스트 → 결과 기록은 CI의 자동 검사 부분을 설명한다. 제목과 부제가 강조하는 ‘자주 통합’은 그림에 없다. 검사 결과를 보고 검토 가능한 작은 변경을 공통 브랜치에 합치는 단계까지 이어주면 정의와 그림이 맞는다. [G] |
| 47 | 에이전트가 설정된 이벤트에 반응해 제한된 범위에서 조사하고 결과를 제안한다는 개념을 그림이 뒷받침한다. 46쪽 검사 실패를 37쪽의 공백 테스트 실패나 43쪽의 응답 불일치로 특정하면, 같은 웹 개발 사례로 읽힌다. |
| 48 | 계획·구현·검증·운영 관찰의 도식은 인용한 GitHub 안내서의 설명과 맞는다. 부제는 ‘계획·구현·검토’까지만 언급하므로 ‘운영 관찰’도 부제에 반영할 수 있다. 운영 관찰이 기능 개선의 다음 계획으로 돌아간다는 연결을 도식에 표시하면 수명 주기라는 본문과 더 잘 맞는다. [H] |
| 49 | 2026년 사례에 근거한 전망으로 표시하고, 진행 기록·통합 검증·승인 지점을 작업 유형과 대응시킨 표가 적절하다. 다만 새 판단을 요구하기보다 앞의 내용을 분류해 되풀이한다. 게시글 기능의 어떤 근거가 확보돼야 맡긴 변경을 받아들일지 한 장면으로 닫으면, 03쪽의 ‘관찰 가능한 행동으로 평가한다’는 질문을 소프트웨어 사례에서 회수할 수 있다. |
