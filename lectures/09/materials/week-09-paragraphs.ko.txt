01. 인공지능의 출발
1950~1970년대 · 지능의 정의와 규칙 기반 추론 · 초기 신경망

1.1 인공지능
서브타이틀: 인간의 지능적 과제를 기계로 수행하려는 연구 분야

인공지능은 인식·언어 이해·문제 해결처럼 인간의 지능과 관련된 과제를 기계로 수행하려는 연구 분야다. 이미 작성해 본 프로그램도 입력을 받아 결과를 만들지만, 지능적 과제에서는 표현이나 상황이 달라져도 적절한 판단을 내려야 한다. 예를 들어 정해진 숫자를 비교하는 일과 서로 다르게 쓰인 문의에서 같은 의도를 파악하는 일은 필요한 처리 방식이 다르며, 인공지능은 이러한 과제를 어떻게 표현하고 해결할지 다룬다.

1.2 튜링 테스트
서브타이틀: 대화에서 관찰되는 행동으로 기계의 지능을 평가하는 관점

기계가 지능적 과제를 수행한다고 말하려면 무엇을 관찰해 평가할지 정해야 한다. 튜링은 1950년 기계가 생각하는지를 직접 정의하는 대신, 문자로 주고받는 대화에서 기계의 응답을 어떻게 판별할 수 있는지 묻는 모방 게임을 제시했다. 이를 통해 지능에 대한 추상적인 질문을 관찰 가능한 행동의 문제로 다룰 수 있지만, 사람처럼 대화했다는 사실만으로 의식이나 모든 과제의 해결 능력이 증명되는 것은 아니다.

1.3 다트머스 연구 모임
서브타이틀: 지능의 구현을 공동의 연구 과제로 정립한 출발점

기계 지능을 평가하는 질문은 지능을 실제로 구현할 수 있는지 탐구하는 공동 연구로 이어졌다. 1955년에 제안되고 1956년에 열린 다트머스 연구 모임은 학습과 지능의 여러 특징을 기계로 모사할 수 있다는 연구 목표를 공유했다. 이 모임은 인공지능이라는 분야를 정립한 중요한 출발점이며, 하나의 완성된 기술을 발표한 사건이라기보다 여러 구현 접근이 발전할 연구 의제를 마련한 사건이다.

1.4 기호 기반 인공지능
서브타이틀: 지식을 기호와 규칙으로 표현해 결론을 도출하는 접근

지능을 구현하는 초기 접근 중 하나는 대상과 관계를 기호로 나타내고 명시적인 규칙을 적용하는 방식이었다. 기호 기반 인공지능에서는 알려진 사실을 지식으로 저장하고, 조건에 맞는 규칙을 적용해 새로운 결론을 얻는다. 예를 들어 어떤 물체가 특정 조건을 만족한다는 사실과 분류 규칙을 함께 사용하면 그 물체의 범주를 판단할 수 있으며, 어떤 규칙이 결론에 사용됐는지 추적할 수 있다.

1.5 퍼셉트론
서브타이틀: 입력값의 가중합으로 결과를 판단하는 초기 계산 모형

명시적인 규칙을 조합하는 접근과 함께 입력을 수치로 처리하는 초기 모형도 연구됐다. 퍼셉트론은 각 입력에 가중치를 곱해 더한 값과 임곗값을 비교해 결과를 결정하며, 가중치는 입력이 판단에 미치는 영향의 크기를 나타낸다. 입력 두 개를 사용하는 분류 문제에서는 가중치와 임곗값에 따라 두 결과를 가르는 기준이 달라지고, 단일 퍼셉트론이 표현할 수 있는 판단에는 한계가 있다.

1.6 전문가 시스템
서브타이틀: 전문가의 지식과 규칙을 적용해 특정 분야의 판단을 도출하는 구조

수치 기반 모형과 병행하던 기호·규칙 계열에서는 전문가의 판단을 특정 분야에 적용하는 전문가 시스템이 발전했다. 전문가 시스템은 분야의 사실과 규칙을 보관한 지식 기반, 그리고 현재 정보에 적용할 규칙을 찾아 결론을 도출하는 추론 부분으로 구성된다. 장비의 증상을 입력하면 점검 규칙에 따라 고장 원인 후보를 제시할 수 있지만, 새로운 증상과 예외를 다루려면 지식을 추가하고 규칙 사이의 일관성을 관리해야 한다.

챕터 흐름 평가
평가: 연구 대상 → 평가 기준 → 연구 분야의 형성 → 구현 접근의 흐름은 성립. 다만 1.4~1.6은 하나의 기술 계보가 아니므로 병행한 접근이라는 연결을 문단에 반영.
챕터 연결: 전문가 시스템의 지식 추가·규칙 관리 부담이 2.1의 기대와 성과 차이, 2.2의 데이터 학습 필요로 연결.
본문 제작 시 주의: 퍼셉트론의 학습 규칙이나 역전파를 1.5에 미리 넣지 않음. 기호·수치 접근의 관계를 보여줄 때 서로를 대체한 단일 연표로 그리지 않음.

02. 데이터로 학습하는 인공지능
1980년대~2016년 · 머신러닝과 딥러닝을 통한 학습 방식의 발전

2.1 AI 겨울
서브타이틀: 기대와 구현 성과의 차이로 나타난 연구지원 위축

전문가 시스템을 비롯한 초기 접근은 제한된 문제에서 성과를 보였지만, 실제 환경의 복잡성과 지식 관리 비용을 충분히 감당하지 못하는 경우도 있었다. AI 겨울은 이러한 기술적 한계와 높은 기대 사이의 차이가 연구비와 관심의 위축으로 이어진 시기를 가리킨다. 1970년대와 1980년대 후반 이후의 위축은 배경이 서로 달랐으며, 이를 하나의 모델 실패나 연구 전체의 중단으로 이해해서는 안 된다.

2.2 머신러닝
서브타이틀: 데이터에서 과제 수행에 필요한 판단 기준을 얻는 방법

판단 규칙을 사람이 모두 작성하는 부담을 줄이는 한 방법은 데이터를 이용해 판단 기준을 얻는 것이다. 머신러닝에서 모델은 입력을 결과로 바꾸는 계산 구조이며, 학습 과정은 데이터와 목표에 맞춰 그 구조의 내부 값을 조정한다. 예를 들어 메시지를 분류할 때 사람이 모든 표현의 규칙을 나열하는 대신 여러 메시지 사례에서 기준을 얻을 수 있으며, 이러한 접근은 초기 인공지능 연구부터 병행되어 이후 데이터와 계산 자원의 확대와 함께 발전했다.

2.3 모델의 학습
서브타이틀: 학습 목표에 따라 모델의 내부 값을 조정하는 과정

모델의 학습은 같은 입력에서 더 적절한 결과가 나오도록 가중치 같은 내부 값을 조정하는 과정이다. 모델이 현재 값으로 결과를 계산하면 학습 목표를 기준으로 그 결과를 평가하고, 개선에 도움이 되는 방향으로 값을 바꾸는 일을 반복한다. 퍼셉트론에서 가중치가 달라지면 판단 기준이 달라지는 것처럼 학습은 모델의 처리 방식을 바꾸지만, 학습에 사용한 사례를 잘 처리했다는 사실만으로 새로운 입력에서도 항상 정확하다고 보장할 수는 없다.

2.4 모델의 추론
서브타이틀: 학습한 모델에 새 입력을 넣어 결과를 얻는 과정

학습이 모델의 내부 값을 조정하는 단계라면 추론은 학습된 모델에 입력을 넣어 결과를 계산하는 단계다. 학습을 마친 메시지 분류기에 처음 보는 메시지를 넣으면, 모델은 이미 얻은 판단 기준을 사용해 분류 결과를 만든다. 일반적인 추론에서는 입력이 달라져 출력이 달라지더라도 그 요청만으로 모델의 가중치가 다시 학습되는 것은 아니므로, 입력의 변화와 모델 자체의 변화를 구분해야 한다.

2.5 지도학습
서브타이틀: 입력과 정답의 대응 관계를 학습하는 방식

학습과 추론의 관계를 이해했다면, 학습 중 어떤 정보를 제공하는지에 따라 학습 방식을 나눠 볼 수 있다. 지도학습은 입력과 그 입력에 대응하는 정답을 함께 제공하고, 모델의 예측이 정답에 가까워지도록 학습하는 방식이다. 스팸 여부가 표시된 메시지로 학습한 뒤 새로운 메시지를 분류하는 사례에서, 정답 표시는 학습 기준을 제공하고 새 메시지의 분류는 추론에 해당한다.

2.6 비지도학습
서브타이틀: 정답 표시 없이 데이터의 구조와 유사성을 찾는 방식

지도학습과 달리 비지도학습은 각 입력의 정답을 지정하지 않은 데이터에서 구조나 반복되는 패턴을 찾는다. 모델은 데이터 사이의 유사성이나 분포를 이용해 묶음과 표현을 만들며, 사람이 미리 붙인 분류 이름을 그대로 맞추는 것이 목표는 아니다. 예를 들어 이름표가 없는 고객 문의를 비슷한 내용끼리 묶을 수 있지만, 만들어진 묶음에 어떤 의미가 있는지는 별도로 확인해야 한다.

2.7 강화학습
서브타이틀: 행동의 결과로 얻는 보상을 바탕으로 행동 방식을 개선하는 과정

정답이 있는 사례나 데이터의 구조를 이용하는 방식에 더해, 행동의 결과를 통해 배우는 강화학습도 있다. 강화학습의 주체는 환경에서 행동을 선택하고 그 결과로 상태의 변화와 보상을 받은 뒤, 장기적으로 더 좋은 보상을 얻도록 행동 방식을 개선한다. 격자에서 목표 지점까지 이동하는 사례에서는 각 위치의 정답 행동을 모두 제공하지 않아도 보상을 통해 이동 방식을 배울 수 있으며, 지금 얻는 보상과 이후의 결과를 함께 고려해야 한다.

2.8 인공 신경망
서브타이틀: 여러 계산 단위를 층으로 연결한 모델 구조

지도학습·비지도학습·강화학습은 어떤 신호로 배우는지를 구분한 것이고, 인공 신경망은 그 학습에 사용할 수 있는 모델의 구조다. 신경망은 입력을 받아 가중치를 적용하는 여러 계산 단위를 층으로 연결하고, 한 층의 출력을 다음 층의 입력으로 전달한다. 각 층에는 계산 결과를 변환하는 처리가 포함될 수 있어 단순한 가중합을 계속 더하는 것보다 복잡한 관계를 표현할 수 있으며, 전체 결과는 층들에 나뉘어 있는 가중치의 영향을 받는다.

2.9 역전파
서브타이틀: 출력 오차에 대한 각 가중치의 영향을 계산하는 방법

여러 층이 연결된 신경망을 학습하려면 최종 출력의 오차에 각 가중치가 어떤 영향을 주는지 알아야 한다. 역전파는 출력 쪽에서 앞선 층으로 계산 관계를 따라가며, 가중치의 작은 변화가 오차에 미치는 영향을 효율적으로 계산하는 방법이다. 학습 절차는 이 계산 결과를 이용해 가중치를 조정하며, 영향을 구하는 역전파와 실제 값을 갱신하는 단계는 서로 구분된다.

2.10 딥러닝
서브타이틀: 여러 층의 신경망으로 데이터의 표현을 학습하는 접근

다층 신경망을 학습할 수 있게 되면 입력에서 유용한 표현을 여러 단계에 걸쳐 얻을 수 있다. 딥러닝은 이러한 여러 층의 신경망을 이용해 과제에 필요한 표현을 데이터에서 학습하는 접근이며, 앞 층의 결과가 뒤 층의 더 복잡한 판단에 사용된다. 이미지를 처리할 때 단순한 무늬와 복합적인 형태에 반응하는 표현을 학습할 수 있지만, 층을 늘리는 것만으로 성능이 보장되지는 않고 데이터와 계산 자원, 학습 방법도 함께 필요하다.

2.11 AlexNet의 이미지 분류
서브타이틀: 대규모 이미지 학습에서 나타난 딥러닝의 성과

AlexNet은 딥러닝이 대규모 이미지 분류에서 성과를 보인 대표적인 사례다. 이미지와 분류 정답을 이용해 신경망의 가중치를 학습한 뒤, 새 이미지가 어떤 범주에 속하는지 예측했으며 2012년 이미지 인식 대회에서 주목할 만한 결과를 얻었다. 이 사례는 사람이 모든 시각적 특징의 판별 규칙을 직접 작성하는 대신 여러 층의 표현을 학습할 수 있음을 보여주며, 모델 구조뿐 아니라 충분한 데이터와 계산 자원의 결합도 성과의 조건이었다.

2.12 AlphaGo의 바둑 판단
서브타이틀: 학습한 신경망으로 바둑의 수와 형세를 평가한 사례

이미지의 범주를 고르는 일에서 한 단계 확장하면, 현재 상황에서 어떤 행동을 선택할지도 학습한 모델로 평가할 수 있다. 2016년 이세돌과 대국한 AlphaGo는 사람의 기보와 스스로의 대국을 활용한 학습을 통해 유망한 수와 형세를 평가하는 신경망을 만들고, 이를 여러 후보 수의 결과를 살펴보는 탐색과 결합했다. 실제 대국에서는 학습된 평가와 탐색을 이용해 수를 선택했으므로, 딥러닝·강화학습과 행동 선택이 각각 어떤 역할을 하는지 구분해 볼 수 있다.

챕터 흐름 평가
평가: 학습·추론을 먼저 구분하고 학습 방식과 모델 구조를 설명한 뒤 사례를 제시하는 순서는 적절. 2.7 → 2.8에서 학습 신호와 모델 구조라는 분류 기준의 전환을 명시.
챕터 연결: AlphaGo는 분류에서 행동 선택으로 응용 범위를 넓히고, 3.1은 같은 학습·추론 관점으로 텍스트 예측이라는 새 과제를 도입.
본문 제작 시 주의: 12장에 학습 방식과 신경망 구조가 집중됨. 분류 사례와 층별 그림을 유지하고, 미분·최적화 공식이나 AlphaGo의 탐색 알고리즘을 추가하면 선수 개념을 보강해야 함.

03. 대규모 언어 모델의 등장
2017~2020년 · Transformer와 사전 학습을 통한 언어 모델의 확장

3.1 언어 모델
서브타이틀: 주어진 문맥에서 가능한 텍스트를 예측하는 모델

이미지나 바둑판 대신 텍스트를 다룰 때는 문맥에 어떤 표현이 나타날 수 있는지를 모델링해야 한다. 언어 모델은 주어진 문맥에서 가능한 텍스트를 예측하도록 학습된 모델로, 문장의 빈 부분이나 뒤에 이어질 표현의 가능성을 계산하는 데 활용할 수 있다. 예를 들어 짧은 문장 앞부분만으로도 여러 표현이 이어질 수 있으므로, 언어 처리는 하나의 정해진 답을 찾는 문제와 다르게 다양한 후보를 다루게 된다.

3.2 토큰
서브타이틀: 모델이 텍스트를 처리하기 위해 나누는 기본 단위

언어 모델이 텍스트를 계산하려면 먼저 문장을 처리 가능한 단위로 나눠야 하며, 이 단위를 토큰이라고 한다. 토큰은 단어 전체일 수도 있고 단어의 일부나 기호일 수도 있으며, 나누는 규칙에 따라 같은 문장의 토큰 수가 달라질 수 있다. 나뉜 단위에는 식별 번호가 대응하지만, 그 번호가 곧 단어의 의미나 중요도를 나타내는 것은 아니다.

3.3 임베딩
서브타이틀: 텍스트 단위를 모델이 계산할 수 있는 수치 배열로 표현하는 방법

토큰의 식별 번호를 신경망이 활용할 수 있는 표현으로 바꾸는 방법이 임베딩이다. 임베딩은 각 단위를 여러 수로 이루어진 배열에 대응시키며, 모델은 이러한 수치 표현을 이용해 입력 사이의 관계를 계산한다. 토큰 번호가 항목을 구분하는 역할이라면 임베딩은 계산에 사용할 표현의 역할을 하고, 문장에서는 같은 단어라도 위치와 주변 표현이 달라질 수 있으므로 순서에 대한 정보도 함께 전달해야 한다.

3.4 어텐션
서브타이틀: 문맥에 필요한 다른 위치의 정보를 선택적으로 반영하는 계산

토큰을 각각 수치로 표현한 것만으로는 문장 안에서 어떤 표현들이 서로 관련되는지 충분히 반영할 수 없다. 어텐션은 현재 위치의 표현과 다른 위치의 표현 사이에서 관련도를 계산하고, 그 정도에 따라 다른 위치의 정보를 가중해 반영하는 방식이다. 문장 속 지시어를 해석할 때 앞에 나온 대상의 정보가 필요한 상황처럼, 같은 토큰도 주변 정보가 반영되면 문맥에 따른 표현으로 바뀔 수 있다.

3.5 Transformer
서브타이틀: 어텐션을 중심으로 문맥 정보를 처리하는 신경망 구조

Transformer는 이러한 어텐션을 중심으로 입력 표현을 여러 층에서 처리하는 신경망 구조다. 토큰의 수치 표현과 순서 정보가 들어오면 각 층은 관련 위치의 정보를 반영하고 표현을 변환해, 출력에 필요한 문맥 정보를 구성한다. 학습에서 여러 위치의 계산을 병렬로 처리할 수 있다는 특성은 많은 텍스트를 효율적으로 학습할 수 있는 기반이 되며, 2017년에 제안된 이 구조는 이후 언어 모델의 발전에 널리 활용됐다.

3.6 자기지도학습
서브타이틀: 데이터 자체에서 예측 목표를 만들어 학습하는 방식

텍스트를 처리할 모델 구조가 있어도 이를 학습시키려면 각 입력에서 무엇을 맞힐지 정해야 한다. 자기지도학습은 데이터 자체에서 예측 목표를 만들어 사용하는 방식으로, 문장의 일부를 가리고 그 내용을 맞히거나 앞부분에서 뒤에 이어질 내용을 예측하게 할 수 있다. 모든 문장에 사람이 별도의 분류 이름을 붙이지 않아도 대량의 텍스트에서 학습 사례를 만들 수 있지만, 사용하는 데이터와 목표에 따라 얻는 능력도 달라진다.

3.7 사전 학습
서브타이틀: 개별 과제에 적용하기 전에 폭넓은 데이터로 기본 능력을 학습하는 단계

자기지도학습이 학습 목표를 얻는 방식이라면, 사전 학습은 개별 과제에 적용하기 전에 폭넓은 데이터로 기본 능력을 익히는 단계다. 언어 모델은 대량의 텍스트에 이러한 학습을 적용해 표현의 관계와 반복되는 패턴을 내부 가중치에 반영할 수 있다. 이 단계에서 얻은 모델은 여러 과제에 활용할 기반이 되지만, 문서를 원문 그대로 보관하는 저장소가 되거나 모든 사용자 요청을 적절히 수행하는 상태가 자동으로 완성되는 것은 아니다.

3.8 대규모 언어 모델
서브타이틀: 대규모 학습을 통해 여러 언어 과제에 활용되는 모델

언어 모델의 구조와 사전 학습을 큰 규모의 데이터와 계산으로 확장한 것이 대규모 언어 모델이다. 모델은 학습된 언어 표현을 여러 과제에 활용할 수 있어 문장 완성뿐 아니라 요약과 질문 응답 같은 작업에도 적용된다. BERT와 GPT 계열은 사전 학습 언어 모델의 발전을 보여주는 사례지만 모델마다 학습 목표와 활용 방식이 다르며, 언어 모델 자체와 그 모델을 이용해 만든 대화 서비스도 구분해야 한다.

3.9 언어 모델의 문장 생성
서브타이틀: 다음 토큰을 반복해 선택하며 출력 문장을 구성하는 과정

대규모 언어 모델 중 생성형 모델은 현재 입력에 이어질 다음 토큰의 가능성을 계산하고, 선택한 토큰을 뒤에 붙이는 과정을 반복해 문장을 만든다. 각 단계의 입력에는 이미 만들어진 토큰도 포함되므로 앞선 선택이 이후의 출력에 영향을 주며, 선택 방식에 따라 같은 요청에서도 서로 다른 결과가 나올 수 있다. Transformer 학습에서 여러 위치를 병렬 계산하는 것과 달리, 이 생성 과정은 앞선 출력에 이어 토큰을 순서대로 만든다. 항상 가장 높은 가능성의 토큰만 선택하는 것은 아니고, 출력이 길어지는 동안 일반적인 생성 요청의 가중치가 매번 다시 학습되는 것도 아니다.

3.10 컨텍스트 윈도
서브타이틀: 한 번의 처리에서 모델이 참조할 수 있는 토큰 범위

다음 토큰을 만들 때 참조할 수 있는 입력의 범위에는 한도가 있으며, 이를 컨텍스트 윈도라고 한다. 요청의 지침, 앞선 대화, 함께 제공한 문서는 모두 모델에 전달된 토큰의 일부로 처리되고, 일반적인 생성형 모델에서는 생성할 출력도 컨텍스트 한도와 관련된다. 대화가 길어졌다고 모든 과거 내용이 항상 그대로 참조되는 것은 아니므로, 현재 모델에 어떤 정보가 들어가 있는지를 구분해야 한다.

3.11 언어 모델의 환각
서브타이틀: 그럴듯한 생성 결과와 사실의 불일치

모델에 정보가 들어 있다는 사실과 생성된 문장이 사실이라는 판단은 별개다. 언어 모델의 환각은 근거가 없거나 사실과 다른 내용을 그럴듯한 표현으로 만들어 내는 현상으로, 학습된 패턴과 현재 입력만으로 답을 구성하는 과정에서도 발생할 수 있다. 제공하지 않은 문서의 세부 내용을 아는 것처럼 답하는 사례에서는 유창함이 근거를 대신하지 못하며, 원인을 입력 길이 하나로만 설명하거나 모델의 확신을 검증 결과로 받아들여서는 안 된다.

3.12 검색 증강 생성
서브타이틀: 관련 자료를 찾아 입력에 추가한 뒤 답변을 생성하는 방식

답변에 필요한 근거가 부족하다면 관련 자료를 찾아 현재 입력에 추가하는 방법을 사용할 수 있다. 검색 증강 생성은 질문과 관련된 문서를 검색한 뒤 그 내용을 언어 모델에 제공해 답변을 만들게 하는 방식이며, 모델 가중치를 다시 학습하지 않고도 외부 자료를 활용할 수 있다. 수업 안내 문서에서 해당 내용을 찾아 질문과 함께 전달하는 사례에서는 답의 근거를 확인하기 쉬워지지만, 검색이 잘못되거나 제공된 자료를 잘못 해석하면 오류가 남을 수 있다.

챕터 흐름 평가
평가: 토큰 → 임베딩 → 어텐션 → Transformer의 구성 순서는 자연스러움. 구조 이후 학습 방식·학습 단계·모델 규모·사용 단계로 전환하는 이유를 문단 첫 문장에 반영.
챕터 연결: 환각에서 근거 자료를 입력에 보충하는 RAG로 연결되고, 4.1은 같은 생성·문맥 활용을 코드라는 대상에 적용.
본문 제작 시 주의: 3.5에서 먼저 나왔던 문장 생성 절차를 3.9로 이동. 토큰 번호·임베딩·위치 정보가 같은 것처럼 보이지 않게 그림을 구분하고, 새 행렬 연산이나 모델별 구조 비교는 넣지 않음.

04. 코드 생성과 대화형 개발 지원
2021~2023년 · 코드 자동 완성에서 대화를 통한 개발 지원으로의 확장

4.1 코드 생성 모델
서브타이틀: 코드의 패턴을 학습해 주어진 문맥에 맞는 코드를 생성하는 모델

언어 생성에 문맥과 관련 자료를 활용하는 방식은 프로그래밍 코드에도 적용할 수 있다. 코드 생성 모델은 코드와 설명의 패턴을 학습하고, 함수 이름이나 주변 코드 같은 입력에 이어질 코드를 생성한다. 함수의 설명을 보고 본문을 제안할 수 있지만 생성 결과가 실제 실행 환경의 조건을 만족하는지는 별도로 확인해야 하며, 2021년의 Codex 코드 모델과 이후의 개발 에이전트 제품은 구분해야 한다.

4.2 코드 자동 완성
서브타이틀: 편집 중인 코드의 주변 문맥을 바탕으로 이어질 코드를 제안하는 기능

코드 생성 모델을 편집기에 연결하면 개발자가 작성 중인 코드의 문맥을 읽고 다음 코드를 제안하는 자동 완성 기능을 만들 수 있다. 개발자는 필요한 제안을 선택하거나 수정해 코드에 반영하고, 제안이 의도와 맞지 않으면 사용하지 않을 수 있다. 초기 Copilot과 같은 활용에서는 코드 작성의 일부가 보조되지만, 무엇을 구현할지 결정하고 결과를 실행해 확인하는 흐름의 중심에는 개발자가 있다.

4.3 지시 튜닝
서브타이틀: 요청과 적절한 응답의 예시로 지시 수행 능력을 조정하는 학습

코드를 이어 쓰는 능력만으로는 사용자의 요청을 정확히 수행하는 응답 방식까지 충분히 학습했다고 보기 어렵다. 지시 튜닝은 요청과 그에 적절한 응답의 예시를 사용해 사전 학습 모델의 가중치를 추가로 조정하는 과정이다. 예를 들어 코드 설명이나 특정 조건의 함수 작성을 요청했을 때 그 요청에 맞는 형태로 응답하도록 학습하며, 이는 요청 시 문장을 조금 바꾸는 것과 구분되는 모델 학습 단계다.

4.4 사람의 피드백을 통한 학습
서브타이틀: 사람의 평가와 선호를 반영해 응답 방식을 조정하는 과정

요청에 맞는 응답 예시를 학습한 뒤에는 여러 응답 중 사람이 어느 것을 더 적절하게 보는지도 반영할 수 있다. 사람의 피드백을 통한 학습은 응답에 대한 평가나 선호 데이터를 이용해 모델의 응답 방식을 조정하는 과정이며, 강화학습을 사용하는 방식도 있고 다른 학습 방식도 있다. 같은 코드 설명이라도 더 정확하고 이해하기 쉬운 응답을 선호하도록 조정할 수 있지만, 학습에서 선호를 반영했다는 사실이 모든 응답의 정확성을 보장하지는 않는다.

4.5 대화형 개발 지원
서브타이틀: 자연어 대화로 코드의 작성과 설명을 요청하는 방식

코드 생성 능력에 지시 수행과 적절한 응답 방식이 결합되면 개발자는 자연어 대화로 작업을 요청할 수 있다. 대화형 개발 지원에서는 함수 작성, 기존 코드의 설명, 오류 원인의 검토를 요청하고 추가 조건을 전달하며 결과를 다듬는다. 여기서 다루는 기본 대화 방식은 개발자가 코드를 프로젝트에 반영하고 실행 결과를 다시 전달하는 형태로, 대화가 이어지는 것만으로 파일 변경이나 명령 실행까지 자동으로 일어나는 것은 아니다.

4.6 개발 프롬프트
서브타이틀: 구현할 동작과 제약을 명확하게 전달하는 요청

대화형 개발에서 원하는 결과를 얻으려면 구현할 동작을 모델이 사용할 수 있는 정보로 구체화해야 한다. 개발 프롬프트는 무엇을 만들지, 어떤 입력과 제약이 있는지, 어떤 결과를 원하는지를 전달하는 요청이다. 단순히 제목을 검사해 달라는 요청보다 공백의 처리와 허용 길이, 반환할 결과를 명시한 요청이 해석의 차이를 줄이며, 역할을 지정하는 문구만으로 빠진 조건이 채워지거나 정확성이 확보되지는 않는다.

4.7 퓨샷 프롬프팅
서브타이틀: 소수의 입력·출력 예시로 원하는 처리 방식을 전달하는 방법

문장으로 조건을 설명해도 해석이 달라질 수 있으므로, 소수의 입력과 기대 출력을 함께 제공해 원하는 동작을 보여줄 수 있다. 퓨샷 프롬프팅은 이러한 예시를 요청의 일부로 사용하는 방식이며, 예시 없이 지시하는 제로샷과 비교하려면 과제와 조건을 같게 유지해야 한다. 제목 검사에서 일반 제목은 허용하고 공백뿐인 제목은 거부하는 예시를 추가하는 것은 현재 입력을 바꾸는 것이며, 지시 튜닝처럼 모델의 가중치를 추가로 학습하는 것은 아니다.

4.8 게시글 제목 검사 함수
서브타이틀: 조건과 예시를 제공해 작은 기능의 생성을 요청하는 사례

제목 검사 함수는 명확한 조건과 예시가 코드 생성 요청을 어떻게 바꾸는지 확인할 작은 사례다. 입력은 문자열로 한정하고 앞뒤 공백을 제거한 제목이 1~20글자일 때만 유효하다는 조건과 함께, 일반 제목·빈 문자열·공백뿐인 문자열의 기대 결과를 제공한다. 모델은 이 조건을 구현한 함수를 제안하고, 개발자는 제안된 코드가 공백 처리와 길이 판단을 실제로 수행하는지 읽어 볼 수 있다.

4.9 생성 코드의 수정
서브타이틀: 직접 확인한 실행 결과를 대화에 돌려주어 코드를 개선하는 과정

생성된 함수를 읽었더라도 실행 결과를 확인하기 전에는 요구를 충족했다고 판단할 수 없다. 개발자가 공백뿐인 문자열을 넣었는데 함수가 유효하다고 판단했다면, 사용한 입력과 실제 결과, 기대 결과를 함께 전달해 수정할 지점을 구체화할 수 있다. 수정된 함수에 같은 입력과 정상 입력을 다시 넣어 결과를 확인하는 과정에서, 대화는 관찰한 실행 결과를 근거로 코드를 개선하는 왕복 흐름이 된다.

챕터 흐름 평가
평가: 코드 생성 기능 → 요청을 수행하도록 하는 학습 → 대화 사용 → 구체적인 요청과 함수 수정의 흐름은 성립. 모델을 만드는 단계와 사용자가 입력을 구성하는 단계를 구분.
챕터 연결: 4.9에서 사람이 입력·실행 결과를 전달하는 왕복을 5.1의 도구 호출이 프로그램 사이의 연결로 바꿈.
본문 제작 시 주의: 4.8 이후 제목 규칙을 일관되게 유지. 퓨샷 예시의 추가를 가중치 학습이라고 쓰지 않고, 기본 대화 사례에 파일 자동 수정·자동 실행을 미리 넣지 않음.

05. 도구를 사용하는 AI 에이전트
2022~2024년 · 도구 호출과 실행 결과를 활용하는 에이전트 구조

5.1 도구 호출
서브타이틀: 모델의 요청을 외부 기능의 실행과 결과 반환으로 연결하는 방식

사람이 실행 요청과 결과를 대화에 옮기는 왕복 과정을 프로그램 사이의 연결로 만들 수 있다. 도구 호출에서는 모델이 사용할 도구의 이름과 필요한 인자를 요청하고, 외부 실행 프로그램이 실제 기능을 수행한 뒤 결과를 모델에 돌려준다. 예를 들어 파일 읽기 요청을 받아 파일 내용을 반환할 수 있으며, 명령을 텍스트로 작성하는 일과 그 명령이 실행 환경에서 실제로 수행되는 일은 서로 다른 단계다.

5.2 도구 실행 권한
서브타이틀: 외부 기능이 접근하고 변경할 수 있는 범위를 제한하는 기준

도구 호출이 실제 환경의 읽기와 변경으로 이어지면, 실행할 수 있는 범위를 정하는 일이 필요하다. 도구 실행 권한은 접근 가능한 파일과 외부 자원, 허용되는 변경을 제한하는 기준이며, 실행 프로그램과 환경의 제한을 통해 적용된다. 프로젝트 파일을 읽는 권한과 수정하는 권한, 외부로 데이터를 보내는 권한은 구분할 수 있으므로, 모델이 도구를 요청했다는 이유만으로 모든 행동을 허용해서는 안 된다.

5.3 AI 에이전트의 작업 반복
서브타이틀: 목표에 따라 도구를 선택하고 결과를 관찰하며 다음 행동을 결정하는 구조

허용된 도구의 실행 결과를 다시 입력으로 사용하면 모델은 한 번의 응답 이후에도 작업을 이어갈 수 있다. AI 에이전트의 작업 반복은 목표를 바탕으로 행동을 선택하고, 도구가 반환한 결과를 관찰한 뒤 다음 행동이나 종료를 결정하는 구조다. 파일을 읽은 결과에 따라 수정하거나 추가 정보를 찾는 것처럼 실제 관찰이 다음 선택의 근거가 되며, 이러한 실행 반복 자체가 모델의 가중치를 학습하는 과정은 아니다.

5.4 개발 환경의 도구
서브타이틀: 파일과 실행 환경을 에이전트의 작업 대상으로 연결하는 수단

일반적인 에이전트 반복을 소프트웨어 개발에 적용하려면 파일과 실행 환경을 다룰 도구를 연결해야 한다. 파일 읽기는 현재 코드를 파악하게 하고, 편집 도구는 변경을 반영하며, 터미널 실행은 명령의 결과와 오류를 확인하게 한다. Claude Code와 현재의 Codex 같은 개발 에이전트는 이러한 기능을 작업 과정에 연결할 수 있어, 개발자가 코드를 복사해 옮기는 단계뿐 아니라 프로젝트 안의 실제 작업도 지원한다.

5.5 제목 검사 함수의 자동 수정
서브타이틀: 에이전트가 코드를 실행하고 관찰한 오류를 수정하는 사례

앞서 사람이 수정했던 제목 검사 함수에도 같은 개발 도구를 적용할 수 있다. 에이전트는 함수 파일을 읽고 공백뿐인 입력을 실행해 결과를 관찰한 뒤, 제목의 앞뒤 공백을 처리하지 않은 부분을 수정하고 같은 입력을 다시 실행한다. 정상 제목도 함께 확인하면 잘못된 입력을 거부하도록 고치는 동안 정상 동작을 해치지 않았는지 살펴볼 수 있으며, 이 사례에서 달라진 것은 요구 조건이 아니라 코드와 실행 결과를 주고받는 작업의 수행 주체다.

5.6 추론 모델
서브타이틀: 응답 과정에 추가 계산을 사용해 문제 해결을 수행하는 모델

도구를 사용하는 작업 구조가 같더라도 여러 조건을 해석하고 해결 방법을 찾는 모델의 능력에 따라 결과가 달라질 수 있다. 추론 모델은 응답을 만드는 과정에 추가 계산을 사용해 문제 해결을 수행하도록 설계·학습된 모델이며, 학습된 모델을 실행한다는 일반적인 추론의 의미와 구분된다. 복잡한 제목 규칙의 충돌을 검토하는 데 도움을 줄 수 있지만 추가 계산이나 길게 제시된 설명이 정답을 보장하지 않으므로, 결과는 실제 입력과 실행 결과로 확인해야 한다.

5.7 멀티모달 모델
서브타이틀: 텍스트 외의 입력 형식도 함께 처리하는 모델

문제를 해결하는 계산의 깊이와 별개로, 모델이 받아들일 수 있는 정보의 형식도 확장될 수 있다. 멀티모달 모델은 텍스트뿐 아니라 이미지 등 서로 다른 형식의 정보를 함께 처리하며, 제공된 정보 사이의 관계를 이용해 응답을 만든다. 예를 들어 코드 설명과 오류 화면의 이미지를 함께 보고 문제를 파악할 수 있지만, 화면을 해석하는 능력만으로 마우스와 키보드를 조작할 수 있는 권한이나 실행 수단까지 생기는 것은 아니다.

5.8 컴퓨터 사용
서브타이틀: 화면을 관찰하고 입력 도구로 사용자 인터페이스를 조작하는 방식

화면을 해석하는 능력을 입력 도구와 연결하면 사용자 인터페이스를 조작하는 컴퓨터 사용 방식이 된다. 모델은 화면을 관찰해 입력할 위치나 실행할 행동을 정하고, 도구가 클릭이나 키 입력을 수행한 뒤 바뀐 화면을 다시 확인한다. 게시글 입력란에 제목을 넣고 버튼을 누르는 작업도 이러한 반복으로 수행할 수 있으며, 클릭을 요청했다는 사실과 원하는 화면 변화가 실제로 일어났다는 사실은 구분해 확인해야 한다.

5.9 Model Context Protocol
서브타이틀: AI 애플리케이션과 외부 도구·자료의 연결 방식을 맞추는 공통 규약

파일과 실행 환경, 화면 등 여러 도구를 활용하게 되면 각 기능을 AI 애플리케이션에 연결하는 방식도 관리해야 한다. Model Context Protocol은 AI 애플리케이션과 외부 도구·자료가 기능을 알리고 요청과 결과를 주고받는 공통 규약이며, 애플리케이션 안의 클라이언트가 외부 기능을 제공하는 서버와 통신하는 구조를 사용한다. 연결 방식을 맞추면 같은 규약을 지원하는 기능을 연동하기 쉬워지지만, MCP 자체가 작업 목표를 결정하거나 모든 권한과 안전성을 대신 보장하는 것은 아니다.

챕터 흐름 평가
평가: 5.1~5.5의 실행 구조와 사례 연결은 명확. 5.5 → 5.6 → 5.7은 작업 방식 → 문제 해결 능력 → 입력 형식으로 관점이 바뀌어 전체에서 가장 전환 부담이 큰 구간이며, 전환 이유를 문단에 명시한 상태로 유지.
챕터 연결: 5.9는 여러 기능의 연결 규약을 다루고, 6.1은 연결할 수 있는 자료 가운데 현재 작업에 필요한 정보의 선택으로 이동.
본문 제작 시 주의: 추론 모델과 멀티모달 모델을 모든 에이전트의 필수 실행 단계로 그리지 않음. 5.8에서 관찰과 입력 도구를 결합하고, MCP는 별도의 연결 계층임을 보여줘야 함.

06. 프로젝트 맥락과 작업 절차의 관리
2025년 · 저장소 맥락과 지침 · 스킬을 통한 작업 지식의 관리

6.1 프로젝트 맥락
서브타이틀: 현재 코드의 구조와 작업 조건을 이해하는 데 필요한 정보

외부 도구와 자료를 연결할 수 있어도 현재 프로젝트를 이해하는 데 필요한 정보가 자동으로 모두 주어지는 것은 아니다. 프로젝트 맥락은 파일의 역할과 연결, 사용 중인 실행 방법, 지켜야 할 조건, 현재 문제처럼 올바른 변경을 판단하는 데 필요한 정보다. 제목 검사 함수를 고칠 때도 그 함수가 어떤 화면과 요청 처리에서 사용되는지 알아야 하므로, 관련 파일과 호출 관계를 확인하는 일이 작업의 출발점이 된다.

6.2 컨텍스트 설계
서브타이틀: 한정된 입력 범위에 작업에 필요한 정보를 선별하고 유지하는 방법

프로젝트의 모든 정보를 한꺼번에 입력하려 하면 컨텍스트의 한도를 넘거나 중요한 내용을 찾기 어려워질 수 있다. 컨텍스트 설계는 작업에 필요한 지침과 자료, 도구 결과를 선별해 적절한 시점에 제공하고 유지하는 방법이다. 처음에는 관련 파일의 위치와 요약을 제공하고 실제 수정에 필요한 파일을 추가로 읽는 방식처럼, 어떤 정보를 지금 사용하고 무엇을 필요할 때 가져올지 결정하는 것이 핵심이다.

6.3 프로젝트 지침 파일
서브타이틀: 프로젝트에서 반복해 적용할 규칙을 기록한 문서

선별할 정보 중 여러 작업에 반복해서 적용되는 규칙은 프로젝트 지침 파일로 관리할 수 있다. Codex의 AGENTS.md와 Claude Code의 CLAUDE.md 같은 문서에는 프로젝트의 실행 방법, 코드 작성 규칙, 작업 시 지켜야 할 조건을 기록해 요청마다 같은 설명을 반복하는 부담을 줄인다. 어떤 파일이 언제 적용되는지는 도구와 위치에 따라 달라질 수 있으며, 문서에 적힌 행동 지침과 실행 환경이 실제로 강제하는 권한은 별도로 관리해야 한다.

6.4 에이전트 스킬
서브타이틀: 특정 작업의 수행 절차와 참고 자료를 묶어 재사용하는 단위

프로젝트 지침이 공통 규칙을 담는다면 특정 종류의 작업에 필요한 절차와 자료는 에이전트 스킬로 묶어 재사용할 수 있다. 스킬은 작업 설명과 수행 지침을 중심으로 필요에 따라 참고 문서나 실행용 스크립트를 함께 제공하며, 해당 작업에 필요한 내용을 불러오는 방식으로 활용된다. 제목 검사 로직을 변경할 때 확인할 입력과 실행 방법을 스킬로 정리할 수 있지만, 이는 모델을 새로 학습하는 기능이나 외부 도구의 연결 규약인 MCP와는 역할이 다르다.

6.5 작업 진행 기록
서브타이틀: 완료한 일과 남은 일의 상태를 작업 밖에 보존하는 기록

재사용할 절차가 준비되어 있어도 현재 작업에서 어디까지 진행했는지는 별도로 남겨야 한다. 작업 진행 기록은 변경한 파일, 직접 실행한 명령과 결과, 해결하지 못한 문제를 대화에만 남기지 않고 파일 등 별도 위치에 보존한 것이다. 제목의 공백 처리는 수정했지만 길이 경계는 아직 확인하지 않았다는 기록이 있으면 이후 작업에서 완료한 부분과 남은 부분을 구분할 수 있으며, 단순히 완료했다고 적는 것보다 확인 근거를 함께 남기는 편이 유용하다.

6.6 컨텍스트 압축
서브타이틀: 긴 작업 이력을 필요한 정보 중심으로 줄여 이어가는 방식

진행 상태를 기록해 두면 긴 대화 이력을 줄여도 필요한 정보를 다시 확인할 수 있는 기반이 생긴다. 컨텍스트 압축은 목표와 핵심 결정, 현재 상태를 요약해 모델이 참조하는 작업 이력의 크기를 줄이는 방식이다. 압축에는 정보 손실이 있을 수 있으므로 모든 내용을 기억한다고 가정하지 않고, 요약에 파일 위치와 미해결 문제를 남겨 필요할 때 원본 코드와 기록을 다시 읽을 수 있게 해야 한다.

6.7 게시글 프로젝트의 작업 맥락
서브타이틀: 검사 함수가 연결될 프로젝트의 규칙과 관련 파일을 제공하는 사례

제목 검사 함수를 실제 게시글 프로젝트에 연결하려면 함수 자체뿐 아니라 사용하는 곳의 맥락을 함께 제공해야 한다. 프로젝트 지침에는 실행 방법과 공통 규칙을 두고, 관련 자료로는 입력 화면과 요청 처리 파일, 현재 검사 함수만 먼저 선택하며, 작업 기록에는 이미 확인한 입력과 남은 문제를 남긴다. 필요할 때 검사 절차를 담은 스킬을 사용하면 규칙·관련 코드·수행 절차·진행 상태가 각각의 역할을 갖게 되고, 현재 프로젝트를 이해한 상태에서 변경할 기능의 범위를 논의할 수 있다.

챕터 흐름 평가
평가: 필요한 정보 → 선별 → 공통 규칙 → 작업 절차 → 현재 상태 → 이력 압축의 역할 구분이 분명. 6.7에서 같은 함수가 쓰이는 프로젝트를 통해 추상적인 관리 개념을 확인.
챕터 연결: 6.7까지는 현재 프로젝트를 이해하는 정보이고, 7.1부터는 앞으로 달성할 동작의 기준이라는 차이를 명시.
본문 제작 시 주의: 지침·스킬·진행 기록·압축을 모두 기억이나 프롬프트라는 이름으로 합치지 않음. 파일명이나 설정법을 추가할 때 제품별 적용 범위를 확인.

07. 구현과 검증의 자동화
2025년 후반~2026년 · 명세와 계획을 바탕으로 반복하는 구현 · 실행 · 검증

7.1 요구사항 명세
서브타이틀: 구현할 기능의 동작과 제약을 명확하게 기록한 기준

현재 프로젝트를 이해했다면 이제 어떤 동작을 새로 만들거나 바꿀지 명확하게 정해야 한다. 요구사항 명세는 구현할 기능의 동작과 제약을 기록한 기준으로, 게시글 등록에서는 앞뒤 공백을 제거한 제목의 허용 길이와 잘못된 입력의 처리, 저장 성공과 실패 때의 응답을 정할 수 있다. 이 사례에서는 1~20글자의 제목만 저장하고 잘못된 제목은 저장하지 않으며, 저장 실패를 성공으로 표시하지 않는다는 동작을 기준으로 삼는다.

7.2 완료 기준
서브타이틀: 작업이 끝났다고 판단할 수 있는 관찰 가능한 조건

명세가 원하는 동작을 설명한다면 완료 기준은 그 동작이 구현됐다고 판단할 관찰 가능한 조건이다. 빈 제목과 공백뿐인 제목은 거부되고, 허용 길이의 제목은 저장되며, 저장에 실패하면 사용자에게 실패가 표시되는지를 각각 확인할 수 있어야 한다. 코드 파일이 생겼거나 화면이 한 번 보였다는 사실만으로 완료를 선언하지 않고, 요구한 결과를 어떤 입력과 증거로 확인할지 정하는 것이다.

7.3 구현 계획
서브타이틀: 완료 기준을 만족시키기 위한 변경 대상과 작업 순서

완료 기준이 정해지면 현재 코드에서 무엇을 어떤 순서로 바꿀지 계획할 수 있다. 구현 계획은 변경할 파일과 기능 사이의 관계를 확인하고, 앞 작업의 결과가 뒤 작업에 필요한 부분을 고려해 실행 순서를 정한 것이다. 게시글 등록에서는 제목 검사 함수를 먼저 정리한 뒤 서버가 입력을 확인해 저장하도록 하고, 그 결과를 화면에 표시하는 순서로 구성할 수 있으며, 이러한 계획은 결과와 대조할 수 있는 작업 문서다.

7.4 작업 분해
서브타이틀: 계획을 결과를 확인할 수 있는 작은 작업 단위로 나누는 방법

전체 구현 순서가 있어도 한 번에 너무 큰 변경을 맡기면 어느 부분이 완료됐는지 판단하기 어렵다. 작업 분해는 계획을 결과와 확인 방법이 분명한 작은 단위로 나누는 것으로, 제목 검사 함수의 수정과 서버의 입력 처리, 화면의 오류 표시는 서로 다른 작업이 될 수 있다. 각 작업에 입력 조건과 완료 결과를 붙이면 순차적으로 진행하면서 문제가 생긴 범위를 좁힐 수 있고, 모든 작은 작업의 결과를 모아 전체 기능의 완료를 판단할 수 있다.

7.5 자동화 테스트
서브타이틀: 입력에 대한 실제 결과를 기대 결과와 반복해서 비교하는 검사

작은 작업마다 같은 입력을 반복해서 확인해야 한다면 기대 결과와의 비교를 프로그램으로 실행할 수 있다. 자동화 테스트는 준비한 입력에 대한 실제 결과가 기대 결과와 일치하는지를 검사하며, 제목 검사 함수에는 빈 문자열과 공백뿐인 문자열, 1글자·20글자·21글자 입력을 사용할 수 있다. 변경 후 같은 검사를 다시 실행하면 이미 확인한 동작이 깨졌는지 발견하기 쉽지만, 기대 결과가 잘못됐거나 필요한 입력이 빠진 검사만 통과했다고 기능 전체가 정확한 것은 아니다.

7.6 브라우저 검증
서브타이틀: 실제 화면의 입력과 응답으로 사용자 동작을 확인하는 방법

함수의 결과가 맞아도 실제 화면에서 입력을 전달하거나 서버의 응답을 표시하는 연결은 잘못될 수 있다. 브라우저 검증은 사용자가 하는 입력과 클릭을 실제 화면에서 수행하고, 화면 변화와 요청 결과가 완료 기준에 맞는지 확인하는 과정이다. 게시글 제목을 입력해 등록한 뒤 성공 표시와 저장된 내용을 확인하고, 잘못된 제목이나 저장 실패에서는 올바른 안내가 나타나는지 살펴보며, Playwright 같은 도구로 이 절차를 반복 실행할 수도 있다.

7.7 구현과 검증의 반복
서브타이틀: 실행 결과를 완료 기준과 비교하며 변경을 반복하는 개발 과정

완료 기준과 검증 수단을 함께 준비하면 에이전트의 행동·관찰 반복을 개발 작업의 완료까지 연결할 수 있다. 에이전트는 작은 작업을 구현하고 자동화 테스트와 필요한 브라우저 검증을 실행한 뒤, 관찰한 실패를 근거로 수정하거나 다음 작업을 선택한다. 이 반복은 검사를 통과시키기 위해 요구 조건을 임의로 낮추는 과정이 아니라 정해진 결과에 도달하는 과정이며, 해결할 수 없는 원인이나 실행 제한이 확인되면 그 근거를 남겨야 한다.

7.8 에이전트 Hooks
서브타이틀: 작업 중 특정 사건이 발생했을 때 정해진 동작을 연결하는 장치

구현과 검증을 반복할 때 특정 시점에 반드시 수행할 동작을 실행 체계에 연결할 수 있다. 에이전트 Hooks는 도구 실행 전이나 파일 편집 후 같은 사건에 설정된 동작을 연결하는 장치로, 명령을 실행하는 Hook을 이용하면 정책 확인이나 포맷 검사를 정해진 시점에 수행하게 할 수 있다. 이는 React 기능을 사용하는 Hooks와 다른 개념이며, 어떤 사건에서 실행되고 실패가 작업을 차단하는지는 도구와 Hook의 설정에 따라 확인해야 한다.

7.9 실행 하네스
서브타이틀: 도구·작업 상태·검사를 연결해 에이전트 실행을 관리하는 구조

Hook이 특정 사건에 동작을 연결한다면 실행 하네스는 작업을 진행할 전체 실행 구조를 구성한다. 하네스는 모델과 도구, 실행 환경, 진행 상태, 검사 결과를 연결하고 다음 작업의 시작과 종료, 실패 후 처리와 실행 한도 등을 관리한다. 같은 모델이라도 필요한 파일을 읽고 검사를 실행하며 중단 시 상태를 남기는 환경이 갖춰졌는지에 따라 결과가 달라지므로, 모델의 능력과 그 주변 실행 구조를 함께 설계해야 한다.

7.10 변경사항 리뷰
서브타이틀: 변경 전후의 차이와 검증 결과로 의도에 맞는 수정을 판단하는 과정

실행 구조가 갖춰져 검사가 끝났더라도 최종 변경이 의도한 범위에 맞는지는 다시 판단해야 한다. 변경사항 리뷰는 수정 전후 코드의 차이와 실제 검증 결과를 요구사항에 대조해, 필요한 동작이 구현됐는지와 관련 없는 변경이 섞이지 않았는지를 살펴보는 과정이다. 제목 검사 조건을 고치면서 기대 결과를 느슨하게 바꾸거나 관계없는 저장 로직을 건드린 것은 아닌지 확인하면, 에이전트의 완료 보고를 구체적인 변경 근거로 검토할 수 있다.

7.11 게시글 등록 기능의 개발
서브타이틀: 명세부터 검증과 리뷰까지 연결하는 개발 사례

게시글 등록 기능의 개발은 지금까지 나눈 절차를 하나의 작업에 적용하는 사례다. 명세와 완료 기준에 따라 제목 검사 함수, 서버의 저장 처리, 화면의 성공·실패 표시를 차례로 구현하고, 각 단계의 검사 뒤 브라우저에서 전체 등록 동작을 확인한다. 개발자는 최종 코드 차이와 실제 검사 결과를 함께 리뷰해 완료를 판단하며, 이 순차 개발 과정이 있어야 작업 방식을 바꿨을 때도 같은 결과를 얻었는지 비교할 수 있다.

챕터 흐름 평가
평가: 요구사항 → 완료 기준 → 계획 → 작은 작업 → 검증 수단 → 반복 실행 → 실행 구조 → 리뷰가 누적되는 흐름으로 연결됨. 함수 검증에서 화면 검증으로 범위를 넓힌 뒤 반복 과정에 결합.
챕터 연결: 7.11에서 순차 개발의 전체 기준을 확보한 뒤 8.1에서 병렬로 나눌 수 있는 경계를 판단.
본문 제작 시 주의: Hooks를 React Hooks와 구분. 하네스를 특정 Hook 하나로 축소하지 않음. 생성한 코드·검사 코드·검사 통과·요구 충족을 같은 증거로 취급하지 않음.

08. 개발 작업의 병렬화와 지속 실행
2026년 · 여러 에이전트의 협업과 장기 작업의 실행 · 통합 · 중단 기준

8.1 독립적인 작업 범위
서브타이틀: 동시에 진행할 수 있도록 변경 대상과 합의할 경계를 나누는 기준

순차로 완성한 개발 과정을 빠르게 진행하려면 먼저 어떤 부분을 서로 기다리지 않고 수행할 수 있는지 구분해야 한다. 독립적인 작업 범위는 각 작업의 변경 대상과 결과를 나누고, 서로 연결되는 지점의 입력과 출력을 미리 합의한 범위다. 게시글 화면과 서버 처리를 따로 맡기려면 제목 조건과 요청·응답 형식부터 맞춰야 하므로, 단순히 작업 수를 늘리는 것보다 의존성을 줄이고 경계를 분명히 하는 일이 먼저다.

8.2 서브에이전트
서브타이틀: 주 작업의 일부를 별도 맥락에서 수행하고 결과를 반환하는 에이전트

작업의 경계가 분명하면 주 작업의 일부를 별도 에이전트에 맡길 수 있다. 서브에이전트는 제한된 목표와 필요한 자료를 받아 별도의 맥락에서 작업한 뒤 결과를 주 에이전트에 반환하는 실행 주체다. 제목 검사 함수의 경계값 검토를 따로 맡기면 주 작업에 필요한 결론과 근거만 돌려받을 수 있지만, 맡기는 행위 자체가 항상 병렬 실행이나 코드 변경을 뜻하는 것은 아니다.

8.3 에이전트 팀
서브타이틀: 여러 에이전트가 역할과 진행 상태를 조정하며 협업하는 구조

한 작업의 결과를 받아오는 위임에서 더 나아가 여러 에이전트의 진행을 함께 조정할 수도 있다. 에이전트 팀은 역할과 작업 상태를 공유하고 필요한 정보를 교환하며 여러 작업을 협업하는 구조로, 조정 역할은 중복 작업과 누락을 확인하고 결과를 모은다. 화면·서버·검증 역할을 나눌 수 있지만 각 에이전트가 같은 지식과 상태를 자동으로 공유한다고 가정해서는 안 되며, 협업 구조를 제공하는 제품의 지원 범위도 구분해야 한다.

8.4 Git 브랜치
서브타이틀: 하나의 저장소에서 변경 이력을 서로 다른 흐름으로 이어가는 방법

여러 에이전트가 코드 변경을 만들면 각 변경이 어떤 기준에서 시작했는지와 어떤 이력을 갖는지 구분해야 한다. Git은 변경 상태를 커밋이라는 기록으로 남기고, 브랜치는 이러한 기록을 서로 다른 흐름으로 이어갈 수 있게 하는 이름 있는 기준이다. 같은 상태에서 시작한 화면 변경과 서버 변경을 별도 브랜치에 기록하면 결과를 나누어 검토할 수 있지만, 브랜치만 만들었다고 각 작업자가 편집할 별도 디렉터리가 자동으로 생기는 것은 아니다.

8.5 Git worktree
서브타이틀: 같은 저장소의 서로 다른 브랜치를 별도 작업 디렉터리에서 다루는 방법

브랜치로 변경 이력을 나눈 뒤 서로 다른 변경을 실제로 동시에 편집하려면 작업 파일을 다룰 공간도 구분해야 한다. Git worktree는 하나의 저장소에 연결된 작업 디렉터리를 추가해, 서로 다른 브랜치의 파일을 각 디렉터리에서 다룰 수 있게 한다. 화면과 서버를 맡은 에이전트에게 각 작업 공간을 줄 수 있지만, 파일 공간의 분리가 외부 데이터베이스나 실행 중인 서버까지 자동으로 분리해 주는 것은 아니므로 공유하는 자원도 확인해야 한다.

8.6 병렬 변경의 통합
서브타이틀: 따로 만든 변경을 합치고 함께 동작하는지 다시 검증하는 과정

작업 공간이 나뉘어 개별 변경이 완성되면 이를 하나의 기능으로 합쳐야 한다. 병렬 변경의 통합은 서로 다른 변경을 함께 반영하고 같은 부분을 다르게 수정한 충돌을 해결한 뒤, 결합된 상태에서도 요구한 동작이 유지되는지 검증하는 과정이다. 게시글 화면과 서버가 각각 검사를 통과했더라도 실제 요청 형식이 어긋날 수 있으므로, 통합한 코드에서 전체 등록 동작을 다시 확인해야 한다.

8.7 지속 실행 목표
서브타이틀: 여러 작업 단계에 걸쳐 유지할 완료 조건과 실행 한도

병렬화가 같은 시간에 여러 작업을 진행하는 문제라면 지속 실행은 여러 단계에 걸쳐 무엇을 완수할지 유지하는 문제다. 지속 실행 목표는 원하는 최종 상태와 확인 근거, 허용 범위와 실행 한도를 함께 정해 현재 결과를 보고 다음 작업을 이어갈 기준을 제공한다. Codex Goals처럼 이러한 목표를 유지하는 기능을 사용할 때도 게시글 등록의 완료 조건과 검증 방법을 명확히 해야 하며, 예산에 도달하거나 진행을 막는 조건이 있으면 완료와 중단을 구분해 기록해야 한다.

8.8 장기 작업의 중단과 재개
서브타이틀: 저장된 진행 상태를 현재 환경과 대조하며 작업을 이어가는 방법

유지할 목표가 있어도 실행은 오류나 사용자 중단, 환경 변경으로 멈출 수 있다. 장기 작업의 재개는 저장된 목표와 진행 기록을 읽고, 현재 파일과 실행 환경이 기록된 상태와 일치하는지 확인한 뒤 남은 작업을 선택하는 과정이다. 이전에 제목 검사만 완료했다면 서버와 화면 작업을 이어갈 수 있지만, 중단 중 코드가 바뀌었다면 과거의 검사 결과를 현재 결과로 간주하지 않고 필요한 부분을 다시 확인해야 한다.

8.9 예약 자동화
서브타이틀: 정해진 조건이나 시간에 작업을 시작하고 결과를 확인하는 방식

중단된 작업을 이어가는 것과 별도로 새로운 작업을 언제 시작할지도 정할 수 있다. 예약 자동화는 정해진 시간이나 시작 조건에 맞춰 작업을 실행하고, 그 결과와 확인이 필요한 항목을 남기는 방식이다. 일정한 시각에 저장소의 검사를 수행하도록 구성할 수 있지만 작업에 필요한 접근 권한과 실행 환경이 준비되어야 하며, 실행 중 사건에 반응하는 Hooks나 목표를 유지하는 기능과 예약 시작은 역할이 다르다.

8.10 AI 개발에서의 개발자 판단
서브타이틀: 위임할 범위와 결과의 수용 여부를 결정하는 역할

코드 제안에서 병렬 작업과 예약 실행까지 자동화의 범위가 넓어져도, 무엇을 맡기고 어떤 결과를 받아들일지는 개발자의 판단이 필요하다. 작은 수정은 단일 작업으로 처리하고, 경계가 명확한 일은 나누어 맡기며, 요구가 불명확하면 실행 규모를 늘리기 전에 명세를 보완해야 한다. 개발자는 실행 속도뿐 아니라 확인할 근거와 통합 비용을 함께 고려하고, 코드 차이와 실제 동작을 바탕으로 결과를 수용함으로써 AI가 수행하는 작업을 소프트웨어의 품질과 연결한다.

챕터 흐름 평가
평가: 독립 범위 → 위임·협업 → 이력·작업 공간 분리 → 통합은 누적 구조. 8.6 → 8.7에서는 동시 실행과 여러 단계 동안의 지속을 서로 다른 문제로 명시해 연결.
강의 마무리: 예약과 지속 실행까지 위임 범위를 확장한 뒤, 개발자가 명세·검증·통합 비용을 기준으로 결과를 판단하는 역할로 돌아옴.
본문 제작 시 주의: Git 브랜치 이전에 변경 기록인 커밋을 문단 안에서 정의. worktree를 외부 자원까지 분리하는 보안 경계로 설명하지 않음. 팀·재개·예약 기능의 제품별 제약을 실제 시연 전에 확인.
