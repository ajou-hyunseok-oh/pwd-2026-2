# 개념 설명 본문 작성

사용자의 2026-10-10 교정에 따른 본문 작성 기준. 05의 신규·재작성 본문과 이후 회차에 적용하며, [1개념 1슬라이드](one-concept.md) 원칙과 함께 사용한다. 원문 그대로 옮기도록 지정한 구간은 보존한다.

## 본문과 코드의 역할

본문에는 해당 개념의 정의, 구성 요소의 역할, 요소들이 연결되는 구조를 일반화해 설명한다. 코드에는 그 설명이 실제로 구현된 사례를 둔다. 강의자는 코드를 짚으며 본문의 개념과 실제 구현을 연결한다.

| 영역 | 담을 내용 | 검토 기준 |
| --- | --- | --- |
| 제목·서브타이틀 | 학습할 개념과 설명 범위 | 개념을 특정하고 본문의 범위를 안내하는가 |
| 설명 본문 | 개념·구성 요소·관계·구조·필요한 조건 | 코드 없이 읽어도 무엇이며 어떻게 구성되는지 이해할 수 있는가 |
| 코드 등 사례 영역 | 일반 설명을 확인할 수 있는 구체적 구현 | 본문에서 설명한 요소와 관계를 실제로 보여주는가 |
| 코드 라벨·실행 결과 | 파일·실행 조건·입력에 따른 실제 출력 | 사례의 실행과 관찰에 필요한 정보를 제공하는가 |
| 강사의 구두 설명 | 예제의 식별자·문장을 짚는 해설과 시연 | 일반 개념이 예제의 어느 부분에 해당하는지 연결하는가 |

개념 설명을 먼저 정리하고, 그 설명에 맞는 코드 사례를 선택하거나 확정된 기존 사례와의 대응을 확인한다. 예제 코드의 각 줄을 풀어 쓴 설명이나 강의 중 말로 할 시연 대본으로 개념 본문을 대신하지 않는다. 예제의 파일명·변수명·화면 문구를 알아야만 이해할 수 있는 설명은 코드 해설에 해당한다. `return`, `key`, `useState`처럼 개념 자체의 문법이나 API 이름은 본문에서 사용한다.

일반적인 구조를 나타내는 도식이나 비교 표도 개념 본문의 역할을 할 수 있다. 특정 구현이나 결과를 보여주는 그림·표는 사례의 역할을 한다. 표현 형식보다 실제로 설명하는 내용에 따라 역할을 구분한다.

## 설명의 흐름

설명의 기본 흐름은 **정의 → 구성 요소의 역할 → 요소 사이의 관계와 전체 구조 → 필요한 사용 조건**이다. 필요하면 개념이 쓰이는 목적에서 정의로 들어간다. 앞 문장에서 소개한 대상을 다음 문장이 구체화하고, 요소를 설명한 뒤 그 요소들이 함께 작동하는 관계로 연결한다.

- 정의: 무엇을 가리키는 개념이며 어떤 역할을 하는지 짧게 설명
- 구성 요소: 이해에 필요한 요소를 골라 각각의 역할 설명
- 관계·구조: 각 요소가 어떤 입력·처리·반환·포함 관계로 연결되는지 설명
- 조건: 앞서 설명한 구조를 올바르게 사용하기 위한 핵심 규칙이나 예외 설명

이는 내용을 검토하는 관점이며, 모든 슬라이드에 네 개의 소제목이나 일정한 항목 수를 넣는 서식이 아니다. 개념에 따라 필요한 요소와 관계를 선택한다. 비교나 처리 순서 자체가 학습 대상이면 표나 흐름을 사용한다.

이름 규칙·선언 위치·반환값·권장 방식 등을 서로 무관한 사실처럼 나열하지 않는다. 각 규칙은 해당 요소의 역할이나 구조를 이해하는 데 필요한 위치에 둔다. 예제의 작성 순서나 실행 순서를 자연스럽게 연결했더라도, 일반적인 개념·요소·구조가 빠져 있으면 개념 설명 본문으로 적합하지 않다.

첫 줄의 정의만 일반적이고 나머지 설명이 예제 코드 해설로 채워진 경우도 재작성 대상이다.

짧은 명사형 문체와 **개념 - 짧은 정의**의 위계는 유지한다. 다만 문장을 줄이면서 주체·대상·인과 관계를 없애거나, 키워드만 남겨 의미를 강사의 구두 설명에 맡기지 않는다.

한 문장에는 하나의 개념이나 구성 요소의 역할만 간결하게 설명한다. 서로 다른 설명을 `~하며`, `~하고`로 한 문장에 묶지 않는다. 세부 설명에는 글머리표를 사용하고, 한 항목에 한 문장씩 배치한다. 문장을 나누더라도 정의 → 요소의 역할 → 관계와 구조의 흐름은 유지한다.

## 함수 컴포넌트로 보는 작성 예

다음은 일반화 수준과 설명의 관계를 보여주는 예다. 실제 본문에서는 학습 범위와 [선수 개념](one-concept.md#학습-순서와-선수-개념)에 맞춰 필요한 요소를 선택한다. 일반화된 설명이라도 뒤에서 배울 Props나 JSX의 정의를 앞 장에 넣지 않는다. 입력 전달은 Props 장에서, UI 표현 문법은 JSX 장에서 설명한다.

### 코드 해설에 머무른 본문

> 상품 목록의 제목을 별도로 다루기 위해 `ProductTitle` 함수를 정의하고, `return`으로 제목 반환
>
> `App`에서 `<ProductTitle />`를 배치하면 React가 이 함수를 호출해 제목 표시
>
> 같은 제목이 필요한 다른 위치에서도 `<ProductTitle />`로 재사용

예제의 목적·정의·사용·재사용은 이어지지만, 함수 컴포넌트의 일반적인 구성 요소와 구조를 설명하지 않는다. 강사가 해당 코드를 짚으며 설명할 내용에 해당한다.

### 개념·요소·구조를 설명하는 본문

**함수 컴포넌트 - UI를 반환하는 JavaScript 함수**

- 컴포넌트 이름은 대문자로 시작하는 함수 이름
- 함수 본문은 표시할 UI를 계산하는 영역
- return은 계산한 UI를 반환하는 구문
- 다른 컴포넌트는 이 이름을 태그로 사용해 UI 배치
- React는 태그에 대응하는 함수를 호출해 반환된 UI로 화면 구성

이 설명은 특정 제목·상품·함수명에 의존하지 않는다. 예제에서는 강사가 `ProductTitle`을 함수 이름, `return <h2>…</h2>`를 UI 반환, `<ProductTitle />`를 다른 컴포넌트에서의 사용에 대응시켜 설명한다. 이름 → 함수 본문 → 반환 → 사용 관계라는 기본 구조는 유지하면서, 독립된 후속 학습 대상의 정의를 먼저 설명하지 않는다. 특정 예제에 없는 요소라는 이유만으로 현재 학습 범위에 필요한 일반 설명을 생략하지 않는다.

클래스 컴포넌트의 지원 여부와 새 코드의 권장 방식은 필요한 배경으로 짧게 덧붙인다. 함수 컴포넌트의 구성 요소·구조를 설명할 자리를 권장 방식 비교로 대신하지 않는다.

## 작성 절차

1. 중심 개념과 설명 범위를 정한다. 학습자가 본문을 읽은 뒤 설명할 수 있어야 하는 내용을 한 문장으로 적는다.
2. 특정 예제의 식별자 없이 개념을 정의하고, 필요한 구성 요소·역할·관계를 정리한다. 아직 배우지 않은 독립 개념은 상세 설명으로 확장하지 않는다.
3. 정의에서 요소의 역할과 전체 구조로 이어지도록 본문을 작성한다. 문장이 앞뒤로 연결되는 이유가 있는지 확인한다.
4. 본문의 요소와 관계를 보여주는 코드·그림·표를 선택하거나 확정된 기존 사례와의 대응을 확인한다. 코드 설명만으로 본문의 빈틈을 메우지 않는다.
5. 개념 설명과 예제의 대응을 검토한다. 예제의 이름·데이터·출력 설명은 필요한 라벨·결과 영역이나 강사의 구두 설명으로 둔다.
6. 의미 검토 후 번역·서식·실행·화면 검사를 진행하고, 개념 설명의 적합성도 검토 기록에 남긴다.

## 본문 검토의 통과 기준

아래 기준을 사람이 내용으로 판단한다. 개념에 필요한 요소가 여러 장에 걸치면 각 장의 제목·서브타이틀이 정한 범위 안에서 판단한다.

- 코드나 강사의 설명을 가려도 중심 개념의 정의와 핵심 구조가 본문에 남는가
- 구성 요소가 이름만 나열되어 있지 않고, 각 역할과 요소 사이의 관계가 설명되어 있는가
- 예제의 함수명·데이터·상황을 바꿔도 일반 설명이 그대로 성립하는가
- 문장의 연결이 코드의 줄 순서 해설을 넘어 개념의 이해로 이어지는가
- 본문에서 다룬 요소와 관계를 예제에서 확인할 수 있는가
- 짧은 문체를 유지하면서도 주체·대상·관계가 분명한가
- 각 글머리 항목이 하나의 개념을 한 문장으로 간결하게 설명하는가
- 구성 요소의 설명이나 예제에 뒤 장의 정의·사용 규칙을 앞당겨 넣지 않았는가

검토 기록에는 설명 범위, 핵심 요소와 관계, 예제와의 대응, 위 기준에 대한 판단 근거를 짧게 남긴다. 본문 문구를 그대로 복사하거나 “검사 통과”만 기록하지 않는다.

자동 검사는 문서 구조·번역·서식·구문·화면 배치 등 기존 검증 범위를 담당한다. 특정 식별자 사용 금지나 `개념`·`요소`·`구조`라는 단어의 존재 여부로 본문의 적합성을 판정하지 않는다. 자동 검사 통과는 이 내용 검토를 대신하지 않는다.
