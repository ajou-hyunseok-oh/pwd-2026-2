## 한 요청을 끝까지 따르는 구성 — 2026-11-02

사용자가 승인한 9장 순서에 맞춰 제목·본문·코드 발췌·실행 결과를 함께 재구성했다. 2장에서 서버 시작 준비를 마친 뒤 3~6장의 기준 요청은 GET /api/restaurants로 유지한다. 클라이언트 → 미들웨어 → Router → Controller → Service → 응답 수신의 같은 흐름도를 사용하고 해당 장의 위치만 강조한다. 6장에서 Service의 배열 → Controller의 JSON → Axios 응답 본문 → 페이지가 읽는 배열까지 전달을 완결한다.

7장은 생성 시 달라지는 입력·처리·성공 응답을 GET과 비교한다. 8장은 실패 분기만 설명하며 Controller·Service의 역할을 다시 시작하지 않는다. 9장은 성공한 변경도 프로세스 재시작 후 사라진다는 저장 수명으로 전환한다. 설명·비교는 왼쪽, 코드·요청·실행 결과는 오른쪽에 두어 시선의 기준도 유지했다.

정상 조회에서 다른 엔드포인트로 이동하던 코드·예시는 줄였다. /health는 서버 시작 확인에만 남겼고, Router 코드는 목록 GET만 발췌했다. Service 코드는 실제 목록 함수로 한정하고 같은 요청의 HTTP 200·id/name 3건을 실제 응답에서 표시했다. 메뉴 변환·201은 생성 장에서, 400·404는 실패 장에서만 관찰한다. 기존 실행 근거의 전체 응답은 보존한다.

영어 제목·정의·표·코드 라벨과 흐름도도 같은 순서로 다시 작성했다. CORS·MVCS·Promise·await·Model·캐시·Axios·시드·프로세스·next(error)·stack trace의 짧은 설명을 해당 처리 단계에 배치했다. 3장의 클라이언트 코드는 README 연동 예제이며 현재 앱의 연동 완료를 주장하지 않는다. 6장의 클라이언트 값 설명은 이 예제의 반환 약속과 대응한다.
