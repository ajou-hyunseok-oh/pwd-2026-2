3페이지 · 1.1 · 서비스의 사용자 식별
확정 문단: 지난주에는 FoodMap의 맛집 데이터를 서버와 데이터베이스에 저장해 다시 조회할 수 있게 했다. 여기에 사용자의 제보를 연결하려면 데이터의 내용뿐 아니라 누가 그 데이터를 보냈는지도 구분해야 한다. 사용자 식별은 여러 요청과 기록을 같은 사람에게 연결하는 출발점이며, 데이터가 저장되어 있다는 사실만으로 요청자의 신원이 확인되지는 않는다.

발표용 본문:
사용자 식별 - 요청과 사람의 연결
  • 같은 사용자의 여러 요청과 기록을 하나의 기준으로 연결
  • 저장된 내용과 그 내용을 보낸 사람을 구분
데이터 관계의 확장 - 기록에 작성자 연결
  • 맛집 정보에 사용자 제보를 연결하면 작성자 식별도 필요
  • 데이터의 존재만으로 요청자의 신원이 확인되지는 않음

자료 배치: wide

4페이지 · 1.2 · 사용자 계정
확정 문단: 사용자 계정은 서비스가 한 사용자를 지속적으로 구분하기 위해 관리하는 기록이다. 고유한 사용자 ID를 기준으로 이름과 연락처 같은 정보를 연결하면 표시 이름이 바뀌어도 같은 사용자의 기록을 유지할 수 있다. FoodMap의 제보도 이름 문자열보다 사용자 ID에 연결하는 편이 안정적이며, 이 ID는 사용자를 가리키는 값이다.

발표용 본문:
사용자 계정 - 한 사용자를 구분하는 기록
  • 고유한 사용자 ID를 기준으로 이름·연락처 등 연결
  • 표시 이름이 바뀌어도 같은 ID로 계정 유지
고유 ID - 사용자 기록의 연결 기준
  • 제보의 작성자를 이름 문자열 대신 사용자 ID로 저장
  • ID는 사용자를 가리키는 값이며 신원 증명과는 별개

자료 배치: wide

5페이지 · 1.3 · 클라이언트 입력의 신뢰 경계
확정 문단: 요청에 사용자 ID가 들어 있어도 그 값을 보낸 사람이 해당 계정의 사용자라고 바로 판단할 수는 없다. 브라우저에서 보내는 값은 사용자가 바꿀 수 있으므로 서버는 클라이언트의 주장과 직접 확인한 사실을 구분해야 한다. FoodMap 요청의 작성자 ID를 다른 사람의 값으로 바꾸는 사례는 식별자를 전달하는 것만으로 신원을 증명할 수 없음을 보여준다.

발표용 본문:
신뢰 경계 - 주장과 확인된 사실의 구분
  • 클라이언트가 보내는 값은 사용자가 변경 가능
  • 서버는 요청의 사용자 ID를 그대로 신뢰할 수 없음
요청의 주장 - 확인이 필요한 입력
  • 다른 계정의 ID를 아는 것만으로 그 계정의 사용자가 되지는 않음
  • 요청자를 확인할 근거를 서버에서 별도로 판단

자료 배치: side

6페이지 · 1.4 · 사용자 인증
확정 문단: 사용자 인증은 요청자가 주장하는 계정에 대해 적절한 증거를 제시하는지 확인하는 과정이다. 비밀번호 방식에서는 서버가 계정을 찾은 뒤 그 계정의 비밀번호를 알고 있다는 증거를 검증한다. 검증에 성공하면 서버는 요청을 확인된 사용자 ID와 연결할 수 있으며, 사용자 ID를 알고 있다는 사실과 그 계정의 사용자라는 사실을 구분하게 된다.

발표용 본문:
사용자 인증 - 계정에 대한 증거의 검증
  • 요청자가 주장한 계정을 찾은 뒤 적절한 증거 확인
  • 비밀번호 방식에서는 해당 계정의 비밀번호 지식 검증
인증 결과 - 확인된 사용자와 요청의 연결
  • 검증에 성공한 요청을 서버가 확인한 사용자 ID에 연결
  • 계정 식별과 그 계정의 사용자임을 증명하는 과정은 구분

자료 배치: aux

7페이지 · 1.5 · 비밀번호 해시
확정 문단: 비밀번호 해시는 비밀번호에서 계산한 검증용 값으로, 서버가 원문 비밀번호를 그대로 보관하지 않고도 입력을 확인하는 데 사용한다. 비밀번호 저장에는 반복적인 추측의 비용을 높이도록 설계한 전용 해시 함수를 사용한다. 로그인할 때는 저장된 원문을 꺼내 비교하는 대신 입력한 비밀번호가 저장된 검증 정보와 일치하는지 확인하며, 해시가 유출되어도 추측 위험까지 사라지는 것은 아니다.

발표용 본문:
비밀번호 해시 - 원문 대신 보관하는 검증값
  • 입력에서 계산한 값을 저장해 원문 보관을 피하는 구조
  • 로그인 입력이 저장된 검증 정보와 일치하는지 확인
전용 해시 함수 - 반복 추측의 비용 증가
  • 비밀번호 저장을 위해 설계한 계산 비용이 큰 함수 사용
  • 해시가 유출되어도 비밀번호 추측 위험은 남아 있음

자료 배치: wide

8페이지 · 1.6 · 비밀번호 솔트
확정 문단: 솔트는 비밀번호를 해시할 때 함께 사용하는 무작위 값으로, 같은 비밀번호를 선택한 계정들도 서로 다른 해시 결과를 갖게 한다. 솔트는 해시와 함께 보관할 수 있으며, 입력을 검증할 때 해당 계정에 저장된 솔트를 다시 사용한다. 두 사용자가 같은 비밀번호를 쓰더라도 저장 결과가 같지 않으므로, 한 번 계산한 추측 결과를 여러 계정에 그대로 대입하기 어려워진다.

발표용 본문:
솔트 - 해시 계산에 더하는 무작위 값
  • 같은 비밀번호도 계정별로 서로 다른 해시 생성
  • 한 번 계산한 추측 결과를 여러 계정에 재사용하기 어렵게 구성
솔트의 보관 - 검증에 재사용할 정보
  • 비밀키와 달리 해시와 함께 보관 가능
  • 검증할 때 해당 계정에 저장된 솔트를 다시 사용

자료 배치: wide

9페이지 · 1.7 · 비밀번호 로그인
확정 문단: 비밀번호 로그인은 계정 조회와 비밀번호 검증을 거쳐 요청자의 사용자 ID를 확정하는 흐름이다. 가입할 때 비밀번호 해시와 솔트 등 검증 정보를 저장하고, 로그인할 때 입력한 비밀번호를 해당 정보와 함께 검증 함수에 전달한다. 검증에 성공하면 FoodMap 서버가 확인한 사용자 ID가 얻어지며, 여기까지의 결과는 현재 로그인 요청에서 사용자를 확인했다는 사실이다.

발표용 본문:
비밀번호 로그인 - 계정 조회와 입력 검증
  • 가입 시 해시·솔트 등 비밀번호 검증 정보 저장
  • 로그인 시 입력과 저장 정보를 검증 함수에 전달
검증 성공 - 현재 요청의 사용자 확인
  • 서버가 조회한 계정의 사용자 ID를 인증 결과로 사용
  • 이 단계의 결과는 현재 로그인 요청에서 확인한 신원

자료 배치: side

11페이지 · 2.1 · HTTP의 무상태성
확정 문단: 현재 로그인 요청에서 사용자를 확인했더라도 그 결과가 새 HTTP 요청에 자동으로 붙지는 않는다. HTTP는 각각의 요청만으로 이전 인증 결과를 보장하지 않으므로, 애플리케이션이 요청 사이를 연결할 정보를 별도로 관리해야 한다. FoodMap의 로그인 직후 맛집 목록을 다시 요청하는 상황을 통해, 한 번의 사용자 확인과 여러 요청에 걸친 로그인 유지가 다른 문제임을 이해한다.

발표용 본문:
HTTP 무상태성 - 요청 사이의 자동 연결 부재
  • 한 요청에서 확인한 인증 결과가 다음 요청에 자동 첨부되지 않음
  • 서버는 새 요청에서 사용자를 확인할 정보를 다시 필요로 함
로그인 유지 - 애플리케이션의 상태 연결
  • 사용자 확인과 여러 요청의 로그인 유지는 서로 다른 문제
  • 요청 사이를 연결할 정보를 애플리케이션에서 별도로 관리

자료 배치: side

12페이지 · 2.2 · 쿠키
확정 문단: 쿠키는 브라우저가 값을 저장했다가 정해진 조건에 맞는 요청에 첨부하는 기능이다. 서버가 응답의 Set-Cookie로 값을 전달하면 브라우저는 이를 저장하고, 전송 조건을 만족하는 이후 요청의 Cookie에 포함할 수 있다. 쿠키 자체가 사용자의 신원을 확인하는 것은 아니며, 서버와 브라우저가 요청 사이에 값을 주고받을 수 있도록 하는 수단이다.

발표용 본문:
쿠키 - 브라우저의 값 보관·첨부 기능
  • 응답의 Set-Cookie로 받은 값을 브라우저에 보관
  • 전송 조건에 맞는 요청의 Cookie 헤더에 값 첨부
전달 수단 - 신원 확인과 구분되는 역할
  • 쿠키 자체가 사용자의 신원을 확인하지는 않음
  • 서버는 전달받은 값의 의미와 유효성을 별도로 판단

자료 배치: side

13페이지 · 2.3 · 서버 세션
확정 문단: 서버 세션은 로그인 상태를 서버에 보관하고 임의의 세션 식별자로 그 상태를 찾아 사용하는 구조다. 로그인에 성공하면 서버는 세션 식별자와 사용자 ID를 연결해 저장하고 식별자를 쿠키로 전달한다. 이후 FoodMap 요청에 식별자가 돌아오면 서버는 저장된 세션을 조회해 사용자를 확인하므로, 브라우저가 보낸 사용자 ID를 그대로 믿을 필요가 없다.

발표용 본문:
서버 세션 - 서버에 보관한 로그인 상태
  • 로그인 성공 후 임의 세션 ID와 사용자 ID를 연결해 저장
  • 브라우저에는 상태를 찾을 세션 ID를 쿠키로 전달
세션 조회 - 식별자로 저장 상태 확인
  • 이후 요청의 세션 ID로 서버 기록을 조회
  • 브라우저가 주장한 사용자 ID 대신 서버의 연결 기록 사용

자료 배치: aux

14페이지 · 2.4 · 인증 토큰
확정 문단: 토큰은 이후 요청을 처리할 때 제시하는 자격정보이며, 서버의 확인을 거쳐 사용자나 접근 자격과 연결된다. 세션 식별자처럼 서버의 기록을 찾아야 의미를 알 수 있는 토큰도 있고, 토큰 자체에 확인할 정보를 담는 형식도 있다. API에 제시하는 액세스 토큰은 요청 헤더 등으로 전달할 수 있으며, 토큰의 형식과 전달 수단은 구분해서 선택한다.

발표용 본문:
토큰 - 요청에 제시하는 자격정보
  • 서버의 검증을 거쳐 사용자 또는 접근 자격에 연결
  • 세션 식별자도 서버 기록을 조회하는 토큰의 한 형태
형식과 전달 - 서로 다른 선택 기준
  • 서버 기록을 찾는 형식과 정보를 직접 담는 형식 존재
  • 액세스 토큰은 요청 헤더 등으로 API에 전달 가능

자료 배치: side

15페이지 · 2.5 · 토큰의 서명
확정 문단: 토큰에 사용자 정보를 직접 담으면 그 내용을 사용자가 바꾸지 않았는지 확인할 방법이 필요하다. 서명은 발급자가 관리하는 암호학적 키를 이용해 검증 가능한 값을 붙이는 방식이며, 수신자는 신뢰하는 발급자의 검증 키와 방법으로 무결성을 확인한다. FoodMap 사용자 ID를 임의로 바꾼 토큰은 검증에 실패하도록 만들 수 있지만, 서명만으로 토큰 내용이 숨겨지는 것은 아니다.

발표용 본문:
서명 - 토큰의 무결성을 확인하는 검증값
  • 발급자가 관리하는 키로 토큰 내용에 대응하는 값 생성
  • 수신자는 신뢰하는 발급자의 키와 방법으로 검증
보호 범위 - 변조 탐지와 내용 공개의 구분
  • 내용만 바꾼 토큰은 기존 서명과 일치하지 않아 검증 실패
  • 서명은 암호화와 달리 내용의 비밀성을 보장하지 않음

자료 배치: wide

16페이지 · 2.6 · JWT의 구조
확정 문단: JWT는 사용자에 관한 주장과 유효 조건을 JSON 기반으로 담는 토큰 형식이다. 이 강의의 서명형 JWT는 서명 방식 등을 나타내는 헤더, 주장들을 담는 페이로드, 변조를 확인하는 서명으로 구성된다. 페이로드의 sub는 사용자 식별자, iss는 발급자, aud는 토큰을 받을 대상, exp는 만료 시각을 나타내며, 내용은 읽을 수 있으므로 비밀번호 같은 비밀을 넣지 않는다.

발표용 본문:
JWT - 주장과 유효 조건을 담는 토큰 형식
  • 서명형 JWT는 헤더·페이로드·서명의 세 부분으로 구성
  • 페이로드에 사용자 식별자와 발급·수신·만료 조건 포함
  • 내용은 읽을 수 있으므로 비밀번호 등 비밀정보 제외

자료 배치: jwt

17페이지 · 2.7 · JWT 검증
확정 문단: JWT의 내용을 읽는 것과 그 내용을 신뢰하는 것은 별도의 단계다. 서버는 미리 허용한 서명 방식과 신뢰하는 키로 서명을 검증하고, 발급자와 수신 대상이 예상과 일치하며 유효 시간이 지나지 않았는지 확인한다. 이 조건을 통과한 뒤에만 토큰의 사용자 식별자를 요청 처리에 사용하므로, 형식이 맞거나 사용자 ID가 보인다는 이유만으로 인증에 성공하지 않는다.

발표용 본문:
JWT 검증 - 주장을 신뢰할 조건 확인
  • 내용을 읽는 디코딩과 신뢰를 결정하는 검증은 별도
  • 서명·발급자·수신 대상·만료를 모두 통과한 신원만 사용

자료 배치: aux

18페이지 · 2.8 · 인증 상태의 만료
확정 문단: 인증 상태의 만료는 과거의 인증 결과를 신뢰할 수 있는 시간을 제한하는 장치다. 서버 세션은 마지막 활동이나 생성 시점을 기준으로 종료할 수 있고, JWT는 exp에 기록된 시각을 기준으로 유효성을 판단한다. 서버의 인증 상태가 만료되었다면 브라우저에 식별자나 토큰이 남아 있더라도 유효한 인증으로 받아들이지 않는다.

발표용 본문:
인증 만료 - 과거 인증을 신뢰하는 시간 제한
  • 한 번 확인한 인증 결과의 효력을 무기한 유지하지 않음
  • 브라우저에 값이 남아 있어도 만료된 자격은 거부
  • 만료 기준은 클라이언트 변경에 의존하지 않고 서버에서 적용

자료 배치: expiry

19페이지 · 2.9 · 리프레시 토큰
확정 문단: 액세스 토큰의 수명을 짧게 유지하면서 매번 비밀번호를 입력하지 않게 하려면 새 토큰을 발급받는 절차가 필요하다. 리프레시 토큰은 이 갱신에 사용하는 별도의 자격정보로, 일반 데이터 API 대신 인증 시스템에 제출한다. 인증 시스템이 갱신 자격을 확인하면 새 액세스 토큰을 발급하며, 토큰을 계속 발급받는 데 악용될 수 있는 갱신 자격은 별도로 보호해야 한다.

발표용 본문:
리프레시 토큰 - 새 액세스 토큰 발급 자격
  • 짧은 액세스 토큰 수명과 반복 로그인 부담을 함께 고려
  • 일반 데이터 API가 아닌 인증 시스템에 제출
갱신 절차 - 별도 자격 검증 후 재발급
  • 인증 시스템이 갱신 자격을 확인한 뒤 새 토큰 발급
  • 계속된 토큰 발급에 악용될 수 있으므로 갱신 자격도 보호

자료 배치: side

20페이지 · 2.10 · 로그아웃과 인증 철회
확정 문단: 로그아웃은 브라우저의 로그인 표시를 지우는 데서 끝나지 않고 사용하던 자격정보의 효력을 종료하는 과정이다. 서버 세션은 서버의 연결 기록을 무효화할 수 있고, 토큰 방식은 보관한 토큰을 제거하면서 갱신 자격도 철회한다. 다만 서명과 유효 조건만으로 검증하는 JWT는 이미 발급된 토큰이 만료까지 유효할 수 있으므로, 즉시 차단이 필요하면 서버에서 철회 여부를 추가로 확인하는 설계가 필요하다.

발표용 본문:
로그아웃 - 사용하던 자격정보의 효력 종료
  • 브라우저의 로그인 표시나 보관값 삭제만으로 종료되지 않음
  • 서버 기록·갱신 자격 등 실제 수용 지점에서 효력 종료
철회 범위 - 방식별로 다른 종료 시점
  • 세션 기록 무효화와 새 액세스 토큰의 발급 중단을 구분
  • 이미 발급된 JWT는 만료 또는 추가 철회 검사까지 유효할 수 있음

자료 배치: wide

22페이지 · 3.1 · 외부 인증 제공자
확정 문단: 사용자를 확인하는 일을 서비스가 직접 수행하지 않고 외부 인증 제공자에게 맡길 수도 있다. 외부 제공자는 자신의 계정으로 사용자를 인증하고, FoodMap은 그 제공자가 전달한 결과를 검증해 활용한다. 이 구조에서는 외부 계정의 비밀번호를 FoodMap이 받아 저장하지 않으며, 외부 제공자의 책임과 서비스 내부 계정 관리의 책임이 나뉜다.

발표용 본문:
외부 인증 제공자 - 사용자 확인을 맡는 서비스
  • 제공자가 자신의 계정으로 사용자를 인증
  • 연결하는 서비스는 전달받은 인증 결과를 검증해 활용
책임의 분리 - 외부 인증과 내부 계정 관리
  • 외부 계정의 비밀번호를 연결 서비스가 받아 저장하지 않음
  • 서비스 내부의 사용자 기록과 기능은 해당 서비스에서 관리

자료 배치: provider

23페이지 · 3.2 · OAuth의 접근 권한 위임
확정 문단: 외부 서비스와 연결할 때는 먼저 그 서비스의 데이터에 접근할 자격을 위임받는 구조를 이해해야 한다. OAuth는 사용자가 동의한 범위인 scope 안에서 애플리케이션이 외부 API를 호출하도록 액세스 토큰을 발급하는 체계다. 예를 들어 FoodMap은 외부 계정의 비밀번호를 받지 않고 허용된 프로필 정보에 접근할 수 있으며, 이 접근 위임만으로 서비스의 사용자 신원 확인 절차 전체가 정의되지는 않는다.

발표용 본문:
OAuth - 외부 API 접근 권한의 위임
  • 사용자가 동의한 범위에서 앱의 데이터 접근 허용
  • 외부 비밀번호를 넘기지 않고 액세스 토큰으로 API 호출
scope - 위임받은 접근 범위
  • 앱이 사용할 수 있는 데이터·기능의 범위 표현
  • 접근 위임만으로 사용자 신원 확인 절차 전체가 정의되지는 않음

자료 배치: side

24페이지 · 3.3 · OIDC의 사용자 인증
확정 문단: OIDC는 OAuth 기반의 흐름에 사용자 인증 결과를 전달하는 규칙을 더한 체계다. 제공자가 OIDC를 지원하면 서비스는 ID 토큰의 서명과 발급자, 수신 대상, 유효 조건을 검증해 누구의 인증 결과인지 확인할 수 있다. ID 토큰은 사용자의 신원을 전달하고 외부 API용 액세스 토큰은 외부 데이터 접근에 사용되므로, 두 토큰의 목적과 받아들이는 대상을 구분한다.

발표용 본문:
OIDC - OAuth에 더한 사용자 인증 규칙
  • 제공자가 지원하면 ID 토큰으로 인증 결과 전달
  • 서비스는 서명·발급자·수신 대상·유효 조건을 검증
토큰의 목적 - 신원과 외부 접근의 구분
  • ID 토큰은 서비스를 위한 사용자 인증 결과
  • 외부 액세스 토큰은 대상 외부 API의 데이터 접근에 사용

자료 배치: side

25페이지 · 3.4 · 인가 코드 흐름
확정 문단: 인가 코드 흐름은 브라우저로 전달받은 짧은 수명의 일회용 코드를 토큰과 교환하는 절차다. FoodMap 서버가 교환을 맡는 사례에서는 사용자가 외부 인증 화면을 거친 뒤 등록된 복귀 주소로 돌아오고, 서버가 전달된 코드를 제공자의 토큰 발급 창구에 제출한다. 코드는 해당 애플리케이션과 복귀 주소 등의 조건에 연결되며, 사용자는 외부 계정의 비밀번호를 FoodMap에 전달하지 않고 인증 결과를 이어갈 수 있다.

발표용 본문:
인가 코드 - 토큰과 교환하는 일회용 값
  • 외부 인증 후 브라우저가 등록된 복귀 주소로 코드 전달
  • 짧은 수명의 코드는 앱·복귀 주소 등의 조건에 연결
서버의 교환 - 코드로 토큰 발급 요청
  • 서비스 서버가 제공자의 토큰 발급 창구에 코드 제출
  • 제공자가 코드·클라이언트 조건을 검증한 뒤 토큰 반환

자료 배치: side

26페이지 · 3.5 · 로그인 요청의 state
확정 문단: 외부 화면을 거쳐 돌아온 응답은 실제로 이 브라우저에서 시작한 로그인 요청에 대한 응답인지 확인해야 한다. state는 요청을 시작할 때 예측하기 어려운 일회용 값을 만들어 해당 브라우저의 로그인 시도에 연결하고, 복귀한 값과 대조하는 데 사용한다. 값이 없거나 일치하지 않으면 연결을 중단하며, state의 일치는 사용자 신원이나 토큰 서명 검증을 대신하지 않는다.

발표용 본문:
state - 시작한 요청과 복귀 응답의 연결값
  • 로그인 시작 시 예측하기 어려운 일회용 값 생성
  • 값을 해당 브라우저의 로그인 시도와 연결해 임시 보관
왕복값 검증 - 요청 연결의 확인
  • 복귀한 값이 없거나 시작한 값과 다르면 연결 중단
  • 일치 여부는 사용자 신원·토큰 서명 검증을 대신하지 않음

자료 배치: side

27페이지 · 3.6 · 인가 코드의 PKCE 보호
확정 문단: PKCE는 인가 코드를 얻은 쪽이 그 코드를 발급받기 위한 요청을 시작한 쪽인지 확인하도록 교환 절차를 보호한다. 로그인 시도마다 비밀로 보관할 검증값을 만들고 그 값의 해시를 먼저 전달한 뒤, 코드를 교환할 때 원래 검증값을 제시한다. 제공자는 받은 검증값으로 해시를 다시 계산해 앞서 받은 값과 비교하므로, 코드만 가로챈 상대는 교환에 필요한 증거를 갖추지 못한다.

발표용 본문:
PKCE - 인가 코드의 교환을 묶는 증명
  • 로그인마다 verifier를 생성해 교환 전까지 비밀로 보관
  • verifier를 변환한 challenge를 인가 요청에 먼저 전달
교환 시 확인 - 처음 요청과 같은 증명 비교
  • 제공자가 제출된 verifier를 변환해 저장된 challenge와 대조
  • 코드만 가로챈 상대는 교환에 필요한 verifier가 없음

자료 배치: side

28페이지 · 3.7 · 외부 계정과 서비스 계정의 연결
확정 문단: 외부 인증 결과를 검증한 뒤에는 외부의 사용자 식별자를 FoodMap 내부 계정에 연결해야 한다. OIDC에서는 발급자와 그 발급자가 부여한 사용자 식별자의 조합을 기준으로 외부 계정을 구분하고, 이를 내부 사용자 ID에 대응시킨다. 표시 이름이나 이메일이 같다는 이유만으로 서로 다른 계정을 자동으로 합치지 않으며, 연결된 내부 ID를 기준으로 FoodMap의 제보와 사용자 기록을 유지한다.

발표용 본문:
계정 연결 - 외부 신원을 내부 ID에 대응
  • 검증한 발급자 iss와 사용자 식별자 sub의 조합 사용
  • 연결된 내부 ID를 기준으로 서비스의 제보·사용자 기록 유지
연결 기준 - 이름·이메일과 신원의 구분
  • 다른 발급자가 같은 sub 값을 부여할 수 있음
  • 이름·이메일 일치만으로 자동 병합하지 않으며 양쪽 계정 확인 필요

자료 배치: wide

29페이지 · 3.8 · 소셜 로그인 이후의 서비스 인증
확정 문단: 외부 계정이 내부 사용자 ID에 연결되면 FoodMap은 앞서 배운 세션이나 토큰 방식으로 자신의 로그인 상태를 만들 수 있다. 이후 FoodMap API 요청은 서비스가 받아들이는 로그인 자격으로 처리하고, 외부 제공자의 액세스 토큰은 필요한 외부 API 접근에 사용한다. 이렇게 하면 비밀번호 로그인과 소셜 로그인 모두 확인된 내부 사용자 ID라는 공통 결과로 이어진다.

발표용 본문:
서비스 인증 - 확인된 내부 계정의 로그인 유지
  • 외부 신원을 검증한 뒤 연결된 내부 사용자 ID 확인
  • 서비스가 자신의 세션 또는 토큰으로 로그인 상태 생성
공통 결과 - 로그인 방식과 내부 사용자 구분
  • 비밀번호·소셜 로그인 모두 확인된 내부 ID로 요청 연결
  • 외부 액세스 토큰은 필요한 외부 API 접근에만 사용

자료 배치: side

31페이지 · 4.1 · 요청의 인가
확정 문단: 인가는 확인된 사용자가 특정 대상에 특정 행동을 해도 되는지 판단하는 과정이다. 서버는 누가 요청했는지에 더해 무엇을 대상으로 어떤 작업을 하려는지 확인하고 서비스의 허용 규칙을 적용한다. FoodMap에 로그인했다는 사실만으로 모든 제보를 수정할 수 있는 것은 아니며, 사용자 확인 이후에 요청별 허용 여부를 판단해야 한다.

발표용 본문:
인가 - 대상과 행동의 허용 여부 판단

54페이지 · 6.7 · CORS
확정 문단: FoodMap 화면과 API의 출처가 다르면 서버가 허용한 범위에서 브라우저가 응답을 읽을 수 있도록 CORS를 설정할 수 있다. 서버는 허용할 출처 등을 응답 헤더로 알리고 브라우저가 그 조건을 적용하며, 일부 요청은 실제 요청 전에 허용 여부를 먼저 확인한다. CORS는 브라우저의 교차 출처 접근 규칙이므로 API에 직접 보내는 요청의 사용자 인증이나 권한 검사를 대신하지 않는다.

적용 범위 - 브라우저의 교차 출처 접근
  • 모든 요청에 사전 확인이 필요한 것은 아님
  • API 인증·인가를 대신하지 않으며 직접 요청은 별도 통제

55페이지 · 6.8 · 크로스 사이트 요청 위조
확정 문단: 응답을 읽지 못해도 요청을 보낼 수 있다는 점은 로그인된 브라우저에서 중요한 문제가 된다. CSRF는 다른 페이지가 사용자의 의도와 다른 요청을 유발하고, 브라우저가 조건에 따라 자동 첨부한 로그인 쿠키를 서버가 받아들이는 상황을 악용한다. FoodMap의 관리 요청에는 허용된 요청 출처와 공격자가 알 수 없는 확인값을 검증하는 방어 등을 적용해, 로그인 자격이 있다는 사실에 더해 허용된 경로의 요청인지 확인한다.

발표용 본문:
CSRF - 로그인 자격의 자동 첨부를 악용
  • 다른 페이지가 사용자의 의도와 다른 상태 변경 요청 유발
  • 브라우저가 조건에 맞는 로그인 쿠키를 요청에 첨부할 수 있음
요청 검증 - 로그인 여부에 더한 경로 확인
  • 허용된 요청 출처와 공격자가 알 수 없는 CSRF 확인값 검증
  • 확인에 실패하면 서버에서 상태 변경 거부

56페이지 · 6.9 · 쿠키의 보호 속성
확정 문단: 쿠키 보호 속성은 이미 배운 전송 경계와 공격 경로에 맞춰 쿠키의 사용 범위를 제한한다. Secure는 HTTPS 전송으로, HttpOnly는 스크립트의 쿠키 읽기 접근 제한으로, SameSite는 사이트 관계에 따른 쿠키 첨부 제한으로 작동한다. 각 속성은 보호하는 범위가 다르므로 HttpOnly가 페이지 안의 모든 악성 동작을 막거나 SameSite만으로 모든 요청 위조를 해결한다고 판단하지 않는다.

발표용 본문:
쿠키 보호 속성 - 전송·접근 범위의 제한
  • 연결 방식·스크립트 접근·사이트 관계에 따라 각기 다른 범위 보호
  • 필요한 전송 조건에 맞춰 속성을 함께 설정
보호의 한계 - 공격 경로에 맞춘 추가 방어
  • HttpOnly가 페이지 안의 모든 악성 동작을 막지는 않음
  • SameSite만으로 모든 요청 위조가 해결되지는 않음

제한 정책 - 보안과 정상 재시도의 균형
  • 정상 사용자가 다시 시도할 여지를 남기면서 추측 비용 증가
  • 타인의 계정을 계속 잠그는 방식의 악용 가능성 고려

59페이지 · 7.1 · 개발·검증·운영 환경

발표용 본문:
환경 설정 - 같은 코드에 전달하는 실행 값
  • 코드는 공통으로 유지하고 연결 대상과 자격정보를 환경별로 구분
  • API 주소·DB 연결·외부 로그인 복귀 주소 등을 설정으로 관리
설정 전달 - 사용 위치에 맞춘 값 주입
  • 환경 변수는 실행 설정을 전달하는 한 방법
  • 브라우저에 전달할 값과 서버에서만 사용할 값을 구분

발표용 본문:
비밀정보 관리 - 보관 장소와 전달 경로 제한
  • 서버 전용 키는 서버에서만 사용하고 저장소·로그 노출 방지
  • 환경 변수라도 브라우저 번들에 포함되면 사용자가 읽을 수 있음
노출 대응 - 기존 자격 폐기와 새 값 적용
  • 공개 파일에서 문자열만 삭제해도 기존 키의 효력은 유지
  • 유출된 키를 폐기하고 안전한 경로로 새 키 주입

  • 개발·검증 작업이 운영 저장소에 닿지 않도록 연결 분리
연결 확인 - 설정 이름보다 실제 대상 검증
  • 환경 전환 시 실제 연결된 DB와 사용하는 자격정보 확인
