챕터 6 보충 자료 — 환경 분리와 서비스 운영 심화
2026-11-09 / 초심자 본문 5장의 추가 읽기 자료

1. 별도 검증 환경(staging)
개발은 변경 작성, 검증은 공개 전 확인, 운영은 실제 서비스 제공을 위한 실행 환경이다. 이번 실습은 로컬 실행과 Vercel·Render 배포를 중심으로 하며 별도 검증 서버·DB를 자동 구성하지 않는다. 규모가 커지면 검증 환경에서 변경을 확인하고 운영에 적용할 수 있다. 관리자 화면은 서비스 기능이며 개발·검증·운영 환경과 다른 구분이다.

2. 환경별 데이터 분리
로컬과 배포 서비스의 주소가 달라도 같은 Supabase 프로젝트를 설정하면 인증 계정과 업무 데이터를 공유할 수 있다. 실제 데이터를 보호해야 하는 서비스에서는 개발·검증용 프로젝트와 자격정보를 별도로 두는 설계를 고려한다. URL이나 NODE_ENV 값만 바꾸는 것으로 DB가 자동 분리되지 않는다. 초기화·삭제 명령은 실제 연결 대상을 확인한 환경에서만 실행한다.

3. 빌드·실행 설정과 실제 실습 파일
클라이언트 package.json의 npm run build는 Vite 빌드이며 dist를 생성한다. Vercel 설정은 해당 결과를 제공한다. 개발용 npm run dev와 공개 배포는 다르다.
서버 package.json의 빌드는 TypeScript 컴파일 외에 copy-data.ts 실행도 포함한다. 본문은 TypeScript → JavaScript 생성 → npm start의 핵심 경로를 발췌했다. 시작 명령은 node dist/server.js다. 설치·검사·빌드의 상세 명령은 실습서를 따른다.
클라이언트 VITE_ 설정은 빌드 결과에 포함되므로 배포 설정을 바꾼 뒤 재빌드해야 한다. 로컬에서는 Vite를 재시작한다. 서버의 실행 환경변수 변경도 실행 중인 프로세스에 자동 반영되는 것으로 보지 않으며 새 프로세스로 반영한다. 로컬 .env 파일이 배포 서비스에 자동 등록되는 것은 아니다.
서버 PORT는 배포 환경의 값을 읽으며 기본값은 3000이다. 브라우저용 Publishable key와 서버 Secret key의 역할은 챕터 4에서 설명한다. 키 유출 대응 심화는 다음 주 보안 범위다.

4. 배포 주소와 두 종류의 인증 복귀 주소
VITE_API_BASE_URL에는 본인 Render의 HTTPS 기본 주소를 지정한다. /api 경로는 클라이언트 요청 코드가 추가한다.
CLIENT_URL에는 Vercel의 프로토콜·호스트·필요한 포트를 포함한 기본 주소를 등록하고 화면 경로나 끝 슬래시는 넣지 않는다. Supabase Site URL은 배포 화면의 기본 주소이며 Redirect URLs에 그 주소의 /auth/callback을 등록한다. vercel.json의 rewrite는 이 직접 접근을 index.html로 연결한다.
Google·네이버에서 Supabase로 돌아오는 제공자 콜백과 Supabase에서 FoodMap 화면으로 돌아오는 주소는 별개다. 제공자 설정에는 실습서에 따라 배포 화면 주소도 갱신한다. 로컬 브라우저 주소의 localhost와 127.0.0.1을 로그인 시작·복귀 중 임의로 섞지 않는다.
CORS·출처 정책의 방어 원리는 다음 주에 다루고 이번 본문에서는 필요한 주소의 역할과 등록 위치만 다룬다.

5. 데이터베이스 마이그레이션
마이그레이션은 DB 구조 변경을 순서와 이력으로 관리하는 방식이다. 이번 실습의 supabase/schema.sql은 테이블·함수·권한 준비에 사용하는 실제 SQL이다. 파일 저장이나 Git 업로드·웹 빌드만으로 원격 DB가 바뀌지 않으며 DB에서 별도로 실행한다. 여러 환경에 변경을 적용하는 마이그레이션 자동화, 기존 행 보완과 이전 버전 호환성은 심화 범위다. 이전 강의의 reports.review_status는 일반 설계 예시였으며 현재 실습의 submissions.status와 구분한다.

6. 운영 지표와 기록
본문의 Network·서버 로그 확인은 학생이 실패한 요청 위치를 찾는 수준이다. p95 응답 시간은 요청의 95%가 그 시간 이내에 응답했다는 지표이고, 요청 실패율은 관측 구간의 요청 중 실패 비율이다. 현재 실습에 지표 대시보드를 구현했다는 뜻은 아니다. 배포 시점과 오류 증가가 겹쳐도 원인을 단정하지 않고 요청·오류 기록을 확인한다. 서버가 모든 요청을 자동으로 기록하는 별도 접근 로그 기능도 본문에서 가정하지 않는다.

7. 백업·롤백·복원
백업은 특정 시점 데이터의 별도 사본이다. 보관 범위·주기·보존 기간과 실제 복원 가능성을 함께 확인한다. DB 백업과 업로드 파일 본문의 사본 범위는 별도로 확인해야 한다.
배포 롤백은 이전 코드·설정으로 돌아가는 작업이며 삭제 데이터나 DB 구조를 자동으로 되돌리지 않는다. 현재 DB와 이전 코드가 함께 동작할 수 있는지 확인한다.
데이터 복원은 사본으로 필요한 데이터를 되살리는 작업이다. 손상 범위·복원 시점·사본 이후의 정상 변경을 확인하고 격리된 환경에서 검증한 뒤 반영 범위를 정한다. 세 작업의 실제 실행 절차는 이번 실습 필수 범위에 포함하지 않는다.
