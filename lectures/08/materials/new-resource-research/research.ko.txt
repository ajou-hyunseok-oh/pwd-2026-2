제작 순서와 공용화

우선순위는 발표 순서가 아니라 도식 제작·내용 검토 순서. 실제 강의 순서는 확정안을 유지.
1) 1.3·1.5~1.6과 3.3·3.7~3.8: 주장/검증, 해시/솔트, 외부 신원/내부 계정의 혼동 방지.
2) 4.3~4.7: 같은 사용자·행 데이터로 소유자 판단→API 검사→RLS→특권 키 범위를 연결.
3) 6.4~6.8: 하나의 URL 표와 브라우저 경계를 확장해 출처→사이트→SOP→CORS→CSRF 연결.
4) 7.1·7.4·7.9~7.10: 사용자/관리자 기능 구분과 실행 환경 구분, 코드 복귀와 데이터 복원을 분리.
5) 나머지 장: 같은 레코드·상태도·시간축을 변형해 제작.
작업량 소: 기존 표·코드·흐름 블록의 내용 교체. 중: 새 연결 관계 또는 복합 결과 검토 필요. 시간 견적은 아님.

- identity: 사용자·계정·제보 연결: 같은 ID와 레코드 카드를 이어 사용
- password: 비밀번호 검증: 1.5의 해시 흐름에 1.6에서 솔트 추가
- request: 요청·응답 시퀀스: 기존 resource_blocks.py의 레인과 화살표 재사용
- time: 시간축: 유효 시간·반복 시도·관측·백업 시점을 같은 읽기 방향으로 표현
- policy: 정책 표와 판단 분기: 행위자·행동·대상·조건을 고정된 순서로 배치
- operations: 운영 업무: 제보 r101의 화면·상태·DB 변경·이력을 이어 사용
- browser: 브라우저 경계: 동일 URL 집합과 브라우저·서버 레인 재사용
- environment: 환경·버전·데이터: 개발/검증/운영의 3열을 고정하고 필요한 요소만 추가

슬라이드별 상세 조사

1.1 · 화면 3 · 서비스의 사용자 식별
부제: 저장된 데이터와 요청한 사용자를 연결할 필요
확정 문단: 지난주에는 FoodMap의 맛집 데이터를 서버와 데이터베이스에 저장해 다시 조회할 수 있게 했다. 여기에 사용자의 제보를 연결하려면 데이터의 내용뿐 아니라 누가 그 데이터를 보냈는지도 구분해야 한다. 사용자 식별은 여러 요청과 기록을 같은 사람에게 연결하는 출발점이며, 데이터가 저장되어 있다는 사실만으로 요청자의 신원이 확인되지는 않는다.
선수 개념: 06주차 9~14장: 클라이언트·서버, HTTP/HTTPS, 요청·응답, JSON, REST API / 07주차: 테이블·기본 키·외래 키·관계와 FoodMap 맛집 데이터의 영구 저장
추천 자료: 관계도 — 사용자와 제보의 연결 전후
구성·사례: 맛집 목록 옆에 작성자를 알 수 없는 제보 r101을 놓고, 사용자 u123과 연결한 후의 모습을 비교. 계정 속성은 아직 펼치지 않음.
학생이 확인할 차이: 데이터가 존재하는 것과 그 데이터를 보낸 사람을 구분하는 것은 별개의 문제.
학습 범위·제외: 07주차 테이블·관계와 HTTP만 사용. 역할·허용/거부·로그인 토큰은 표시하지 않음.
수정·재사용: 07주차 데이터 카드 형식; 이후 1.2·3.7·4.3에서도 u123/r101 유지.
근거: [authn] https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html

1.2 · 화면 4 · 사용자 계정
부제: 서비스 안에서 같은 사용자를 구분하는 고유 식별자
확정 문단: 사용자 계정은 서비스가 한 사용자를 지속적으로 구분하기 위해 관리하는 기록이다. 고유한 사용자 ID를 기준으로 이름과 연락처 같은 정보를 연결하면 표시 이름이 바뀌어도 같은 사용자의 기록을 유지할 수 있다. FoodMap의 제보도 이름 문자열보다 사용자 ID에 연결하는 편이 안정적이며, 이 ID는 사용자를 가리키는 값이다.
선수 개념: 1.1 서비스의 사용자 식별 / 07주차: 테이블·기본 키·외래 키·관계와 FoodMap 맛집 데이터의 영구 저장
추천 자료: 표 — 이름 변경 전후의 사용자 ID와 제보 연결
구성·사례: 두 시점의 user_id=u123, display_name=민수/민수의 맛지도와 r101.user_id=u123을 나란히 표시.
학생이 확인할 차이: 이름이 달라져도 ID와 제보 연결은 유지됨.
학습 범위·제외: 고유 ID는 식별 수단. 비밀번호 증명·외부 계정 연결을 미리 설명하지 않음.
수정·재사용: 1.1 카드의 사용자 부분만 확장.
근거: [authn] https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html

1.3 · 화면 5 · 클라이언트 입력의 신뢰 경계
부제: 사용자가 보낸 주장과 서버가 확인한 사실의 구분
확정 문단: 요청에 사용자 ID가 들어 있어도 그 값을 보낸 사람이 해당 계정의 사용자라고 바로 판단할 수는 없다. 브라우저에서 보내는 값은 사용자가 바꿀 수 있으므로 서버는 클라이언트의 주장과 직접 확인한 사실을 구분해야 한다. FoodMap 요청의 작성자 ID를 다른 사람의 값으로 바꾸는 사례는 식별자를 전달하는 것만으로 신원을 증명할 수 없음을 보여준다.
선수 개념: 1.2 사용자 계정 / 06주차 9~14장: 클라이언트·서버, HTTP/HTTPS, 요청·응답, JSON, REST API
추천 자료: 도식 — 클라이언트의 주장과 서버의 확인 경계
구성·사례: 브라우저가 보낸 userId=u999에 ‘변경 가능’ 표시. 서버 경계 너머에는 ‘요청의 주장만으로 신원 확정 불가’ 표시.
학생이 확인할 차이: 요청 본문에 적힌 ID를 곧바로 요청자의 ID로 믿을 수 없음.
학습 범위·제외: 해결 방법을 인증·JWT 검증 코드로 앞당기지 않음. 1.4에서 증거 확인을 설명할 여지 유지.
수정·재사용: 1.1 레코드의 ID를 변경하는 사례만 추가.
근거: [authn] https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html / [authz] https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html

1.5 · 화면 7 · 비밀번호 해시
부제: 비밀번호 원문 대신 검증용 값을 생성해 저장하는 원리
확정 문단: 비밀번호 해시는 비밀번호에서 계산한 검증용 값으로, 서버가 원문 비밀번호를 그대로 보관하지 않고도 입력을 확인하는 데 사용한다. 비밀번호 저장에는 반복적인 추측의 비용을 높이도록 설계한 전용 해시 함수를 사용한다. 로그인할 때는 저장된 원문을 꺼내 비교하는 대신 입력한 비밀번호가 저장된 검증 정보와 일치하는지 확인하며, 해시가 유출되어도 추측 위험까지 사라지는 것은 아니다.
선수 개념: 1.4 사용자 인증
추천 자료: 흐름도 — 비밀번호 원문과 검증용 값의 저장 경로
구성·사례: 입력 비밀번호 → 비밀번호 전용 해시 처리 → 검증 정보 저장. 원문을 그대로 보관하는 대안과 저장 대상만 비교.
학생이 확인할 차이: 검증 정보를 저장해 입력을 확인하며, 해시도 추측 공격에 대비해야 함.
학습 범위·제외: 솔트의 구조는 1.6에 배치. SHA-256 단독 예제·복호화 화살표·자체 암호 구현 제외.
수정·재사용: 1.6에서 같은 해시 처리 상자에 솔트 입력만 더하고, 기존 1.7 로그인 흐름으로 연결.
근거: [password] https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html

1.6 · 화면 8 · 비밀번호 솔트
부제: 같은 비밀번호도 서로 다른 해시가 되도록 더하는 계정별 값
확정 문단: 솔트는 비밀번호를 해시할 때 함께 사용하는 무작위 값으로, 같은 비밀번호를 선택한 계정들도 서로 다른 해시 결과를 갖게 한다. 솔트는 해시와 함께 보관할 수 있으며, 입력을 검증할 때 해당 계정에 저장된 솔트를 다시 사용한다. 두 사용자가 같은 비밀번호를 쓰더라도 저장 결과가 같지 않으므로, 한 번 계산한 추측 결과를 여러 계정에 그대로 대입하기 어려워진다.
선수 개념: 1.5 비밀번호 해시 / 1.2 사용자 계정
추천 자료: 표 — 같은 비밀번호·서로 다른 솔트·서로 다른 저장 결과
구성·사례: 열: 계정 / 입력 비밀번호 / 계정별 솔트 / 저장 결과. 두 행은 동일 비밀번호, 서로 다른 salt-A·salt-B와 hash-A·hash-B. 값은 계산 결과가 아닌 도식용 기호로 명시.
학생이 확인할 차이: 솔트는 비밀키가 아니며 같은 비밀번호의 저장 결과를 계정마다 다르게 함.
학습 범위·제외: 솔트는 해시와 함께 보관. 검증 시 저장된 솔트를 사용하며 매번 새 솔트로 비교하지 않음. pepper는 제외.
수정·재사용: 1.5와 같은 입력·처리·저장 색상 사용.
근거: [password] https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html

2.1 · 화면 11 · HTTP의 무상태성
부제: 이전 요청의 인증 결과가 새 요청에 자동으로 이어지지 않는 특성
확정 문단: 현재 로그인 요청에서 사용자를 확인했더라도 그 결과가 새 HTTP 요청에 자동으로 붙지는 않는다. HTTP는 각각의 요청만으로 이전 인증 결과를 보장하지 않으므로, 애플리케이션이 요청 사이를 연결할 정보를 별도로 관리해야 한다. FoodMap의 로그인 직후 맛집 목록을 다시 요청하는 상황을 통해, 한 번의 사용자 확인과 여러 요청에 걸친 로그인 유지가 다른 문제임을 이해한다.
선수 개념: 1.7 비밀번호 로그인 / 06주차 9~14장: 클라이언트·서버, HTTP/HTTPS, 요청·응답, JSON, REST API
추천 자료: 시퀀스 — 로그인 요청과 다음 조회 요청의 분리
구성·사례: 같은 브라우저→서버 레인에 ① 로그인 요청·결과 ② 맛집 조회 요청을 표시. 두 번째 요청에서 이전 결과를 자동으로 알 수 없는 지점에 표시.
학생이 확인할 차이: 로그인 한 번과 여러 요청의 사용자 연결은 서로 다른 문제.
학습 범위·제외: 다음 장의 Set-Cookie·Cookie·세션 저장소는 아직 넣지 않음.
수정·재사용: 기존 2.2~2.4 시퀀스와 주체 위치·화살표 스타일 통일.
근거: [http] https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview#http_is_stateless_but_not_sessionless

2.5 · 화면 15 · 토큰의 서명
부제: 키를 이용해 토큰의 변조 여부와 발급 주체를 확인하는 원리
확정 문단: 토큰에 사용자 정보를 직접 담으면 그 내용을 사용자가 바꾸지 않았는지 확인할 방법이 필요하다. 서명은 발급자가 관리하는 암호학적 키를 이용해 검증 가능한 값을 붙이는 방식이며, 수신자는 신뢰하는 발급자의 검증 키와 방법으로 무결성을 확인한다. FoodMap 사용자 ID를 임의로 바꾼 토큰은 검증에 실패하도록 만들 수 있지만, 서명만으로 토큰 내용이 숨겨지는 것은 아니다.
선수 개념: 2.4 인증 토큰
추천 자료: 비교도 — 토큰 내용 유지와 변조의 검증 결과
구성·사례: 발급된 ‘사용자 u123 + 서명’과 내용만 u999로 바꾼 증표를 같은 검증 상자에 통과시켜 성공/실패 비교. 검증 상자에는 신뢰하는 발급자의 키 표시.
학생이 확인할 차이: 서명 검증은 변조를 탐지하며 내용을 숨기는 기능과 구분됨.
학습 범위·제외: JWT의 세 부분·Base64url·알고리즘 수식은 2.6 이후. 특정 키 방식의 세부를 섞지 않고 일반 서명 원리로 한정.
수정·재사용: 기존 2.4 토큰 모양과 2.7 검증 단계의 시각 표현 재사용.
근거: [jws] https://www.rfc-editor.org/rfc/rfc7515.html#section-3

2.8 · 화면 18 · 인증 상태의 만료
부제: 한 번 확인한 인증 결과를 계속 신뢰할 수 있는 시간의 제한
확정 문단: 인증 상태의 만료는 과거의 인증 결과를 신뢰할 수 있는 시간을 제한하는 장치다. 서버 세션은 마지막 활동이나 생성 시점을 기준으로 종료할 수 있고, JWT는 exp에 기록된 시각을 기준으로 유효성을 판단한다. 서버의 인증 상태가 만료되었다면 브라우저에 식별자나 토큰이 남아 있더라도 유효한 인증으로 받아들이지 않는다.
선수 개념: 2.3 서버 세션 / 2.7 JWT 검증
추천 자료: 시간축 — 서버 세션과 JWT의 만료 시점
구성·사례: 위에는 서버 세션의 마지막 활동/최대 수명 기준, 아래에는 JWT exp 기준 시간축. 만료 뒤 같은 증표를 제출하는 요청을 거부로 표시.
학생이 확인할 차이: 브라우저에 값이 남아 있어도 서버에서 유효하지 않을 수 있음.
학습 범위·제외: 수명 숫자는 설명용으로만 표시. 쿠키 Max-Age를 서버의 인증 만료와 동일시하지 않음.
수정·재사용: 기존 2.3 세션·2.7 exp 검증 라벨 연결; 2.9 갱신 도식으로 이어짐.
근거: [session] https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html / [oidc] https://openid.net/specs/openid-connect-core-1_0.html

2.9 · 화면 19 · 리프레시 토큰
부제: 비밀번호 재입력 없이 새 액세스 토큰을 발급받는 자격정보
확정 문단: 액세스 토큰의 수명을 짧게 유지하면서 매번 비밀번호를 입력하지 않게 하려면 새 토큰을 발급받는 절차가 필요하다. 리프레시 토큰은 이 갱신에 사용하는 별도의 자격정보로, 일반 데이터 API 대신 인증 시스템에 제출한다. 인증 시스템이 갱신 자격을 확인하면 새 액세스 토큰을 발급하며, 토큰을 계속 발급받는 데 악용될 수 있는 갱신 자격은 별도로 보호해야 한다.
선수 개념: 2.8 인증 상태의 만료 / 2.4 인증 토큰
추천 자료: 시퀀스 — 만료된 액세스 토큰의 갱신
구성·사례: RFC 6749 Figure 2의 클라이언트/데이터 API/인증 시스템 레인 유지. 데이터 요청→만료 응답→인증 시스템에 갱신 자격 제출→새 액세스 토큰→데이터 요청 순서.
학생이 확인할 차이: 갱신 자격의 제출 대상은 일반 데이터 API가 아니라 인증 시스템.
학습 범위·제외: 원본의 Authorization Grant 시작 단계와 OAuth 역할명은 제거. 3.2의 외부 권한 위임은 아직 설명하지 않음.
수정·재사용: 기존 resource-sequence 블록 확장; RFC ASCII 도식 전체 스크린샷은 불필요.
근거: [refresh] https://www.rfc-editor.org/rfc/rfc6749.html#section-1.5

3.3 · 화면 24 · OIDC의 사용자 인증
부제: 외부 인증 제공자의 ID 토큰으로 사용자 신원을 확인하는 방식
확정 문단: OIDC는 OAuth 기반의 흐름에 사용자 인증 결과를 전달하는 규칙을 더한 체계다. 제공자가 OIDC를 지원하면 서비스는 ID 토큰의 서명과 발급자, 수신 대상, 유효 조건을 검증해 누구의 인증 결과인지 확인할 수 있다. ID 토큰은 사용자의 신원을 전달하고 외부 API용 액세스 토큰은 외부 데이터 접근에 사용되므로, 두 토큰의 목적과 받아들이는 대상을 구분한다.
선수 개념: 3.2 OAuth의 접근 권한 위임 / 2.7 JWT 검증
추천 자료: 비교도 — ID 토큰과 외부 API 액세스 토큰의 목적지
구성·사례: 제공자에서 나온 두 증표를 분기: ID 토큰→FoodMap의 신원 확인, 액세스 토큰→외부 API 데이터 접근. 목적/수신 대상 두 행 표를 함께 사용.
학생이 확인할 차이: 같은 로그인 과정에 있어도 토큰의 목적과 받아들이는 곳은 다름.
학습 범위·제외: 2.7의 검증 항목만 참조. code·state·PKCE는 3.4~3.6에 남김.
수정·재사용: 기존 3.2 외부 API 주체를 유지하고 색이 아닌 텍스트로 두 토큰 구분.
근거: [oidc] https://openid.net/specs/openid-connect-core-1_0.html

3.7 · 화면 28 · 외부 계정과 서비스 계정의 연결
부제: 인증 제공자와 사용자 식별자로 내부 계정을 연결하는 기준
확정 문단: 외부 인증 결과를 검증한 뒤에는 외부의 사용자 식별자를 FoodMap 내부 계정에 연결해야 한다. OIDC에서는 발급자와 그 발급자가 부여한 사용자 식별자의 조합을 기준으로 외부 계정을 구분하고, 이를 내부 사용자 ID에 대응시킨다. 표시 이름이나 이메일이 같다는 이유만으로 서로 다른 계정을 자동으로 합치지 않으며, 연결된 내부 ID를 기준으로 FoodMap의 제보와 사용자 기록을 유지한다.
선수 개념: 3.3 OIDC의 사용자 인증 / 3.6 인가 코드의 PKCE 보호 / 1.2 사용자 계정 / 07주차: 테이블·기본 키·외래 키·관계와 FoodMap 맛집 데이터의 영구 저장
추천 자료: 표 — 외부 식별자와 내부 계정의 대응
구성·사례: 열: issuer / subject / FoodMap user_id. 공급자 A의 sub=42와 공급자 B의 sub=42를 서로 다른 내부 계정으로 대응. 같은 이메일 사례에는 자동 병합 금지 라벨.
학생이 확인할 차이: 발급자와 사용자 식별자 조합이 외부 계정의 기준이며, 내부 ID는 별도로 유지됨.
학습 범위·제외: 기존 계정에 새 외부 신원을 추가할 때는 양쪽의 확인이 필요함을 메모. 이메일 일치만으로 합치는 코드 제외.
수정·재사용: 1.2 계정 카드에 외부 식별자 두 열만 추가.
근거: [oidc] https://openid.net/specs/openid-connect-core-1_0.html / [authn] https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html

3.8 · 화면 29 · 소셜 로그인 이후의 서비스 인증
부제: 외부 인증 결과를 서비스의 로그인 상태로 이어가는 과정
확정 문단: 외부 계정이 내부 사용자 ID에 연결되면 FoodMap은 앞서 배운 세션이나 토큰 방식으로 자신의 로그인 상태를 만들 수 있다. 이후 FoodMap API 요청은 서비스가 받아들이는 로그인 자격으로 처리하고, 외부 제공자의 액세스 토큰은 필요한 외부 API 접근에 사용한다. 이렇게 하면 비밀번호 로그인과 소셜 로그인 모두 확인된 내부 사용자 ID라는 공통 결과로 이어진다.
선수 개념: 3.7 외부 계정과 서비스 계정의 연결 / 2.3 서버 세션 / 2.4 인증 토큰
추천 자료: 시퀀스 — 외부 인증 완료에서 FoodMap 로그인 상태로
구성·사례: 검증된 외부 신원→3.7 계정 대응→내부 u123→FoodMap 세션 또는 토큰→FoodMap API. 외부 액세스 토큰→외부 API 경로는 옆에 별도 표시.
학생이 확인할 차이: 비밀번호 로그인과 소셜 로그인이 내부 사용자 ID라는 같은 결과로 모임.
학습 범위·제외: 외부 액세스 토큰을 FoodMap API의 사용자 인증에 그대로 대입하지 않음. 세션/토큰 중 선택 가능한 구조로 표시.
수정·재사용: 기존 1.7·2.3·2.4의 끝부분을 연결; 새로운 SDK 초기화 코드 불필요.

4.2 · 화면 32 · 역할 기반 접근 제어

4.3 · 화면 33 · 소유자 기반 접근 제어

4.4 · 화면 34 · 기본 거부 정책
부제: 명시적으로 허용한 규칙이 없으면 요청을 거부하는 기준
확정 문단: 접근 정책에는 규칙이 없거나 판단에 필요한 정보가 부족할 때 어떻게 처리할지도 포함되어야 한다. 기본 거부 정책은 명시적으로 허용된 조건을 충족하지 못한 요청을 거부하는 원칙이다. FoodMap에서는 알 수 없는 역할이나 확인되지 않은 소유 관계를 임의로 허용하지 않으며, 로그인 없이 가능한 맛집 공개 조회도 별도의 허용 규칙으로 표현한다.
선수 개념: 4.2 역할 기반 접근 제어 / 4.3 소유자 기반 접근 제어
추천 자료: 판단도 — 명시적 허용 조건과 나머지 요청
구성·사례: 요청→정해진 허용 조건 충족?→예: 허용 / 아니오·정보 없음: 거부. 공개 맛집 조회도 명시한 허용 분기에 포함.
학생이 확인할 차이: 규칙이 없거나 판단 정보가 부족한 경우가 허용으로 빠지지 않음.
학습 범위·제외: 기본 거부를 모든 요청에 로그인 강제로 설명하지 않음.
수정·재사용: 4.2·4.3의 역할/소유자 사례를 분기 조건으로 사용.
근거: [authz] https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html

4.5 · 화면 35 · API 접근 제어
부제: 서버가 요청마다 사용자와 대상 데이터의 권한을 확인하는 구조
확정 문단: 접근 정책은 실제 데이터 처리를 수행하는 서버에서 요청마다 적용되어야 한다. 서버는 로그인 자격을 검증해 사용자를 확인하고, 대상 데이터와 요청 행동에 대한 권한을 검사한 뒤 작업을 수행한다. FoodMap 화면에서 수정 버튼을 숨겼더라도 사용자가 API 요청을 직접 보낼 수 있으므로, 화면의 표시 조건과 서버의 인가 검사는 각각 자신의 역할을 맡는다.
선수 개념: 4.4 기본 거부 정책 / 2.7 JWT 검증 / 1.3 클라이언트 입력의 신뢰 경계
추천 자료: 시퀀스 — 화면 숨김과 서버의 요청별 검사
구성·사례: 숨긴 수정 버튼 옆에서 직접 API 요청 경로를 표시. API→사용자 확인→행동·대상 권한 확인→DB 처리, 실패는 DB 앞에서 중단.
학생이 확인할 차이: 권한 없는 요청을 실제로 막는 지점은 서버의 처리 경계.
학습 범위·제외: authorize() 한 줄을 완전한 구현처럼 제시하지 않음. RLS와 특권 키는 아직 추가하지 않음.
수정·재사용: 2.7의 인증 검사 뒤에 4.2·4.3 조건을 붙임.
근거: [authz] https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html

4.6 · 화면 36 · 행 수준 보안 정책
부제: 데이터베이스의 각 행에 접근 규칙을 적용하는 방식
확정 문단: 행 수준 보안인 RLS는 데이터베이스가 테이블의 개별 행에 접근 조건을 적용하는 기능이다. 테이블의 기본 접근 권한에 더해 RLS 적용 대상 요청에 행 정책을 검사하며, 검증된 사용자 정보와 행의 소유자를 비교하는 규칙을 만들 수 있다. FoodMap의 자기 제보 조회 정책을 DB에서도 표현할 수 있지만, 정책이 판단에 필요한 사용자 정보를 전달받는 구조와 적용 범위를 함께 확인해야 한다.
선수 개념: 4.5 API 접근 제어 / 4.3 소유자 기반 접근 제어 / 07주차: 테이블·기본 키·외래 키·관계와 FoodMap 맛집 데이터의 영구 저장
추천 자료: 코드 — 자기 제보 SELECT 정책과 반환 행
구성·사례: RLS 활성화·SELECT 정책 코드와 u123/u456/u123 소유 행 3개를 나란히 배치. u123 요청에서는 첫째·셋째 행만 결과로 연결. 이 표의 u123·u456은 실제 UUID를 줄인 표시 이름으로 명시.
학생이 확인할 차이: 애플리케이션 조건 외에 DB가 행 접근 조건을 적용하는 위치를 이해.
학습 범위·제외: Supabase Auth의 검증된 사용자 문맥, SELECT 기본 권한, RLS 적용 역할 전제 명시. NULL 비교 결과를 false 값이라고 쓰지 않음. UPDATE 정책은 제외.
수정·재사용: 4.3의 동일 행을 코드 결과로 재사용. 4.7에서 특권 키의 예외를 확장.

4.7 · 화면 37 · API 키의 권한 범위
부제: 애플리케이션의 API 접근 자격과 사용자 인증의 구분
확정 문단: API 키는 애플리케이션이 API에 접근할 때 사용하는 자격정보로, 로그인한 개인의 신원과는 역할이 다르다. Supabase에서는 공개 가능한 키와 서버 전용 권한 키의 권한 범위가 다르며, 서버 전용 secret 키는 RLS를 우회할 수 있다. FoodMap 서버가 이런 키로 DB에 접근한다면 서버가 각 사용자의 요청을 먼저 인가해야 하고, 키를 브라우저에 노출해서는 안 된다.
선수 개념: 4.6 행 수준 보안 정책 / 2.4 인증 토큰 / 4.5 API 접근 제어
추천 자료: 표 — 공개 앱 키·서버 키·사용자 자격의 차이
구성·사례: 열: publishable key / secret key / 사용자 로그인 JWT. 행: 식별 대상, 노출 위치, DB 사용자 문맥, RLS 적용 여부. 특권 서버 경로에는 별도의 API 인가 필요 표시.
학생이 확인할 차이: 앱 접근 키와 로그인한 개인의 신원을 구분하고 서버 키의 우회 범위를 이해.
학습 범위·제외: 현재 키 명칭 사용. 공개 키가 임의 접근 허용을 뜻하지 않으며 secret 키는 브라우저에 배치하지 않음. 실제 키 문자열은 표시하지 않음.
수정·재사용: 4.5 API와 4.6 DB 경계에 이 표의 경로를 대응.
근거: [keys] https://supabase.com/docs/guides/getting-started/api-keys

4.8 · 화면 38 · FoodMap의 접근 정책
부제: 역할과 데이터 소유 관계를 조합한 요청별 허용 기준
확정 문단: FoodMap의 접근 정책은 사용자 종류, 요청 행동, 대상 데이터의 관계를 한 표에 모아 확인할 수 있다. 공개 맛집 목록은 비로그인 사용자에게 허용하고, 개인 제보는 작성자에게 조회·수정을 허용하며, 전체 제보 조회는 운영자에게 허용하는 식으로 규칙을 정한다. 각 규칙이 API와 적용 대상 DB 정책에서 어떻게 지켜지는지 확인하면 화면의 기능과 실제 데이터 접근 범위를 일치시킬 수 있다.
선수 개념: 4.2 역할 기반 접근 제어 / 4.3 소유자 기반 접근 제어 / 4.4 기본 거부 정책 / 4.5 API 접근 제어 / 4.6 행 수준 보안 정책 / 4.7 API 키의 권한 범위
추천 자료: 표 — FoodMap의 행위자·행동·대상·조건 정책표
구성·사례: 행: 비로그인 공개 맛집 조회 / 작성자 본인 제보 조회·수정 / 운영자 전체 제보 조회. 열: 대상 조건, API 검사, RLS 적용 경로의 DB 조건.
학생이 확인할 차이: 기능별 접근 정책을 하나의 검토 가능한 명세로 표현.
학습 범위·제외: 강의용 설계 정책임을 명시. 4.6 코드는 SELECT 예시이므로 수정 작업의 SQL 구현이 끝난 것처럼 보이지 않게 함. 공개 상태의 구체 기준은 5.4에 남김.
수정·재사용: 4.2~4.7 표를 합성. 새 권한 체계나 전체 CRUD 코드 추가 불필요.
근거: [authz] https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html / [rls] https://supabase.com/docs/guides/database/postgres/row-level-security / [keys] https://supabase.com/docs/guides/getting-started/api-keys

5.1 · 화면 40 · 사용자 서비스와 관리자 시스템
부제: 이용자의 서비스 이용과 운영자의 관리 업무를 나누는 구조
확정 문단: 관리자 시스템은 운영자가 서비스 전체를 관리하는 업무를 수행하도록 구성한 기능과 화면이다. FoodMap의 맛집 탐색·제보 기능은 이용자의 활동에 맞추고, 전체 제보 조회와 관리 기능은 운영자의 업무에 맞춰 구분한다. 두 영역은 서버나 데이터베이스를 함께 사용할 수도 있지만, 진입 화면을 나누는 것과 별개로 관리 요청에는 운영자 권한을 적용해야 한다.

5.2 · 화면 41 · 관리자 권한의 경계
부제: 서비스 운영에 필요한 권한을 업무 범위에 맞게 제한하는 기준
확정 문단: 운영자라는 이름이 모든 시스템의 권한을 한꺼번에 뜻하지는 않는다. FoodMap의 제보를 관리하는 권한과 DB 구조를 바꾸거나 배포 계정을 관리하는 권한은 서로 다른 대상에 대한 권한이다. 관리자 시스템에는 해당 업무에 필요한 기능만 제공하고, 서비스 내부의 운영자 역할을 부여했다는 이유로 서버 전용 키나 클라우드 관리 권한까지 전달하지 않는다.
선수 개념: 5.1 사용자 서비스와 관리자 시스템 / 4.2 역할 기반 접근 제어 / 4.7 API 키의 권한 범위
추천 자료: 표 — 서비스·DB·플랫폼 관리 권한의 대상
구성·사례: 행: FoodMap 운영자 / DB 구조 변경 권한 / 배포 플랫폼 관리 권한. 열: 관리 대상·할 수 있는 일·자동으로 따라오지 않는 권한.
학생이 확인할 차이: 앱의 운영자 역할과 인프라 관리 권한은 서로 다른 권한 부여.
학습 범위·제외: 서비스 내부 admin을 DB superuser나 플랫폼 Owner와 동일시하지 않음. 복잡한 클라우드 IAM 구성은 생략.
수정·재사용: 5.1의 화면·서버·DB 경계를 표의 관리 대상으로 연결.

5.3 · 화면 42 · 운영 업무의 상태 전이
부제: 제보의 처리 상태와 허용 가능한 변경을 정의하는 방식
확정 문단: 운영 업무는 처리 대상의 현재 상태와 그 상태에서 허용되는 변경으로 표현할 수 있다. FoodMap의 제보는 검토 대기에서 승인 또는 반려로 이동하도록 정하고, 서버는 운영자 권한과 현재 상태가 모두 조건에 맞는지 확인한 뒤 변경한다. 이렇게 하면 버튼을 누르는 동작이 어떤 업무 결정을 뜻하는지 명확해지고, 이미 처리한 제보를 다시 처리할 수 있는지도 정책으로 정할 수 있다.
선수 개념: 5.2 관리자 권한의 경계 / 4.1 요청의 인가
추천 자료: 상태도 — 검토 대기에서 승인 또는 반려로
구성·사례: pending→approved / pending→rejected 두 화살표. 화살표 위에 운영자·현재 상태 조건. 이미 승인된 r101에 같은 변경을 다시 요청하면 조건 불충족.
학생이 확인할 차이: 업무 행동에는 허용된 시작 상태와 도착 상태가 있음.
학습 범위·제외: FoodMap의 예시 업무 규칙으로 명시. 보편적인 필수 상태 구조나 결제 인증 절차라고 설명하지 않음.
수정·재사용: 5.1 제보 상세에 상태 표시를 추가; 5.5·5.6에서도 r101 유지.

5.4 · 화면 43 · 콘텐츠 공개 상태
부제: 검토 결과와 사용자에게 보이는 상태를 구분하는 기준
확정 문단: 검토 결과는 제보를 받아들였는지를 나타내고, 공개 상태는 콘텐츠를 일반 이용자에게 보여줄지를 나타낸다. 두 상태를 구분하면 승인된 맛집이라도 정보 확인 중에는 비공개로 둘 수 있고, 문제가 발견되면 승인 이력을 유지한 채 노출만 중지할 수 있다. 따라서 FoodMap의 공개 목록은 승인 여부만 확인하지 않고 서비스가 정한 공개 조건까지 만족하는 데이터를 대상으로 구성한다.
선수 개념: 5.3 운영 업무의 상태 전이 / 4.3 소유자 기반 접근 제어
추천 자료: 표 — 검토 결과와 공개 여부의 두 축
구성·사례: 열: 검토 상태 / 공개 여부 / 사용자 목록 노출. 승인+공개와 승인+비공개를 비교하고 ‘승인 이력 유지, 노출 중지’ 사례 강조.
학생이 확인할 차이: 업무의 승인 결정과 사용자에게 보여주는 결정은 구분됨.
학습 범위·제외: 두 축의 구체 정책은 자체 FoodMap 설계. 원문 OWASP에 동일한 공개 상태표가 있다고 표기하지 않음.
수정·재사용: 5.3 상태를 바꾸지 않고 visibility 열만 추가.

5.5 · 화면 44 · 운영 작업의 트랜잭션
부제: 함께 성공해야 하는 데이터 변경을 하나의 작업으로 묶는 원리
확정 문단: 하나의 운영 결정이 여러 데이터 변경을 요구할 때는 일부만 반영되는 상황을 막아야 한다. 지난주에 배운 트랜잭션으로 제보의 승인 상태 변경과 맛집 데이터 등록을 같은 DB 작업에 묶으면 둘 다 성공하거나 둘 다 취소되게 할 수 있다. 이 보장은 같은 트랜잭션 안의 변경에 적용되므로 브라우저 저장소와 서버 API를 따로 변경하는 동작까지 자동으로 묶어 주지는 않는다.
선수 개념: 5.3 운영 업무의 상태 전이 / 5.4 콘텐츠 공개 상태 / 07주차 41장: 여러 변경을 모두 반영하거나 모두 취소하는 트랜잭션
추천 자료: 도식 — 승인 변경과 맛집 등록의 단일 트랜잭션
구성·사례: 하나의 DB 트랜잭션 괄호 안에 제보 승인 UPDATE와 맛집 INSERT. 모두 성공: 둘 다 반영 / 두 번째 실패: 둘 다 취소를 전후 표로 비교.
학생이 확인할 차이: 연관된 두 DB 변경 중 하나만 남지 않도록 원자성을 적용.
학습 범위·제외: 다른 DB·외부 API·브라우저 저장까지 자동 원자화하지 않음. 조건 확인 없이 INSERT하는 불완전한 SQL 예제는 제외.
수정·재사용: 07주차 트랜잭션 개념을 5.3의 r101 업무에 적용.
근거: [transaction] https://www.postgresql.org/docs/current/tutorial-transactions.html

5.6 · 화면 45 · 중복 요청의 처리
부제: 같은 운영 요청이 반복되어도 결과가 중복되지 않도록 하는 기준
확정 문단: 트랜잭션으로 한 번의 처리를 일관되게 만들었더라도 같은 요청이 다시 도착하면 결과가 중복될 수 있다. 멱등성은 같은 작업을 반복 요청해도 그 작업의 효과가 한 번 수행한 결과와 같도록 처리하는 성질이다. FoodMap의 승인 작업을 구분하는 식별자와 처리 결과를 서버에 기록하고 DB의 중복 제약 등을 함께 사용하면, 응답을 받지 못해 재전송해도 같은 맛집을 다시 만들지 않도록 설계할 수 있다.
선수 개념: 5.5 운영 작업의 트랜잭션 / 5.3 운영 업무의 상태 전이
추천 자료: 시퀀스 — 응답 유실 후 같은 승인 요청 재전송
구성·사례: 첫 요청 operation=approve:r101 처리→결과 저장→응답 유실. 같은 키로 재전송→저장한 결과 반환. 맛집은 1건 유지.
학생이 확인할 차이: 한 번의 원자적 처리와 반복 요청의 중복 방지는 별도 문제.
학습 범위·제외: 헤더만 추가하면 해결되는 것으로 그리지 않음. 서버의 키/요청 일치 확인·중복 제약·원자적 결과 기록이 필요. Stripe 보관 시간은 차용하지 않음.
수정·재사용: 5.5 트랜잭션 상자를 첫 요청 안에 넣고 두 번째 요청에서는 재실행하지 않는 경로 표시.
근거: [idempotency] https://docs.stripe.com/api/idempotent_requests

5.7 · 화면 46 · 감사 로그
부제: 운영자의 작업 주체·대상·결과를 남기는 기록
확정 문단: 감사 로그는 운영 업무의 결과뿐 아니라 누가 어떤 대상을 언제 어떻게 처리했는지 남기는 기록이다. FoodMap의 제보 승인에는 운영자 ID, 제보 ID, 행동, 결과, 시각과 필요한 사유를 연결해 이후에 변경 경위를 확인할 수 있게 한다. 이 기록에는 비밀번호나 토큰 원문을 넣지 않으며, 조회와 변경 권한도 제한해 운영 기록 자체가 임의로 훼손되지 않도록 관리한다.
선수 개념: 5.6 중복 요청의 처리 / 1.2 사용자 계정
추천 자료: 기록표 — 제보 승인 감사 기록 한 행
구성·사례: 가상 행: 시각 2026-11-07T10:00:00+09:00 / 행위자 op-01 / 대상 r101 / 행동 approve / 결과 success / 사유 정보 확인. 필드를 상태 전이와 연결.
학생이 확인할 차이: 최종 상태만으로는 알 수 없는 변경 경위를 기록으로 재구성.
학습 범위·제외: 실제 운영 기록이 아닌 예시 데이터 표시. 비밀번호·토큰·불필요한 개인정보 제외. 모니터링 지표는 7.7에서 다룸.
수정·재사용: 5.3~5.6의 동일 작업에 감사 필드 연결.

6.1 · 화면 48 · 입력 검증

6.2 · 화면 49 · SQL 인젝션
부제: 입력값이 SQL 명령으로 해석될 때의 위험과 방어 원리
확정 문단: SQL 인젝션은 입력 데이터가 SQL 명령문의 일부로 해석되어 원래 의도와 다른 조회나 변경을 유발하는 문제다. FoodMap의 검색어를 SQL 문자열에 직접 이어 붙이면 데이터와 명령의 경계가 흐려질 수 있다. 매개변수화된 쿼리는 명령의 구조와 입력값을 분리해 값을 데이터로 처리하게 하므로, 입력 형식을 검사하는 것과 함께 DB 접근 경로에서 적용해야 한다.
선수 개념: 6.1 입력 검증 / 07주차: SQL로 테이블 데이터를 조회·변경하는 기본 역할

구성·사례: node-postgres client.query의 SQL $1과 [searchTerm]을 두 색으로 대응. 검색어 김's 식당을 값으로 전달하는 경우와 문자열 결합 구조를 비교.
학생이 확인할 차이: 따옴표가 있는 정상 데이터도 명령문 구조와 분리해 처리.
학습 범위·제외: 연결된 서버 pg client와 restaurants.name 열 전제. 값 매개변수는 테이블·열 이름의 치환 수단이 아님. 위험 쿼리는 실행 예제로 제공하지 않음.
수정·재사용: 07주차 SELECT에 값 배열 한 줄만 추가.

6.3 · 화면 50 · 크로스 사이트 스크립팅
부제: 사용자 입력이 웹 페이지의 코드로 실행될 때의 위험
확정 문단: 사용자 입력이 명령으로 해석되는 문제는 데이터베이스뿐 아니라 브라우저 화면에서도 발생한다. XSS는 공격자가 넣은 내용이 웹 페이지의 실행 코드로 처리되어 사용자의 브라우저에서 서비스의 기능에 영향을 주는 공격이다. FoodMap의 제보 설명은 기본적으로 텍스트로 출력하고, HTML을 허용할 필요가 있다면 허용 요소를 제한하는 정제 과정을 적용해 입력 내용과 실행 코드를 구분해야 한다.
선수 개념: 6.1 입력 검증 / 04~05주차: 사용자 입력과 목록을 표시하는 React 화면
추천 자료: 코드 — 문자열 자식과 HTML 해석의 출력 차이
구성·사례: report.description에 <strong>추천</strong> 문자열을 넣고 <p>{report.description}</p>의 결과를 태그까지 보이는 텍스트로 표시. HTML 해석 경로는 별도 경고 도식.
학생이 확인할 차이: 사용자 내용을 텍스트로 표시하는 것과 브라우저가 HTML로 해석하는 것을 구분.
학습 범위·제외: 텍스트 자식 문맥으로 한정. React만 쓰면 모든 URL·HTML·스크립트 문맥이 안전하다는 설명 제외. 실행 공격 코드는 불필요.
수정·재사용: 기존 React 코드·결과 병렬 형식; 원문 dangerouslySetInnerHTML은 참조만 하고 정답 코드로 배치하지 않음.
코드 후보: code-candidates.ko.txt · jsx-text
근거: [react] https://react.dev/reference/react-dom/components/common#dangerously-setting-the-inner-html

6.4 · 화면 51 · 웹 출처
부제: 프로토콜·호스트·포트로 웹 자원의 경계를 구분하는 기준
확정 문단: 브라우저에서 실행되는 코드의 접근 범위를 이해하려면 먼저 웹 출처를 구분해야 한다. 출처는 URL의 프로토콜, 호스트, 포트의 조합으로 정해지며, 경로가 달라도 이 조합이 같으면 같은 출처다. FoodMap 화면과 API가 서로 다른 호스트나 포트에서 제공되면 다른 출처가 되므로, 같은 서비스가 운영한다는 사실과 브라우저의 경계 판단은 별개다.
선수 개념: 6.3 크로스 사이트 스크립팅 / 06주차 9~14장: 클라이언트·서버, HTTP/HTTPS, 요청·응답, JSON, REST API
추천 자료: 표 — 프로토콜·호스트·포트별 출처 판정
구성·사례: 기준 https://app.example.com. /map, /reports, :443, :8443, api.example.com, http://app.example.com을 비교. 경로와 기본 포트를 분리 표시.
학생이 확인할 차이: 경로가 달라도 동일 출처일 수 있고 포트가 다르면 다른 출처.
학습 범위·제외: 사이트·CORS·쿠키 규칙은 아직 설명하지 않음. https 기본 포트 443의 생략 표기를 정확히 대응.
수정·재사용: 6.5에서도 같은 URL 행을 유지.
근거: [origin] https://developer.mozilla.org/en-US/docs/Glossary/Origin

6.5 · 화면 52 · 브라우저의 사이트 구분
부제: 등록 가능한 도메인과 프로토콜을 기준으로 한 사이트 경계
확정 문단: 브라우저는 출처와 함께 사이트라는 더 넓은 경계도 사용한다. 쿠키 정책에서 사용하는 사이트는 프로토콜과 등록 가능한 도메인을 기준으로 구분하므로, HTTPS의 app.example.com과 api.example.com은 출처가 다르지만 같은 사이트다. 등록 가능한 도메인은 example.com이나 example.co.kr 같은 단위이며, 포트와 하위 도메인의 차이가 출처와 사이트 판정에서 다르게 반영된다는 점을 구분해야 한다.
선수 개념: 6.4 웹 출처
추천 자료: 표 — 같은 URL에 출처와 사이트 판정 두 열
구성·사례: 6.4 표에 same-site 열 추가. HTTPS app/api.example.com은 다른 출처·같은 사이트, HTTP/HTTPS는 다른 사이트. example.co.kr을 등록 가능 도메인 보조 예시로 표시.
학생이 확인할 차이: 출처와 사이트는 서로 다른 기준이며 쿠키 정책 이해에 모두 필요.
학습 범위·제외: schemeful site 기준. 도메인의 마지막 두 조각만 취하는 공식은 사용하지 않음. SameSite 속성값은 6.9에서 설명.
수정·재사용: 6.4 표에 한 열만 추가해 차이 강조.
근거: [site] https://developer.mozilla.org/en-US/docs/Glossary/Site / [origin] https://developer.mozilla.org/en-US/docs/Glossary/Origin

6.6 · 화면 53 · 동일 출처 정책
부제: 다른 출처의 응답을 스크립트가 읽는 범위를 제한하는 원칙
확정 문단: 동일 출처 정책은 한 출처에서 실행되는 스크립트가 다른 출처의 자원을 읽거나 조작하는 범위를 제한하는 브라우저의 보안 원칙이다. 다른 사이트에서 실행한 코드가 사용자의 FoodMap 응답을 마음대로 읽지 못하게 하는 것이 대표적인 역할이다. 다만 다른 출처로 보내는 모든 요청을 막는 것은 아니므로, 응답을 읽을 수 있는지와 요청이 서버에 도착할 수 있는지는 구분해야 한다.
선수 개념: 6.4 웹 출처 / 6.5 브라우저의 사이트 구분
추천 자료: 시퀀스 — 요청 도착과 응답 읽기 제한의 위치
구성·사례: 외부 페이지→FoodMap 요청은 도착할 수 있음. 서버 응답→외부 페이지 스크립트 읽기는 브라우저 경계에서 차단. 전송/읽기 화살표를 각각 표시.
학생이 확인할 차이: 동일 출처 정책이 모든 교차 출처 요청 자체를 막는 것은 아님.
학습 범위·제외: CORS 헤더는 6.7에서 추가. 인증이 자동으로 보장된다고 표시하지 않음.
수정·재사용: 6.7에서 응답 허용 조건을, 6.8에서 쿠키 자동 첨부 경로를 같은 레인에 추가.
근거: [sop] https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy

6.7 · 화면 54 · CORS
부제: 서버가 허용한 출처에 브라우저의 응답 읽기를 허용하는 방식
확정 문단: FoodMap 화면과 API의 출처가 다르면 서버가 허용한 범위에서 브라우저가 응답을 읽을 수 있도록 CORS를 설정할 수 있다. 서버는 허용할 출처 등을 응답 헤더로 알리고 브라우저가 그 조건을 적용하며, 일부 요청은 실제 요청 전에 허용 여부를 먼저 확인한다. CORS는 브라우저의 교차 출처 접근 규칙이므로 API에 직접 보내는 요청의 사용자 인증이나 권한 검사를 대신하지 않는다.
선수 개념: 6.6 동일 출처 정책 / 4.5 API 접근 제어
추천 자료: 시퀀스 — CORS 응답 허용과 필요한 경우의 사전 확인
구성·사례: MDN simple SVG를 주자료로 단순화: Origin 요청 헤더→서버의 허용 출처 응답→브라우저의 읽기 판단. preflight SVG는 JSON POST 등 필요한 경우의 OPTIONS 단계를 추가하는 보조 원형.
학생이 확인할 차이: 응답을 읽을 수 있게 하는 브라우저 규칙이며 사용자 권한 검사와 별개.
학습 범위·제외: 모든 요청에 OPTIONS가 있는 것처럼 그리지 않음. 자격정보 요청에 ACAO:* 사용 불가. 허용 목록 없이 요청 Origin을 그대로 반사하는 코드 제외.
수정·재사용: 6.6 레인을 재사용. 원본의 foo/bar 주소·XML·X-PINGOTHER·장황한 헤더를 FoodMap에 맞춰 줄이고 전체 그림 2개를 한 장에 억지로 배치하지 않음.
확보 파일: reference-figures/mdn-cors-simple.svg, reference-figures/mdn-cors-preflight.svg
근거: [cors] https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS

6.8 · 화면 55 · 크로스 사이트 요청 위조
부제: 브라우저가 자동으로 보내는 인증정보를 이용한 요청 위조
확정 문단: 응답을 읽지 못해도 요청을 보낼 수 있다는 점은 로그인된 브라우저에서 중요한 문제가 된다. CSRF는 다른 페이지가 사용자의 의도와 다른 요청을 유발하고, 브라우저가 조건에 따라 자동 첨부한 로그인 쿠키를 서버가 받아들이는 상황을 악용한다. FoodMap의 관리 요청에는 허용된 요청 출처와 공격자가 알 수 없는 확인값을 검증하는 방어 등을 적용해, 로그인 자격이 있다는 사실에 더해 허용된 경로의 요청인지 확인한다.
선수 개념: 6.7 CORS / 6.5 브라우저의 사이트 구분 / 2.2 쿠키 / 2.3 서버 세션 / 5.3 운영 업무의 상태 전이
추천 자료: 시퀀스 — 다른 페이지가 유발한 로그인 브라우저의 요청
구성·사례: 외부 페이지→피해자 브라우저→FoodMap 상태 변경 API. 조건에 따라 첨부된 로그인 쿠키와 별도로 CSRF 확인값·요청 출처 검증을 서버 경계에 표시.
학생이 확인할 차이: 자격이 첨부되었다는 사실만으로 사용자의 의도에 맞는 요청이라 판단할 수 없음.
학습 범위·제외: 쿠키가 모든 상황에 무조건 붙는다고 단정하지 않음. 실제 적용 조건과 SameSite 속성은 6.9로 연결. XSS 공격 코드나 전체 토큰 발급 구현은 제외.
수정·재사용: 6.6의 요청/읽기 구분을 그대로 두고 서버의 상태 변경 위치만 강조.
근거: [csrf] https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html

6.10 · 화면 57 · 로그인 시도 제한
부제: 반복되는 인증 요청의 횟수와 속도를 제어하는 방어
확정 문단: 브라우저 경계와 쿠키를 보호하더라도 공격자가 로그인 API에 비밀번호를 반복해서 제출하는 시도는 별도로 통제해야 한다. 로그인 시도 제한은 계정과 요청 출처 등의 기준으로 일정 시간의 실패 횟수나 요청 속도를 관찰하고 지연 또는 제한을 적용하는 방식이다. FoodMap에서는 정상 사용자의 재시도 여지를 두면서 자동 추측 비용을 높이고, 공격자가 타인의 계정을 계속 잠그는 방식으로 제한을 악용하지 못하도록 기준을 정한다.
선수 개념: 6.9 쿠키의 보호 속성 / 1.7 비밀번호 로그인 / 6.1 입력 검증
추천 자료: 시간축 — 관찰 구간의 로그인 실패와 지연·제한
구성·사례: 같은 계정으로 반복되는 실패 시점과 점진적 지연을 표시. 요청 출처가 바뀌어도 계정 기준 관측이 이어지는 보조 표시.
학생이 확인할 차이: 계정과 출처 등을 함께 보고 반복 추측 비용을 높임.
학습 범위·제외: 표시 횟수·시간은 예시 정책. IP만 제한하거나 타인 계정을 무기한 잠그는 단순 구현은 제외.
수정·재사용: 2.8 시간축의 스타일을 반복 요청 관찰에 재사용.
근거: [authn] https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html

7.1 · 화면 59 · 개발·검증·운영 환경
부제: 실험과 검증이 실제 사용자 서비스에 영향을 주지 않도록 나누는 실행 공간
확정 문단: 보안 기능을 갖춘 서비스도 개발 중인 변경이 실제 사용자에게 바로 영향을 주면 안정적으로 운영하기 어렵다. 개발 환경은 변경을 만드는 공간, 검증 환경은 배포 전에 동작을 확인하는 공간, 운영 환경은 실제 사용자에게 서비스를 제공하는 공간으로 구분한다. 각 환경 안에 사용자 화면과 관리자 화면이 함께 있을 수 있으므로, 업무에 따른 기능 분리와 실행 목적에 따른 환경 분리는 서로 다른 기준이다.
선수 개념: 5.1 사용자 서비스와 관리자 시스템 / 06주차 25장 및 07주차 실습: 서버·클라이언트의 배포와 DB 연결
추천 자료: 구성도 — 세 실행 환경과 각 환경 안의 두 업무 화면
구성·사례: 개발/검증/운영 3열. 각 열 안에 사용자 화면·관리자 화면을 함께 표시하고 목적 라벨 추가. Supabase 원본의 3개 환경 구분만 참조.
학생이 확인할 차이: 기능에 따른 사용자/관리자 구분과 실행 목적에 따른 환경 구분은 서로 다른 축.
학습 범위·제외: Git main/develop/feature와 CI 상세는 원본에서 제거. DB·자격 분리의 구체 내용은 7.4에 추가.
수정·재사용: 5.1 화면 두 개를 각 환경에 재배치. 7.4~7.6·7.9~7.10의 기본 판으로 사용.
확보 파일: reference-figures/supabase-environments.svg
근거: [environments] https://supabase.com/docs/guides/deployment/managing-environments

7.3 · 화면 61 · 비밀정보 관리
부제: 외부에 공개되면 안 되는 자격정보의 보관과 교체
확정 문단: 환경별 설정 중 서버 전용 키와 같은 비밀정보는 보관 장소와 전달 경로를 제한해야 한다. 환경 변수에 넣었더라도 브라우저용 코드에 포함되어 배포되면 사용자가 읽을 수 있으므로, 비밀정보는 서버에서 관리하고 저장소와 로그에 남기지 않는다. 키가 유출되면 해당 키를 폐기하고 새 키를 적용해야 하며, 공개된 파일에서 문자열만 삭제해도 이전 키의 효력이 사라지는 것은 아니다.
선수 개념: 7.2 환경별 설정 / 4.7 API 키의 권한 범위 / 2.5 토큰의 서명
추천 자료: 흐름도 — 환경 변수에서 서버 또는 브라우저로 향하는 경로
구성·사례: 서버 전용 secret→서버 프로세스, VITE_공개설정→빌드→브라우저 번들 경로를 비교. 노출된 키는 폐기→교체 단계로 표시.
학생이 확인할 차이: 환경 변수라는 보관 형태만으로 비밀성이 보장되지는 않음.
학습 범위·제외: 실제 키 대신 SERVER_SECRET 같은 이름만 표시. 모든 프레임워크의 규칙이 VITE_라고 일반화하지 않음.
수정·재사용: 기존 7.2 환경 설정 코드에 전달 대상 도식 추가.
근거: [vite] https://vite.dev/guide/env-and-mode#env-variables / [secrets] https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html

7.4 · 화면 62 · 환경별 데이터 분리
부제: 개발·검증 작업이 운영 데이터에 닿지 않도록 저장소를 분리하는 기준
확정 문단: 서로 다른 주소로 실행되는 서비스가 같은 데이터베이스에 연결되어 있다면 개발 작업이 운영 데이터에 영향을 줄 수 있다. 환경별 데이터 분리는 저장소와 접근 자격을 구분해 개발·검증 작업이 운영 데이터에 닿지 않도록 하는 구성이다. FoodMap의 테스트 제보 초기화는 테스트 DB에서만 수행되도록 만들고, 환경을 전환할 때 실제 연결 대상도 함께 확인해야 한다.
선수 개념: 7.3 비밀정보 관리 / 7.1 개발·검증·운영 환경 / 07주차: 테이블·기본 키·외래 키·관계와 FoodMap 맛집 데이터의 영구 저장
추천 자료: 구성도 — 환경별 서버·DB·접근 자격의 분리
구성·사례: 7.1의 3열 각각에 서버→해당 DB와 해당 자격만 연결. 개발 서버→운영 DB의 잘못된 교차 연결은 별도의 실패 사례로 한 번 비교.
학생이 확인할 차이: 주소만 다르고 DB가 같으면 운영 데이터가 분리되지 않음.
학습 범위·제외: DB 분리와 접근 자격을 함께 표시. 운영 데이터 전체를 개발로 그대로 복사하는 절차는 제외.
수정·재사용: Supabase 환경 그림의 세 저장소 관계를 7.1 기본 판에 추가.

근거: [environments] https://supabase.com/docs/guides/deployment/managing-environments

7.5 · 화면 63 · 서비스 배포
부제: 검증한 코드와 설정을 대상 환경에 반영하는 과정
확정 문단: 서비스 배포는 검증한 코드와 대상 환경의 설정을 실제 실행 환경에 반영하는 과정이다. FoodMap은 검증 환경에서 로그인과 데이터 조회, 관리 기능을 확인한 뒤 운영 환경에 해당 버전을 적용한다. 배포 후에도 적용된 버전과 연결 대상을 확인하고 주요 요청이 정상 처리되는지 살펴야 하며, 서버 프로세스가 실행 중이라는 사실만으로 서비스 전체의 정상 동작을 판단하지 않는다.
선수 개념: 7.4 환경별 데이터 분리 / 7.2 환경별 설정 / 06주차 25장 및 07주차 실습: 서버·클라이언트의 배포와 DB 연결
추천 자료: 흐름도 — 검증한 버전의 운영 반영과 주요 요청 확인
구성·사례: 버전 v2+대상 설정→검증 환경의 로그인·조회·관리 기능 확인→운영 반영→같은 주요 요청 확인. 연결 대상 DB도 확인 항목으로 표시.
학생이 확인할 차이: 프로세스 실행과 서비스 기능의 정상 동작을 구분.
학습 범위·제외: CI YAML·특정 호스팅 클릭 절차·배포 명령은 실습 세션에 남김. 운영의 파괴적 테스트 데이터 초기화 제외.
수정·재사용: 7.1·7.4의 환경 구성에 코드 버전 이동 화살표만 추가.
근거: [environments] https://supabase.com/docs/guides/deployment/managing-environments

7.6 · 화면 64 · 데이터베이스 마이그레이션
부제: 데이터베이스 구조의 변경을 순서와 이력으로 관리하는 방식
확정 문단: 서비스 변경이 새 열이나 제약조건을 요구하면 코드 배포와 함께 데이터베이스 구조의 변경도 관리해야 한다. 마이그레이션은 이런 변경을 순서와 이력이 있는 작업으로 남겨 각 환경에 일관되게 적용하는 방식이다. FoodMap에 제보 처리 상태 열을 추가한다면 기존 행의 값을 어떻게 채울지와 이전 코드가 변경된 구조에서도 동작하는지를 확인하고, 그 조건에 맞춰 DB 변경과 앱 배포의 실행 순서를 정한다.
선수 개념: 7.5 서비스 배포 / 07주차: 테이블·기본 키·외래 키·관계와 FoodMap 맛집 데이터의 영구 저장 / 5.3 운영 업무의 상태 전이
추천 자료: 코드 — 검토 상태 열 추가와 변경 이력
구성·사례: 버전이 붙은 SQL 파일명과 열 추가 코드, schema v1/v2 표를 병렬 배치. 기존 행 보완→새 코드→추가 제약 검토 순서를 보조 라벨로 표시.
학생이 확인할 차이: DB 구조 변경도 이력·실행 순서·기존 데이터와의 호환성을 관리해야 함.
학습 범위·제외: 코드는 확장 첫 단계만. 모든 기존 제보를 pending으로 덮어쓰지 않음. db reset이나 운영 DB 실행 명령 제외.
수정·재사용: 5.3에서 배운 상태를 열로 표현하고 7.5의 버전 흐름에 연결.

7.7 · 화면 65 · 운영 모니터링
부제: 오류와 서비스 지표로 운영 상태를 파악하는 관찰
확정 문단: 배포와 DB 변경이 끝난 뒤에는 서비스가 실제로 어떻게 동작하는지 지속적으로 관찰해야 한다. 운영 모니터링은 오류 기록과 응답 시간, 실패율 같은 지표를 모아 정상 상태의 변화와 장애 징후를 파악하는 활동이다. FoodMap에서는 로그인 실패 증가나 DB 연결 오류를 확인할 수 있으며, 운영자의 변경 경위를 남기는 감사 로그와 함께 보되 각 기록의 목적은 구분한다.
선수 개념: 7.6 데이터베이스 마이그레이션 / 5.7 감사 로그 / 6.10 로그인 시도 제한
추천 자료: 차트 — 배포 시점 전후의 실패율과 지연·오류 기록
구성·사례: 가상 10분 관측값: 요청 수, 5xx 수, p95 응답 시간. 동일 x축의 작은 그래프 2개와 배포 시점 선·DB 연결 오류 한 줄 연결.
학생이 확인할 차이: 상태 변화는 지표로 관측하고 구체 사건은 오류 기록으로 확인.
학습 범위·제외: 실제 FoodMap 측정값이 아닌 설명용 데이터 표시. 배포 뒤 증가했다는 상관관계를 원인 확정으로 단정하지 않음. 감사 로그와 목적 구분.
수정·재사용: 공용 HTML/SVG 차트로 간단히 제작; 외부 모니터링 제품의 복잡한 대시보드 캡처는 불필요.
근거: [telemetry] https://opentelemetry.io/docs/concepts/signals/

7.8 · 화면 66 · 데이터 백업
부제: 운영 데이터의 사본과 복원 가능성을 확보하는 준비
확정 문단: 운영 상태를 관찰해 문제를 발견하더라도 이미 삭제되거나 손상된 데이터가 저절로 돌아오지는 않는다. 백업은 이런 상황에 대비해 특정 시점의 데이터를 별도 사본으로 보관하는 준비이며, 보관 주기와 기간, 접근 권한과 복원 가능성을 함께 관리한다. FoodMap은 어느 시점까지의 데이터를 확보하는지와 그 이후 얼마나 잃을 수 있는지 정하고, 사본이 존재한다는 사실에 더해 실제로 사용할 수 있는 상태인지 확인해야 한다.
선수 개념: 7.7 운영 모니터링 / 7.4 환경별 데이터 분리 / 07주차: 테이블·기본 키·외래 키·관계와 FoodMap 맛집 데이터의 영구 저장
추천 자료: 시간축 — 마지막 백업 이후의 정상 변경과 손실 가능 구간
구성·사례: 09:00 백업→09:15 새 제보→09:30 장애. 백업 사본이 포함하는 시점과 이후 별도 보존해야 할 변경을 색·라벨로 구분.
학생이 확인할 차이: 사본의 존재뿐 아니라 복원할 수 있는 시점과 범위가 중요.
학습 범위·제외: 시간은 예시. 요금제별 자동 백업·보관 기간을 보편 보장하지 않음. Supabase DB 백업과 Storage 파일 바이트 백업 범위를 구분.
수정·재사용: 2.8의 시간축을 사본·데이터 변경에 적용; 7.10에서 같은 시점을 재사용.
근거: [backups] https://supabase.com/docs/guides/platform/backups

7.9 · 화면 67 · 배포 롤백
부제: 문제가 있는 배포를 이전 코드와 설정으로 되돌리는 대응
확정 문단: 배포한 코드나 설정이 장애의 원인이라면 이전에 동작하던 버전으로 되돌리는 롤백을 고려할 수 있다. FoodMap 서버를 이전 버전으로 바꾸기 전에는 이미 적용한 DB 구조와 그 버전이 호환되는지 확인해야 한다. 코드를 되돌리는 동작이 변경된 DB 구조나 삭제된 데이터까지 자동으로 되돌리지는 않으므로, 장애 원인과 되돌릴 대상을 구분해 대응한다.
선수 개념: 7.5 서비스 배포 / 7.6 데이터베이스 마이그레이션 / 7.7 운영 모니터링 / 7.8 데이터 백업
추천 자료: 비교도 — 앱 버전 복귀와 그대로 남는 DB
구성·사례: 운영 앱 v2→v1 화살표, 아래 DB는 현재 스키마·데이터 유지. v1과 현재 DB 사이에 호환성 확인 지점 표시.
학생이 확인할 차이: 배포 버전을 되돌리는 것과 DB 변경을 되돌리는 것은 서로 다른 작업.
학습 범위·제외: Vercel은 배포 복귀의 사례이며 모든 호스팅의 설정 동작을 동일시하지 않음. DB 복원 기능이 함께 실행되는 버튼처럼 표현하지 않음.
수정·재사용: 7.5 버전 화살표 방향만 바꾸고 7.6 DB 변경 상태를 유지.
근거: [rollback] https://vercel.com/docs/instant-rollback / [migrations] https://supabase.com/docs/guides/deployment/database-migrations

7.10 · 화면 68 · 데이터 복원
부제: 백업을 사용해 손상되거나 유실된 데이터를 되살리는 절차
확정 문단: 장애의 대상이 데이터라면 확보한 백업을 이용해 필요한 상태를 되살리는 복원 절차가 필요하다. 복원할 시점을 정하고 격리된 환경에서 데이터와 서비스 동작을 확인한 뒤 반영 범위를 결정하며, 그 시점 이후에 발생한 정상 변경을 어떻게 보존할지도 검토한다. FoodMap의 잘못 삭제된 제보를 복구하는 사례를 통해, 이전 코드로 돌아가는 대응과 데이터 자체를 되살리는 대응을 구분한다.
선수 개념: 7.8 데이터 백업 / 7.9 배포 롤백 / 7.4 환경별 데이터 분리
추천 자료: 흐름도 — 백업을 격리 환경에서 검증한 뒤 필요한 데이터 반영
구성·사례: 선택한 시점 사본→격리 DB 복원→데이터·앱 검증→반영 범위 결정→선별 병합 또는 전환. 백업 이후 정상 제보는 별도로 보존.
학생이 확인할 차이: 코드 버전 복귀와 달리 데이터 자체를 되살리며 복원 이후의 정상 변경도 고려.
학습 범위·제외: 강의용 대응 설계로 명시. 서비스별 복원 가능 방식이 다르므로 운영 DB 덮어쓰기 명령은 포함하지 않음.
수정·재사용: 7.8 시간축의 사본과 7.4의 격리된 DB 표현을 연결.
근거: [backups] https://supabase.com/docs/guides/platform/backups
