01. 사용자 인증의 원리
요청한 사용자의 신원을 확인하는 원리
연결: 지난주의 데이터 저장에서 출발해, 요청한 사람이 누구인지 확인하는 문제로 확장.
범위: 로그인 성공으로 사용자 식별이 끝나는 지점까지. 쿠키·세션 발급이나 역할 판단은 뒤 챕터에서 설명.

| 설계 번호 | 타이틀 | 서브타이틀 | 선수 개념 위치 | 연결 사례 |
| --- | --- | --- | --- | --- |
| 1.1 | 서비스의 사용자 식별 | 저장된 데이터와 요청한 사용자를 연결할 필요 | prior-web, prior-data | 맛집 목록은 저장되지만 누가 제보했는지는 별도로 확인해야 하는 상황 |
| 1.2 | 사용자 계정 | 서비스 안에서 같은 사용자를 구분하는 고유 식별자 | 1.1, prior-data | 표시 이름이 바뀌어도 같은 사용자 ID로 연결되는 계정 |
| 1.3 | 클라이언트 입력의 신뢰 경계 | 사용자가 보낸 주장과 서버가 확인한 사실의 구분 | 1.2, prior-web | 요청 본문의 사용자 ID를 다른 사람의 값으로 바꾸어 보내는 상황 |
| 1.4 | 사용자 인증 | 계정에 대한 증거를 확인해 요청자의 신원을 판단하는 과정 | 1.2, 1.3 | 사용자 ID를 아는 것과 그 계정의 비밀번호를 증명하는 것의 차이 |
| 1.5 | 비밀번호 해시 | 비밀번호 원문 대신 검증용 값을 생성해 저장하는 원리 | 1.4 | 비밀번호 원문 저장과 비밀번호 검증용 해시 저장의 비교 |
| 1.6 | 비밀번호 솔트 | 같은 비밀번호도 서로 다른 해시가 되도록 더하는 계정별 값 | 1.5, 1.2 | 같은 비밀번호를 선택한 두 계정의 서로 다른 저장 결과 |
| 1.7 | 비밀번호 로그인 | 입력한 비밀번호를 저장된 검증 정보와 대조하는 흐름 | 1.4, 1.5, 1.6 | 가입 시 검증 정보 저장 → 로그인 시 검증 → 서버가 사용자 ID 확인 |

02. 로그인 상태의 유지
이후 요청에서도 인증된 사용자를 식별하는 방법
연결: 한 번 확인한 사용자를 이후 요청에서도 식별하려면 무엇을 보관하고 전달해야 하는지 설명.
범위: 쿠키는 전달 수단, 세션은 상태 관리, JWT는 토큰 형식이라는 서로 다른 역할을 유지. 역할 claim은 사용하지 않음.

| 설계 번호 | 타이틀 | 서브타이틀 | 선수 개념 위치 | 연결 사례 |
| --- | --- | --- | --- | --- |
| 2.1 | HTTP의 무상태성 | 이전 요청의 인증 결과가 새 요청에 자동으로 이어지지 않는 특성 | 1.7, prior-web | 로그인 요청과 그 뒤의 맛집 조회 요청을 따로 받는 서버 |
| 2.2 | 쿠키 | 브라우저가 값을 저장하고 조건에 맞는 요청에 첨부하는 방식 | 2.1 | 응답의 Set-Cookie → 브라우저 저장 → 이후 요청의 Cookie |
| 2.3 | 서버 세션 | 세션 식별자로 서버에 보관한 로그인 상태를 찾는 구조 | 2.2, 1.7 | 브라우저의 임의 식별자와 서버의 사용자 연결 기록 |
| 2.4 | 인증 토큰 | 이후 요청에서 인증 결과를 확인하는 데 사용하는 증표 | 2.3, 1.3, prior-web | 요청에 첨부하는 액세스 토큰의 역할; 세션 식별자도 토큰의 한 형태이며 전달 수단과 형식은 별도 선택 |
| 2.5 | 토큰의 서명 | 키를 이용해 토큰의 변조 여부와 발급 주체를 확인하는 원리 | 2.4 | 사용자 식별 정보를 바꾼 토큰의 검증 실패; 내용의 비밀 보장과 서명의 역할 구분 |
| 2.6 | JWT의 구조 | 서명된 토큰에 사용자 정보와 유효 조건을 담는 형식 | 2.5, prior-web | 서명형 JWT의 헤더·페이로드·서명과 sub·iss·aud·exp의 의미 |
| 2.7 | JWT 검증 | 서명과 발급 조건을 확인해 토큰의 수용 여부를 판단하는 과정 | 2.6, 1.3 | 읽을 수 있는 토큰이라도 서명·발급자·수신 대상·유효 시간이 맞지 않으면 거부 |
| 2.8 | 인증 상태의 만료 | 한 번 확인한 인증 결과를 계속 신뢰할 수 있는 시간의 제한 | 2.3, 2.7 | 서버 세션의 만료와 JWT의 유효 시간 경과 후 요청 처리 |
| 2.9 | 리프레시 토큰 | 비밀번호 재입력 없이 새 액세스 토큰을 발급받는 자격정보 | 2.8, 2.4 | 짧은 수명의 액세스 토큰을 갱신하는 흐름과 갱신용 자격정보의 별도 보호 |
| 2.10 | 로그아웃과 인증 철회 | 인증 방식에 따라 사용 중인 로그인 자격을 종료하는 방법 | 2.3, 2.9, 2.7 | 브라우저 값 삭제·서버 세션 종료·갱신 자격 철회와 이미 발급된 토큰의 남은 유효 시간 |

03. 외부 인증과 소셜 로그인
외부 서비스의 인증 결과와 서비스 사용자 계정의 연결
연결: 서비스가 직접 비밀번호를 확인하는 구조에서 외부 인증 결과를 받아 같은 내부 사용자로 연결하는 구조로 확장.
범위: OAuth는 외부 API 접근 위임, OIDC는 신원 확인으로 구분. 서비스 내부 역할·RLS는 사용하지 않음. 제공자별 설정과 SDK 코드는 실습 범위.

| 설계 번호 | 타이틀 | 서브타이틀 | 선수 개념 위치 | 연결 사례 |
| --- | --- | --- | --- | --- |
| 3.1 | 외부 인증 제공자 | 다른 서비스가 확인한 사용자 신원을 활용하는 구조 | 1.4, 1.7 | FoodMap과 외부 계정 제공자 사이의 비밀번호 확인 책임 구분 |
| 3.2 | OAuth의 접근 권한 위임 | 사용자가 동의한 범위의 외부 API 접근을 허용하는 방식 | 3.1, 2.4, prior-web | 사용자의 비밀번호를 전달하지 않고 외부 프로필 API의 제한된 접근을 허용하는 사례 |
| 3.3 | OIDC의 사용자 인증 | 외부 인증 제공자의 ID 토큰으로 사용자 신원을 확인하는 방식 | 3.2, 2.7 | 외부 API용 액세스 토큰과 신원 확인용 ID 토큰의 목적 비교 |
| 3.4 | 인가 코드 흐름 | 브라우저가 전달한 임시 코드를 토큰으로 교환하는 과정 | 3.3, prior-web | 서버가 교환을 맡는 사례: 외부 화면 이동 → 등록된 복귀 주소로 코드 전달 → 토큰 교환 |
| 3.5 | 로그인 요청의 state | 로그인을 시작한 요청과 돌아온 응답을 연결하는 값 | 3.4 | 시작할 때 보관한 값과 복귀한 값이 일치하는지 확인하는 흐름 |
| 3.6 | 인가 코드의 PKCE 보호 | 코드 발급 요청과 코드 교환 요청을 같은 시작 주체에 연결하는 증명 | 3.4, 3.5 | 일회성 검증값의 변환값을 먼저 보내고 코드 교환 때 원래 검증값을 확인하는 흐름 |
| 3.7 | 외부 계정과 서비스 계정의 연결 | 인증 제공자와 사용자 식별자로 내부 계정을 연결하는 기준 | 3.3, 3.6, 1.2, prior-data | 검증한 제공자·사용자 식별자와 FoodMap 사용자 ID의 대응; 이메일만으로 자동 연결하지 않는 기준 |
| 3.8 | 소셜 로그인 이후의 서비스 인증 | 외부 인증 결과를 서비스의 로그인 상태로 이어가는 과정 | 3.7, 2.3, 2.4 | 외부 ID 토큰·외부 API 액세스 토큰·FoodMap 로그인 자격의 사용처 구분 |

04. 권한과 데이터 접근 제어
사용자에게 허용할 기능과 데이터의 범위
연결: 인증 방식과 무관하게 확인된 사용자가 생긴 뒤, 그 사용자의 개별 요청을 허용할 기준을 학습.
범위: 역할·소유 관계를 먼저 정의하고 검사 위치로 확장. 제보 승인 상태와 공개 상태는 5장에서 처음 설명.

| 설계 번호 | 타이틀 | 서브타이틀 | 선수 개념 위치 | 연결 사례 |
| --- | --- | --- | --- | --- |
| 4.1 | 요청의 인가 | 사용자·행동·대상을 기준으로 요청 허용 여부를 결정하는 과정 | 3.8, 1.4 | 로그인한 사용자라는 사실과 특정 제보를 수정할 수 있다는 판단의 구분 |
| 4.2 | 역할 기반 접근 제어 | 역할에 부여된 권한으로 기능 사용 범위를 정하는 방식 | 4.1 | 일반 사용자와 운영자에게 필요한 기능만 부여하는 최소 권한의 역할 표 |
| 4.3 | 소유자 기반 접근 제어 | 요청자와 데이터 소유자의 관계로 접근 범위를 정하는 방식 | 4.1, 4.2, 1.2, prior-data | 같은 일반 사용자 역할이어도 자신의 제보와 다른 사람의 제보에 다르게 적용되는 정책 |
| 4.4 | 기본 거부 정책 | 명시적으로 허용한 규칙이 없으면 요청을 거부하는 기준 | 4.2, 4.3 | 등록된 역할이 없거나 대상 데이터의 소유 관계를 확인할 수 없는 요청 |
| 4.5 | API 접근 제어 | 서버가 요청마다 사용자와 대상 데이터의 권한을 확인하는 구조 | 4.4, 2.7, 1.3 | 화면의 버튼을 숨겨도 직접 보낼 수 있는 요청에 대한 서버의 권한 검사 |
| 4.6 | 행 수준 보안 정책 | 데이터베이스의 각 행에 접근 규칙을 적용하는 방식 | 4.5, 4.3, prior-data | 테이블 접근 권한과 사용자 ID·행 소유자 비교 정책이 함께 적용되는 사례 |
| 4.7 | API 키의 권한 범위 | 애플리케이션의 API 접근 자격과 사용자 인증의 구분 | 4.6, 2.4, 4.5 | 공개 가능한 키와 서버 전용 권한 키의 차이; RLS 우회 키를 쓰는 서버의 인가 책임 |
| 4.8 | FoodMap의 접근 정책 | 역할과 데이터 소유 관계를 조합한 요청별 허용 기준 | 4.2, 4.3, 4.4, 4.5, 4.6, 4.7 | 사용자별 자기 제보 조회·수정과 운영자의 전체 제보 조회를 묶은 정책 표 |

05. 관리자 시스템과 운영 업무
운영자의 권한을 서비스 관리 업무로 연결하는 구조
연결: 앞서 정한 권한을 이용자가 쓰는 기능과 운영자가 수행하는 관리 업무에 적용.
범위: 업무 화면과 기능의 분리를 설명. 개발·운영 인프라의 분리는 7장에 배치. 운영 데이터는 서버에서 일관되게 관리하는 설계 사례.

| 설계 번호 | 타이틀 | 서브타이틀 | 선수 개념 위치 | 연결 사례 |
| --- | --- | --- | --- | --- |
| 5.1 | 사용자 서비스와 관리자 시스템 | 이용자의 서비스 이용과 운영자의 관리 업무를 나누는 구조 | 4.8, prior-ui | 맛집 탐색·제보 화면과 전체 제보 관리 화면; 공통 서버를 사용해도 구분되는 기능과 권한 |
| 5.2 | 관리자 권한의 경계 | 서비스 운영에 필요한 권한을 업무 범위에 맞게 제한하는 기준 | 5.1, 4.2, 4.7 | 제보를 관리하는 앱 운영자와 DB·클라우드 프로젝트 관리자의 권한 구분 |
| 5.3 | 운영 업무의 상태 전이 | 제보의 처리 상태와 허용 가능한 변경을 정의하는 방식 | 5.2, 4.1 | 검토 대기 → 승인 또는 반려; 현재 상태에 따른 허용 행동 |
| 5.4 | 콘텐츠 공개 상태 | 검토 결과와 사용자에게 보이는 상태를 구분하는 기준 | 5.3, 4.3 | 승인되었지만 비공개인 맛집과 공개 중인 맛집의 구분 |
| 5.5 | 운영 작업의 트랜잭션 | 함께 성공해야 하는 데이터 변경을 하나의 작업으로 묶는 원리 | 5.3, 5.4, prior-transaction | 제보 승인 기록과 맛집 등록이 모두 반영되거나 모두 취소되는 서버·DB 작업 |
| 5.6 | 중복 요청의 처리 | 같은 운영 요청이 반복되어도 결과가 중복되지 않도록 하는 기준 | 5.5, 5.3 | 승인 요청 재전송으로 같은 맛집이 두 번 생성되지 않게 하는 멱등성 |
| 5.7 | 감사 로그 | 운영자의 작업 주체·대상·결과를 남기는 기록 | 5.6, 1.2 | 운영자·제보·승인 결과·시각·사유를 남기되 비밀번호와 토큰 원문은 제외하는 기록 |

07. 환경 분리와 서비스 운영

학습 순서 검토 기록

1. 1장에서는 인증 결과로 확인한 사용자까지만 다룬다. 역할·소유자별 허용 규칙은 4장, 세션 발급은 2장.
2. 비밀번호 검증 도식보다 해시·솔트가 먼저 온다. 비밀번호 해시에는 전용 함수를 사용한다는 범위를 유지하고 직접 암호 구현은 제외.
3. 쿠키 설명의 첫 사례는 값의 저장·첨부만 사용한다. 세션 ID는 서버 세션에서, SameSite는 사이트 개념 뒤에서 설명.
4. JWT 서명 원리 → 구조와 claim의 의미 → 검증 순서. 서명형 JWT를 사례로 명시하고 Base64url 표기는 암호화나 검증으로 설명하지 않음.
5. JWT 검증에서는 exp의 조건을 배운 뒤 적용한다. 만료 장은 세션을 포함한 수명 관리, 갱신·철회 장은 그 이후의 처리로 범위를 구분.
6. OAuth에서 위임·scope를 처음 정의한다. 4장의 서비스 역할·데이터 소유 정책을 이해해야 하는 예제를 사용하지 않음.
7. 외부 인증 제공자 → OAuth → OIDC → 코드 흐름 → state → PKCE → 내부 계정 연결 순서. 최초 흐름도에는 아직 설명하지 않은 보호값의 내부 동작을 넣지 않음.
8. PKCE의 변환값은 해당 장에서 일반 해시의 역할과 함께 설명. 비밀번호 저장용 해시와 같은 구현·설정이라고 가정하지 않음.
9. 3장 마지막은 외부 인증의 결과를 2장의 로그인 상태로 연결한다. 서비스 권한은 검증된 사용자 식별 이후 4장에서 판단.
10. 지난주 Auth·RLS 소개는 내부 동작을 배운 근거로 사용하지 않음. RLS는 역할·소유자 정책·API 검사를 배운 뒤 다시 정의.
11. 4장의 FoodMap 정책 표에는 아직 소개하지 않은 승인·공개 상태를 넣지 않음. 운영 업무와 상태를 배운 5장에서 조건을 확장.
12. 5장 트랜잭션은 지난주 전부 반영/취소 범위에서 사용. 트랜잭션만으로 중복 요청이나 동시 실행 문제가 모두 해결된다고 설명하지 않음.
13. 출처와 사이트를 구분한 뒤 동일 출처 정책·CORS·CSRF로 진행. CSRF 전에 쿠키 자동 첨부, 쿠키 보호 속성 전에 XSS·CSRF를 설명.
14. 7장의 환경별 설정은 3장의 복귀 주소와 4장의 API 키를 재사용. 관리자 화면을 운영 환경과 같은 뜻으로 쓰지 않음.
15. 백업 전에 복원 명령이나 복구 시나리오를 전제로 삼지 않음. 코드 롤백이 DB 변경·데이터 손실까지 되돌린다고 설명하지 않음.
