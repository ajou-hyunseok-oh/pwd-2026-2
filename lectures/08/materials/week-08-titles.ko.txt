02. 로그인 상태의 유지
이후 요청의 사용자 확인과 로그인 자격의 만료·갱신·종료
연결: 챕터 1에서 확인한 u123을 이후 맛집 생성 요청에서도 확인하고, 그 로그인 자격의 만료·갱신·종료를 관리하는 원리로 확장.
범위: 쿠키는 값 전달, 세션은 서버 상태 관리, 토큰은 자격정보, JWT는 토큰 형식으로 구분. 현재 요청의 사용자 확인까지 다루며 작업 허용 정책은 챕터 4, 쿠키 보호 속성과 공격 방어는 챕터 6에 유지.

| 설계 번호 | 타이틀 | 서브타이틀 | 선수 개념 위치 | 연결 사례 |
| --- | --- | --- | --- | --- |
| 2.1 | HTTP의 무상태성 | 이전 요청의 인증 결과가 새 요청에 자동으로 이어지지 않는 특성 | 1.7, prior-web | 로그인에서 확인한 u123과 사용자 확인 정보 없는 다음 맛집 생성 요청 사이의 연결 부재 |
| 2.2 | 쿠키 | 브라우저에 보관한 작은 데이터를 이후 요청에 자동 전달하는 수단 | 2.1 | 응답의 Set-Cookie → 브라우저 저장 → 이후 요청의 Cookie |
| 2.3 | 세션 | 세션 식별자로 서버에 보관한 로그인 상태를 찾는 구조 | 2.2, 1.7 | 예측하기 어려운 세션 식별자를 u123과 연결해 저장하고 이후 요청에서 해당 서버 기록 조회 |
| 2.4 | 토큰 | 사용자 확인이나 자원 접근을 위해 요청에 제시하는 증표 | 2.3, 1.3, prior-web | u123 인증 후 발급된 토큰을 맛집 생성 요청의 Authorization 헤더에 첨부. 세션 식별자도 토큰이며 액세스 토큰의 형식과 전달 수단은 별도 선택 |
| 2.5 | 토큰의 서명 | 정보를 직접 담은 토큰의 내용이 바뀌었는지 검증하는 원리 | 2.4 | u123의 발급 당시 내용과 u999로 바꾼 내용에 같은 signature-A를 첨부해 검증 결과 비교. 변조 탐지와 내용의 비밀 보장 구분 |
| 2.6 | JWT | 정보와 조건을 JSON 기반으로 표현해 전달하는 표준 토큰 형식 | 2.5, prior-web | API 액세스 토큰으로 사용하는 서명형 JWT의 헤더·페이로드·서명 역할과 sub=u123·iss·aud·exp의 의미 |
| 2.7 | JWT 검증 | 서명과 발급 조건을 확인해 토큰의 수용 여부를 판단하는 과정 | 2.6, 1.3 | JWT 수신 → sub=u123 읽기 → 서명·iss·aud·exp 검증 → 모두 통과하면 u123 수용, 하나라도 실패하면 인증 거부 |
| 2.8 | 인증 상태의 만료 | 한 번 확인한 인증 결과를 계속 신뢰할 수 있는 시간의 제한 | 2.3, 2.7 | u123의 세션 또는 JWT 발급 후 시간이 경과해 같은 자격으로 요청해도 인증을 거부하는 시간선 |
| 2.9 | 리프레시 토큰 | 비밀번호 재입력 없이 새 액세스 토큰을 발급받는 자격정보 | 2.8, 2.4 | 데이터 API의 액세스 토큰과 인증 시스템의 리프레시 토큰을 구분. 유효한 갱신 자격으로만 재발급하고 만료·철회된 자격은 거부 |
| 2.10 | 로그아웃과 인증 철회 | 인증 방식에 따라 사용 중인 로그인 자격을 종료하는 방법 | 2.3, 2.9, 2.7 | 현재 로그인 자격의 사용 종료와 자격 자체의 유효성을 구분. 브라우저 삭제·세션 무효화·갱신 자격 철회 및 이미 발급된 JWT의 남은 효력 비교 |

학습 순서 검토 기록

1. 1장에서는 인증 결과로 확인한 사용자까지만 다룬다. 역할·소유자별 허용 규칙은 4장, 세션 발급은 2장.
2. 비밀번호 검증 도식보다 해시·솔트가 먼저 온다. 비밀번호 해시에는 전용 함수를 사용한다는 범위를 유지하고 직접 암호 구현은 제외.
3. 쿠키 설명의 첫 사례는 값의 저장·첨부만 사용한다. 세션 ID는 서버 세션에서 설명. 쿠키 보호 속성은 다음 주 보안 강의로 분리.
4. JWT 서명 원리 → 구조와 claim의 의미 → 검증 순서. 서명형 JWT를 사례로 명시하고 Base64url 표기는 암호화나 검증으로 설명하지 않음.
5. JWT 검증에서는 exp의 조건을 배운 뒤 적용한다. 만료 장은 세션을 포함한 수명 관리, 갱신·철회 장은 그 이후의 처리로 범위를 구분.
6. OAuth에서 위임·scope를 처음 정의한다. 4장의 서비스 역할·데이터 소유 정책을 이해해야 하는 예제를 사용하지 않음.
7. 챕터 3은 외부 제공자·Auth·SDK → OAuth/OIDC → 실제 로그인·복귀 → 인증 계정·프로필 → API 요청 순서.
8. state·PKCE 내부 계산·클레임 검증은 초심자 본문에서 제외. SDK와 인증 서비스를 사용하는 실제 실습 경로를 구분.
9. 3장 마지막은 외부 인증의 결과를 2장의 로그인 상태로 연결한다. 서비스 권한은 검증된 사용자 식별 이후 4장에서 판단.
10. 챕터 4는 인증·인가 → 역할 → 본인 프로필 → 미들웨어 → 키와 DB 접근 순서. RLS 정책 SQL은 보충 자료.
11. 현재 라우트의 권한 표를 사용. 제보 조회·관리는 관리자 기능이며 본인 정보 사례는 프로필 수정으로 설명. 승인 업무 조건은 5장에 유지.
12. 5장 트랜잭션은 지난주 전부 반영/취소 범위에서 사용. 트랜잭션만으로 중복 요청이나 동시 실행 문제가 모두 해결된다고 설명하지 않음.
13. 6장의 환경별 설정은 3장의 복귀 주소와 4장의 API 키를 재사용. 관리자 화면을 운영 환경과 같은 뜻으로 쓰지 않음.
14. 6장은 실제 로컬 설정 → Vercel·Render 빌드·배포 → 주소 연결 → 기능 확인. 별도 검증 환경·복구 심화는 보충 자료.
