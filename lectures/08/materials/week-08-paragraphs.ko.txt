01. 사용자 인증의 원리
요청한 사용자의 신원을 확인하는 원리

1.1 서비스의 사용자 식별
서브타이틀: 저장된 데이터와 요청한 사용자를 연결할 필요

7주차 FoodMap의 POST /api/restaurants는 요청 사용자를 확인하지 않고 입력 검증을 통과한 맛집 정보를 DB에 저장한다. 실제 맛집뿐 아니라 입력 형식만 맞춘 허위 맛집도 같은 경로로 저장될 수 있으며, 입력 형식 검사만으로 등록을 허용할 요청인지 판단할 수는 없다. 사용자 식별은 요청과 서비스 사용자를 연결해 누가 데이터 생성을 요청했는지 구분하는 것이다. 사용자별로 작업을 제한하려면 먼저 요청자를 구분할 수 있어야 하며, 식별만으로 허위 정보를 판별하거나 작업 허용 여부가 결정되는 것은 아니다. 이 장은 식별의 필요성까지 설명하고, 요청자의 증거 검증과 구체적인 권한 판단은 후속 슬라이드에서 다룬다.

1.2 사용자 계정
서브타이틀: 사용자 정보를 관리하는 계정과 요청을 연결하는 고유 ID

앞 장에서 맛집 생성 요청의 사용자를 구분할 필요를 확인했다. 사용자 계정은 서비스가 사용자 ID와 표시 이름, 이메일 등의 정보를 함께 관리하는 사용자 기록이다. 사용자 ID는 계정마다 고유하며, 표시 이름이 같거나 바뀌더라도 서로 다른 계정을 구분하고 같은 계정과의 연결을 유지하는 기준이 된다. FoodMap의 확장 설계 사례에서는 표시 이름이 모두 민수인 두 계정을 u123과 u999로 구분하고, POST /api/restaurants 요청 A와 B를 각 계정의 ID에 연결한다. 이 표는 계정과 요청의 관계를 보여주는 설계 예시이며 7주차 구현 결과가 아니다. ID는 계정을 가리킬 뿐 요청자가 실제로 해당 계정의 사용자인지 증명하지는 않는다.

1.3 클라이언트 입력의 신뢰 경계
서브타이틀: 사용자가 보낸 주장과 서버가 확인한 사실의 구분

앞 장에서는 고유한 사용자 ID로 맛집 생성 요청과 계정을 연결하는 구조를 살펴보았다. 그러나 사용자 제어 영역인 클라이언트와 서버의 처리 영역 사이에는 신뢰 경계가 있다. 사용자는 클라이언트에서 요청에 넣는 값을 변경할 수 있으므로, 서버가 받은 사용자 ID는 검증 전까지 요청자의 주장이다. 맛집 생성 요청 본문의 ID로 계정을 연결한다고 가정하면, 전송 전 userId를 u123에서 다른 계정의 u999로 바꾸어 보낼 수 있다. 서버가 이 값을 그대로 믿으면 요청을 다른 계정에 잘못 연결할 수 있으므로, 존재하는 계정의 ID라는 사실과 요청자가 그 계정의 사용자라는 사실을 구분해야 한다. 서버는 요청자의 별도 증거를 확인한 뒤 계정과 요청을 연결해야 한다. 이 도식은 04번의 설계를 검토하기 위한 가정 사례이며 7주차의 구현 결과가 아니다.

1.4 사용자 인증
서브타이틀: 계정에 대한 증거를 확인해 요청자의 신원을 판단하는 과정

05번에서 클라이언트가 보낸 사용자 ID만으로 요청자를 인정할 수 없음을 확인했다. 사용자 인증은 서버가 지정된 계정에 대한 별도 증거를 검증해 요청자의 신원을 판단하는 과정이다. 이메일은 어느 계정을 확인할지 지정하며, 비밀번호는 해당 계정의 사용자임을 검증할 증거를 제공한다. 사례는 04번의 minsu@example.com에 해당하는 u123 계정을 이어받고 서버가 입력 비밀번호를 이 계정에 대해 검증한다. 검증 성공 시 현재 인증 요청의 사용자를 u123으로 인정하고, 실패 시 계정이 존재하더라도 u123 사용자로 인정하지 않는다. 해시·솔트의 구현은 후속 슬라이드에 유지하며, 현재 인증 요청에서의 확인을 이후 요청의 로그인 유지나 맛집 등록 권한 부여와 동일하게 설명하지 않는다.

1.5 비밀번호 해시
서브타이틀: 비밀번호 원문 대신 검증용 값을 생성해 저장하는 원리

서버는 비밀번호 원문 대신 비밀번호에서 계산한 해시를 계정에 보관하며, 해시는 저장값에서 원문을 복원하기 어렵도록 설계된다. 설정 시 u123 계정의 비밀번호를 전용 해시 함수로 처리해 검증값을 저장하는 도식으로 이를 확인한다. hash-A는 설명용 기호다. 로그인 시에는 입력 비밀번호와 기존 저장 정보를 검증 함수에 전달해 일치 여부를 확인한다. 원문 저장은 DB 유출 시 비밀번호 자체를 드러내지만, 해시 저장은 직접 노출을 줄이는 대신 추측 공격의 가능성은 남긴다. 간결화를 위해 별도 로그인 흐름도와 반복 추측의 계산 비용 설명은 제외하고, 저장 도식과 유출 비교 표를 유지한다. 솔트와 전체 로그인 절차는 후속 슬라이드에서 다룬다.

1.6 비밀번호 솔트
서브타이틀: 같은 비밀번호도 서로 다른 해시가 되도록 더하는 계정별 값

07번에서 원문 대신 해시를 보관하되 추측 공격의 위험은 남음을 확인했다. 솔트 없이 같은 조건에서 같은 비밀번호를 해시하면 결과가 같으므로, 공격자가 후보 비밀번호의 계산 결과를 여러 계정에 재사용할 수 있다. 솔트는 해시 계산에 함께 사용하는 무작위 값으로, 서로 다른 솔트를 사용하면 같은 비밀번호도 다른 해시가 되어 계정 간 추측 계산의 재사용을 어렵게 한다. 표에서는 u123과 u999가 같은 비밀번호를 입력하지만 salt-A와 salt-B에 따라 hash-A와 hash-B를 저장하는 관계를 보여준다. 솔트와 해시는 별도 열로 구분하며 각 값은 설명용 기호다. 입력 비밀번호 원문은 저장하지 않고 솔트와 해시를 함께 보관하며, 로그인 검증에는 해당 계정에 저장된 솔트를 다시 사용한다. 솔트는 개별 비밀번호의 추측 가능성 자체를 없애는 수단은 아니다.

1.7 비밀번호 로그인
서브타이틀: 이메일로 조회한 계정의 해시·솔트로 입력 비밀번호를 검증하는 흐름

06번에서 증거 검증의 의미를, 07·08번에서 해시와 솔트의 저장 역할을 확인했다. 비밀번호 로그인에서 서버는 입력 이메일에 해당하는 계정을 조회하고 그 계정에 저장된 해시와 솔트를 확보한다. 사례에서는 minsu@example.com으로 u123 계정을 찾아 저장된 salt-A와 hash-A를 사용한다. 서버는 입력 비밀번호와 이 계정의 저장 정보를 검증 함수에 전달한다. 검증에 성공하면 클라이언트가 주장한 ID가 아니라 서버가 조회하고 검증한 계정의 ID u123을 현재 요청의 인증 결과로 사용한다. 계정이 없거나 검증에 실패하면 인증을 거부한다. 해시 문자열과 원문을 직접 비교하거나 복호화하는 과정으로 설명하지 않으며, 여기까지의 결과는 현재 로그인 요청에서 확인한 사용자다. 이후 요청의 로그인 유지와 작업 권한은 별도다.

챕터 흐름 평가
순서 유지. 저장된 데이터 → 지속적인 사용자 식별 → 입력 주장의 한계 → 증거 검증 → 안전한 검증 정보 저장 → 로그인 흐름으로 연결된다.
1.7은 현재 요청의 사용자 확인에서 끝낸다. 로그인 유지 수단을 끌어오지 않아 2.1의 필요성이 남는다.
계정 인증을 실제 인물의 실명 확인과 동일하게 설명하지 않는다. 해시·솔트의 수학이나 구현 세부는 이번 문단 범위 밖이다.

02. 로그인 상태의 유지
이후 요청의 사용자 확인과 로그인 자격의 만료·갱신·종료

2.1 HTTP의 무상태성
서브타이틀: 이전 요청의 인증 결과가 새 요청에 자동으로 이어지지 않는 특성

챕터 1의 로그인 요청에서 u123 사용자를 확인했더라도 그 결과가 새 HTTP 요청에 자동으로 붙지는 않는다. HTTP는 각각의 요청만으로 이전 인증 결과를 보장하지 않으므로, 애플리케이션이 요청 사이를 연결할 정보를 별도로 관리해야 한다. 로그인 유지 수단을 아직 적용하지 않은 FoodMap 설계 사례에서, 다음 맛집 생성 요청에 사용자를 확인할 정보가 없으면 서버는 이 요청도 u123의 요청인지 판단할 근거가 부족하다. 이 사례는 한 번의 사용자 확인과 이후 요청의 사용자 연결이 다른 문제임을 보여주며, 맛집 생성 권한의 허용 정책이나 실제 7주차 서버의 인증 구현을 설명하는 것은 아니다.

2.2 쿠키
서브타이틀: 브라우저에 보관한 작은 데이터를 이후 요청에 자동 전달하는 수단

쿠키는 브라우저에 이름과 값의 쌍으로 보관하는 작은 데이터다. 서버는 응답의 Set-Cookie 헤더로 저장을 요청하고, 브라우저는 전송 조건에 맞는 이후 요청의 Cookie 헤더에 저장한 값을 자동으로 첨부한다. 쿠키의 역할은 서버가 요청 사이의 상태를 연결할 수 있도록 값을 보관하고 전달하는 것이다. 사용자 확인에 쓰는 값의 의미와 유효성은 서버가 별도로 판단한다. 용도로는 로그인 상태 확인용 식별값을 전달하는 로그인 상태 관리, 언어·테마 선택을 유지하는 개인화, 식별값으로 방문·활동 기록을 연결하는 이용 행동 분석이 있다. 세션 ID라는 명칭은 다음 장에서 구체화한다. 사례의 name=value가 응답, 브라우저 저장, 이후 요청에서 동일하게 유지되는 흐름으로 정의와 역할을 확인한다.

2.3 세션
서브타이틀: 세션 식별자로 서버에 보관한 로그인 상태를 찾는 구조

세션은 서버에서 관리하는 사용자별 상태이며, 예측하기 어려운 세션 ID와 상태 정보를 연결해 보관한다. 역할은 여러 요청을 서버의 같은 상태에 연결하는 것으로, 쿠키 등으로 전달받은 세션 ID로 유효한 서버 기록을 조회한다. 용도로는 인증된 사용자 정보를 유지하는 로그인 상태 관리, 상품 선택 정보를 유지하는 장바구니 관리, 단계별 입력과 진행 상태를 유지하는 여러 단계 작업이 있다. 사례에서는 로그인으로 확인한 u123을 세션 ID 예시 sid-A의 상태 정보에 저장하고, 브라우저에는 sid-A를 쿠키로 전달한다. 이후 FoodMap 요청에 식별자가 돌아오면 서버는 유효한 세션 기록을 조회해 그 안의 userId=u123을 확인한다. 브라우저가 주장한 사용자 ID를 그대로 믿는 것이 아니라 서버의 연결 기록으로 사용자를 확인한다. 서버 저장 예시 JSON에는 sid-A를 키로, userId=u123을 담은 상태 정보를 값으로 표시해 흐름도와 대응시킨다. 이는 저장 관계를 보여주는 개념 모델이며 실제 저장소 구현이나 실제 ID 생성값이 아니다.

2.4 토큰
서브타이틀: 사용자 확인이나 자원 접근을 위해 요청에 제시하는 증표

토큰은 사용자 확인이나 접근 자격을 제시하는 증표로, 서버가 발급하고 클라이언트가 이후 요청에 제시하는 값이다. 역할은 서버의 유효성 검증을 통해 요청의 사용자 또는 접근 자격을 확인하는 것이다. 세션 식별자처럼 서버의 기록을 찾아야 의미를 알 수 있는 토큰도 있고, 토큰 자체에 확인할 정보를 담는 형식도 있다. 액세스 토큰은 토큰의 한 종류로 API 등 보호된 자원에 접근할 때 제시하는 자격이다. 토큰의 형식과 별개로 쿠키나 Authorization 헤더 등으로 전달할 수 있다. 토큰은 세션 ID까지 포함하는 상위 개념이다. 종류별 용도로 세션 ID는 서버에 저장한 세션 상태 조회, 액세스 토큰은 API 접근 자격 제시에 사용한다. 세션 자체는 서버가 관리하는 상태이고 그 상태를 찾는 ID가 토큰이므로 두 개념을 경쟁하는 별도 방식으로 설명하지 않는다. 본문은 쿠키·요청 헤더라는 전달 수단을 설명한다. 사례에서는 Authorization을 토큰 등 인증 자격을 전달하는 HTTP 요청 헤더로 소개하고, u123 인증 후 발급된 액세스 토큰을 맛집 생성 요청에 첨부해 서버가 검증하고 사용자 u123을 확인하는 과정을 보여준다. 정의 아래에는 반복되는 자격정보 설명을 덜고 상위 개념 관계에 집중한다. 도식은 현재 요청의 사용자 u123 확인에서 끝내며 맛집 생성의 처리 결과를 표시하지 않는다. 작업 권한은 별도 판단이다. 토큰의 변조 검증과 구체적인 JWT 형식은 후속 장에서 설명한다.

2.5 토큰의 서명
서브타이틀: 정보를 직접 담은 토큰의 내용이 바뀌었는지 검증하는 원리

15번은 토큰에 담긴 사용자 정보를 클라이언트가 바꾸어 보낼 가능성에서 출발한다. 서버는 전달받은 내용이 발급 당시와 같은지 검증할 근거가 필요하다. 설명 대상은 사용자 정보를 직접 담은 토큰이며, 서버 기록을 찾는 세션 ID와의 저장 방식 비교를 도입에 앞세우지 않는다. 서명은 발급자가 관리하는 암호학적 키를 이용해 검증 가능한 값을 붙이는 방식이며, 수신자는 신뢰하는 발급자의 검증 키와 방법으로 무결성을 확인한다. 표에서는 발급 당시 사용자 정보 u123과 서명 signature-A를 검증한 경우, 사용자 정보만 u999로 바꾸고 같은 signature-A를 첨부한 경우를 비교한다. 후자는 내용과 기존 서명이 맞지 않아 검증에 실패하며, u999라는 계정 자체가 거부 대상이라는 뜻은 아니다. 표의 성공·실패는 서명 검증 결과이며 요청 전체의 허용 판단을 뜻하지 않는다. 서명은 변조 확인에 사용되며, 서명 검증만으로 내용의 비밀성·만료·작업 권한까지 보장되지는 않는다. 구체적인 토큰 형식과 유효 조건의 검사는 이후 JWT 장에 남긴다.

2.6 JWT
서브타이틀: 정보와 조건을 JSON 기반으로 표현해 전달하는 표준 토큰 형식

JWT는 JSON Web Token의 약자로, 사용자 등에 관한 정보와 조건을 JSON 기반으로 표현해 전달하는 표준 토큰 형식이다. 이 장은 그중 서명을 사용하는 JWT를 설명하며 JWT 전체가 항상 서명된 세 부분이라고 정의하지 않는다. 이 강의의 서명형 JWT에서 헤더는 서명 방식 등을 나타내고 페이로드는 사용자와 유효 조건을 담으며, 서명은 헤더와 페이로드의 변조를 확인하는 데 사용한다. 각 부분을 Base64url로 인코딩해 마침표로 연결한 전달 형태를 원본 그림으로 보여주고, 코드 라벨은 헤더와 페이로드를 풀어 읽은 JSON임을 명시한다. 그림의 aaaaa 등은 실제 유효한 JWT가 아닌 자리표시다. 사례의 JWT는 API 액세스 토큰으로 발급된 것으로 한정한다. 페이로드의 sub=u123은 사용자 식별자, iss=https://auth.example.com은 발급자, aud=foodmap-api는 수신 대상, exp는 만료 시각을 나타낸다. 내용은 읽을 수 있으므로 비밀번호 같은 비밀을 넣지 않으며, 각 필드의 의미를 아는 것과 토큰을 신뢰하는 것은 별도다.

2.7 JWT 검증
서브타이틀: 서명과 발급 조건을 확인해 토큰의 수용 여부를 판단하는 과정

JWT의 내용을 읽는 디코딩과 그 내용을 신뢰할 수 있는지 확인하는 검증은 별도의 단계다. sub=u123을 읽었다는 사실만으로 현재 요청의 사용자를 u123으로 인정할 수 없다. 서명이 유효해도 다른 발급자의 토큰, 다른 서비스용 토큰, 만료된 토큰은 현재 요청의 자격으로 받아들이면 안 된다. 서버는 미리 허용한 서명 방식과 신뢰하는 키로 서명을 검증하고, 발급자와 수신 대상이 예상과 일치하며 유효 시간이 지나지 않았는지 확인한다. 사례에서는 맛집 생성 요청의 JWT를 받은 뒤 sub=u123을 읽되 아직 신뢰하지 않고, 앞 장에서 제시한 iss=https://auth.example.com과 aud=foodmap-api 및 서명·만료 조건을 확인한다. 서명은 내용의 변조 여부, iss는 신뢰하는 발급자 여부, aud는 이 API용인지, exp는 현재도 유효한지를 판단하는 데 사용한다. 필수 검사를 모두 통과하면 현재 요청의 사용자를 u123으로 인정하고 하나라도 실패하면 인증을 거부한다. 흐름도 캡션은 사용자 확인과 맛집 생성 권한의 별도 판단을 구분한다. 2.4의 로그인 입력·토큰 발급을 반복하지 않고 수신·읽기·검증·수용 여부에 집중하며, 검증 통과가 맛집 생성 권한까지 자동으로 허용한다는 뜻은 아니다.

2.8 인증 상태의 만료
서브타이틀: 한 번 확인한 인증 결과를 계속 신뢰할 수 있는 시간의 제한

인증 상태의 만료는 세션이나 토큰을 인증 자격으로 받아들이는 시간을 제한하는 장치다. 탈취된 자격이 무기한 재사용되지 않도록 재사용 가능 시간을 줄이는 데 목적이 있다. 서버 세션은 마지막 활동이나 생성 시점을 기준으로 종료할 수 있고, JWT는 exp에 기록된 시각을 기준으로 유효성을 판단한다. 시간선은 발급 후 최대 유효 기간을 30분으로 가정한다. 09:00 u123의 세션 또는 JWT 발급, 09:10 다른 검사도 통과해 인증 자격 수용, 09:30 최대 수명 또는 exp 도달, 09:31 같은 값으로 다시 요청해도 만료로 거부하는 상황을 비교한다. 만료는 브라우저 보관 여부와 별개로 서버가 판단한다. 계정 삭제나 항상 비밀번호 재입력이 필요하다는 뜻은 아니며, 새 자격을 받는 갱신과 의도적인 종료 절차는 뒤 장에 유지한다. 시간선의 세션은 비활동 시간 기준이 아닌 최대 수명 기준의 예시이며 표에서는 두 기준을 구분한다.

2.9 리프레시 토큰
서브타이틀: 비밀번호 재입력 없이 새 액세스 토큰을 발급받는 자격정보

액세스 토큰의 수명을 짧게 유지하면서 매번 비밀번호를 입력하지 않게 하려면 새 토큰을 발급받는 절차가 필요하다. 리프레시 토큰은 이 갱신에 사용하는 별도의 자격정보로, 일반 데이터 API 대신 인증 시스템에 제출한다. 인증 시스템은 갱신 자격이 유효할 때만 새 액세스 토큰을 발급하고, 자격이 만료되었거나 철회되었으면 갱신을 거부한다. 이 경우 로그인 상태를 다시 만들려면 재로그인이 필요하다. 도식은 로그인 시 리프레시 토큰도 발급받아 보관한 사례다. 만료된 액세스 토큰 A의 시간을 연장하는 것이 아니라 갱신 자격 검증 후 새 액세스 토큰 B를 발급하고 B로 재요청한다. 데이터 API와 인증 시스템은 처리 역할을 구분한 것이며 반드시 서로 다른 서버라는 뜻은 아니다. 토큰을 계속 발급받는 데 악용될 수 있는 갱신 자격은 별도로 보호하고, 철회의 처리 위치와 효력은 다음 장에서 설명한다.

2.10 로그아웃과 인증 철회
서브타이틀: 인증 방식에 따라 사용 중인 로그인 자격을 종료하는 방법

로그아웃은 현재 로그인 자격의 사용을 종료하는 과정이며, 브라우저 보관값 삭제와 서버의 세션 또는 갱신 자격 종료를 함께 처리한다. 브라우저에서만 삭제하면 다른 곳의 유효한 복사본은 재사용될 수 있으므로, 해당 브라우저의 사용 종료와 자격 자체의 유효성을 구분해야 한다. 철회는 서버가 기존 자격을 무효화하거나 새 자격 발급을 차단하는 처리로, 자연적인 만료 전에도 수행할 수 있다. 표의 첫 열은 위치와 자격 종류를 혼합한 종료 위치 대신 처리 대상으로 명명한다. 13번의 sid-A는 서버 기록을 무효화한 뒤 해당 ID로 요청해도 인증을 거부한다. 19번의 리프레시 토큰을 철회하면 새 액세스 토큰 발급을 중단한다. 19번에서 발급된 액세스 토큰 B가 JWT인 경우, 서명과 발급 조건만 검사하면 갱신 자격을 철회해도 B는 만료까지 유효할 수 있다. 즉시 차단이 필요하면 서버가 철회 여부를 추가로 확인해야 한다. 일반적인 모든 액세스 토큰이나 모든 JWT의 동작으로 확대하지 않는다. 이 장은 2.8의 시간에 따른 만료와 구분되는 의도적인 종료를 설명하고, 각 방식의 남은 효력까지 비교해 챕터를 마무리한다.

챕터 흐름 평가
목적은 챕터 1에서 확인한 u123을 이후 요청에서도 확인하고 로그인 자격의 만료·갱신·종료를 이해하는 것. 순서를 유지하고 맛집 생성 요청과 u123을 이어받아 값 전달 → 서버 기록 조회 → 토큰과 서명 → JWT 구조·검증 → 자격의 수명 관리로 연결한다.
2.4는 토큰의 발급·전달, 2.6은 JWT 요소의 역할, 2.7은 수신·읽기·검증·판단, 2.8은 시간에 따른 만료, 2.9는 유효한 자격으로만 가능한 갱신, 2.10은 의도적인 사용 종료와 남은 효력으로 구분. 작업 허용 정책은 챕터 4, 공격과 보호 속성은 챕터 6에 유지한다.
쿠키·세션·JWT를 서로 배타적인 세 방식으로 비교하지 않는다. 인증 성공이 맛집 생성 허용을 보장하거나, 리프레시 토큰이 무기한 갱신을 보장하거나, 브라우저 값 삭제가 모든 복사본을 무효화한다고 설명하지 않는다. FoodMap의 사례는 개념 설계이며 현재 실습의 구현 결과로 단정하지 않는다.

03. 외부 인증과 소셜 로그인
외부 로그인 용어와 Supabase Auth·SDK를 이용한 FoodMap 인증 흐름

3.1 외부 인증 제공자
서브타이틀: 외부 계정 인증과 FoodMap의 로그인 연결 역할

챕터 1~2는 수정하지 않고 이 장의 앞부분에서 인증 서비스·SDK의 뜻을 짧게 확인한 뒤 외부 제공자 연결의 역할로 설명을 제한한다. 외부 인증 제공자는 외부 계정의 사용자를 인증하는 서비스다. FoodMap에서 Google·네이버를 선택하면 해당 제공자가 자신의 계정으로 사용자를 인증한다. FoodMap은 외부 비밀번호를 받아 저장하지 않는다. Supabase Auth는 외부 인증 결과를 처리해 서비스용 로그인 자격을 발급하고 브라우저 SDK는 인증 요청·토큰 보관·갱신을 연결하는 라이브러리다. 기존 로그인 선택 화면을 유지하고 세 구성 요소의 책임을 비교한다. 실제 구현 근거는 클라이언트 authApi.js·config/supabase.js이며 실제 로그인 시연 결과로 표시하지 않는다.

3.2 OAuth와 OIDC의 역할
서브타이틀: 접근 권한 위임과 사용자 인증 결과 전달의 구분

외부 제공자가 발급한 액세스 토큰·ID 토큰과 Supabase가 FoodMap API용으로 발급한 액세스 토큰을 표의 별도 행으로 구분한다. OAuth 2.0은 다른 서비스의 자원 접근을 허용하는 인가 프레임워크이고 OIDC는 OpenID Connect의 약칭으로 OAuth 2.0에 사용자 인증 결과 전달·검증 규칙을 더한 표준이다. 외부 액세스 토큰은 외부 API 접근, ID 토큰은 수신 서비스의 사용자 확인에 쓰인다. 실습에서 외부 제공자의 토큰 처리는 Supabase Auth가 맡으며 FoodMap Express API에는 Supabase Auth가 발급한 서비스용 액세스 토큰을 보낸다. 모든 외부 로그인이 동일한 OIDC 절차라고 일반화하지 않는다. scope·클레임·수동 서명 검증은 제외하고 두 용어의 목적과 실제 담당만 설명한다.

3.3 소셜 로그인의 전체 흐름
서브타이틀: 로그인 선택부터 복귀와 SDK의 로그인 결과 처리까지

콜백은 외부 인증 뒤 돌아오는 처리 주소이며 실습은 /auth/callback 페이지에서 SDK로 결과를 처리한다. 인가 코드는 토큰 교환용 일회용 값이고 SDK 세션은 토큰·사용자 정보를 묶은 객체로 서버 세션 ID와 다르다. 로그인 선택은 signInWithOAuth로 Supabase Auth에 전달되고 외부 제공자의 인증을 거친 브라우저가 Auth로 돌아온다. Auth는 FoodMap 콜백으로 코드를 전달하고 브라우저 SDK의 exchangeCodeForSession이 Auth와 교환해 서비스용 토큰·사용자 정보를 받는다. 외부 제공자와 Auth 사이의 교환과 Auth와 브라우저 사이의 교환을 FoodMap Express 서버의 직접 외부 코드 교환으로 설명하지 않는다. state·PKCE 내부 계산은 본문에서 제외하되 실제 SDK 설정이 PKCE임을 보충 기록에 남긴다. 근거: authApi.js, config/supabase.js, utils/oauthCallback.js.

3.4 인증 계정과 FoodMap 사용자 정보
서브타이틀: 같은 사용자 ID로 인증 계정과 서비스 데이터를 연결

auth.users는 Supabase가 관리하는 인증 계정이고 public.profiles는 FoodMap의 이름·역할·활성 상태 테이블이다. UUID는 사용자를 구분하는 고유 ID이며 profiles.id는 auth.users.id와 같은 UUID를 사용한다. 제보의 submitter_id는 프로필 ID를 참조하므로 이름·이메일 대신 검증된 사용자 ID로 사용자와 서비스 데이터를 연결한다. 기존 u123·provider-A/42의 수동 외부 계정 매핑 예시는 실습 스키마의 실제 연결로 교체하며 임의 숫자 ID를 넣지 않는다. 근거: 서버 supabase/schema.sql의 외래 키와 계정 생성 시 프로필 생성 트리거.

3.5 로그인 이후의 API 요청
서브타이틀: 브라우저의 토큰 첨부와 Express 서버의 사용자 확인

Express에 첨부하는 값은 Supabase 액세스 토큰이며 외부 제공자의 액세스 토큰·ID 토큰과 구분한다. Bearer는 API 요청에 토큰을 제시하는 방식이다. 브라우저의 api.jsx는 SDK의 getSession으로 액세스 토큰을 읽어 Authorization 헤더에 첨부한다. GET /api/auth/me에서 Express는 Supabase Auth의 getUser로 토큰을 검증하고 반환된 사용자 ID로 profiles를 조회한다. 프로필이 없거나 비활성 계정이면 거부하고 성공하면 현재 사용자 정보를 반환한다. SDK 저장값 읽기와 서버의 사용자 검증은 구분하며 외부 제공자의 토큰을 FoodMap API에 보내는 것으로 설명하지 않는다. 작업별 관리자 권한은 다음 챕터에 남긴다. 근거: 클라이언트 api.jsx·authApi.js와 서버 middleware/auth.middleware.ts·routes/auth.routes.ts·controllers/users.controller.ts.

챕터 흐름 평가
본문 8장을 5장으로 통합. 용어·책임 분리 → OAuth/OIDC → 실제 SDK 로그인·복귀 → 인증 계정·프로필 → API 사용자 확인 순서.
SDK 호출 이름은 실제 구현과 연결하는 라벨로 사용하고 전체 코드를 외우게 하지 않음. 내부 계정 병합·state·PKCE 계산·클레임 검증은 별도 보충 자료. 사용자별 작업 허용은 챕터 4.
실제 코드 경로를 검토한 설명이며 외부 제공자 로그인 실환경 테스트를 수행한 것은 아님. Auth·브라우저 SDK·Express 서버를 구분하고 외부 토큰과 서비스용 토큰을 혼동하지 않음.

- OpenID Connect Core: https://openid.net/specs/openid-connect-core-1_0.html
- OAuth Security Best Current Practice: https://www.rfc-editor.org/rfc/rfc9700.html
- PKCE: https://www.rfc-editor.org/rfc/rfc7636.html

04. 권한과 데이터 접근 제어
실습의 역할·본인 정보·미들웨어와 서버의 권한 검사

4.1 인증과 인가
서브타이틀: 사용자 확인과 작업 허용 판단의 구분

인증은 요청한 사용자를 확인하는 과정이고 인가는 그 사용자에게 특정 작업을 허용할지 판단하는 과정이다. 챕터 3의 토큰 검증·프로필 조회 결과를 이어받되 로그인 성공 자체가 맛집 생성 허용을 뜻하지 않음을 설명한다. 본문 정의 뒤 사용자 확인 → 관리자 역할 검사 → 허용된 맛집 생성의 흐름을 배치한다. 실제 restaurants.routes.ts의 isAuthenticated·requireAdmin·controller.create 순서가 근거다.

4.2 사용자 역할과 허용 기능
서브타이틀: 일반 사용자와 관리자의 기능 사용 범위

역할은 사용자의 기능 사용 범위를 구분하는 기준이며 실습의 user와 admin을 일반 사용자와 관리자로 정의한다. 역할은 클라이언트가 적어 보낸 표시가 아니라 서버가 조회한 profiles.user_type에서 확인한다. 공개 맛집 조회, 본인 프로필 수정, 로그인 사용자의 제보 작성, 관리자 맛집·제보 관리와 역할 변경을 실제 라우트에 맞춰 비교한다. 일반 사용자의 자기 제보 조회·수정은 현재 실습 기능이 아니므로 허용 기능에 넣지 않는다. 관리자 작업은 추가 업무 조건에도 제한될 수 있으며 역할만으로 모든 DB 변경이 무조건 성공한다고 설명하지 않는다.

4.3 본인 정보의 처리
서브타이틀: 서버가 확인한 사용자 ID로 수정 대상 결정

isAuthenticated를 처음 사용하는 본문에서 토큰·프로필을 확인해 req.auth를 채우는 서버 함수로 짧게 설명한다. 본인 정보는 인증된 사용자 ID에 연결된 개인 데이터다. req.auth는 인증 검사 뒤 요청에 연결한 프로필 정보이며 req.auth.id는 서버가 확인한 ID다. 브라우저는 이름·이미지 입력을 보내지만 서버의 users.controller.ts는 updateProfile(req.auth.id, req.body)를 호출하고 users.service.ts가 같은 ID의 profiles 행만 수정한다. 본문의 userId는 신뢰하지 않을 입력을 설명하는 이름이며 실제 요청에 그 필드를 요구하는 것은 아니다. 가상의 제보 소유자 정책 대신 현재 구현의 본인 프로필 수정을 사례로 사용한다.

4.4 서버의 권한 검사 흐름
서브타이틀: 요청한 기능을 실행하기 전 인증과 관리자 권한 검사

미들웨어는 요청한 기능 실행 전에 공통 조건을 확인하는 함수다. POST /api/restaurants는 isAuthenticated로 Bearer 토큰·프로필·활성 상태를 확인하고 requireAdmin으로 req.auth.userType을 검사한 뒤 controller.create를 실행한다. 필요한 검사에 실패하면 다음 단계로 진행하지 않는다. 토큰 누락·무효는 401, 관리자 역할 부족은 403으로 구분한다. 실제 구현은 프로필 누락·비활성에 403, 인증 서비스 장애에 503도 사용할 수 있으므로 모든 실패를 두 상태로 일반화하지 않는다. React의 AdminRoute는 화면 접근을 안내하지만 서버 권한 검사를 대신하지 않는다.

4.5 API 키와 데이터베이스 접근
서브타이틀: 사용자 토큰과 서버 전용 키의 역할 구분

API 키는 프로그램의 Supabase 프로젝트 접근 자격이며 사용자의 액세스 토큰과 구분한다. Publishable key는 브라우저 SDK, Secret key는 Express 서버 전용이다. Supabase가 발급한 사용자 액세스 토큰은 Express 요청에 첨부하여 요청자를 확인한다. 본문은 사용자 토큰·브라우저 키·서버 키의 역할에 집중하고 RLS의 정의·정책·Secret key의 우회 경로는 챕터4 보충 자료로 이동한다. 브라우저 키가 사용자의 관리자 권한을 증명하는 것은 아니며 Express가 사용자와 작업 권한을 검사한다. 현재 DB 권한 구조는 바꾸지 않는다.

챕터 흐름 평가
본문 8장을 5장으로 통합. 용어 정의 → 실제 허용 기능 → 본인 ID → 미들웨어 흐름 → 키와 DB 경로 순서.
클라이언트·서버·DB의 책임을 구분하고 실제 구현과 확장 설계를 혼합하지 않음. RLS SQL·DB 역할 체계·범용 소유자 정책은 보충 자료. 승인 업무 조건과 트랜잭션은 챕터 5.
코드·스키마를 읽어 대조한 내용이며 실환경 로그인·DB 변경 테스트 결과가 아님. Secret key를 가진 서버에서 별도 인가를 수행하는 현재 구조를 설명.

내용 확인 출처
- OWASP Authorization: https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html
- Supabase Row Level Security: https://supabase.com/docs/guides/database/postgres/row-level-security
- Supabase API keys: https://supabase.com/docs/guides/getting-started/api-keys

05. 관리자 시스템과 운영 업무
제보 상태와 실제 승인·트랜잭션·중복 요청 처리 흐름

5.1 사용자 제보와 관리자 업무
서브타이틀: 등록 요청과 서비스 데이터 반영의 구분

제보는 사용자가 등록을 요청한 맛집 정보이며 서비스의 공개 맛집과 구분한다. 로그인 사용자의 POST /api/submissions 요청은 서버가 확인한 사용자 ID를 submitter_id로 붙이고 pending으로 저장한다. 관리자 업무는 이 제보를 검토한 후 승인 또는 거절하는 과정이다. 조회와 처리에는 관리자 권한이 필요하며 플랫폼 운영자 권한과 혼동하지 않는다. 승인 시에만 제보를 바탕으로 restaurants에 맛집을 생성한다.

5.2 제보의 처리 상태
서브타이틀: 대기·승인·거절로 구분하는 검토 결과

status는 현재 처리 단계를 저장한 값이다. pending은 검토 대기, approved는 승인 완료, rejected는 거절 완료다. 대기 제보의 승인 시 맛집을 생성하고 승인 상태와 reviewed_by·reviewed_at을 저장한다. 거절은 맛집을 만들지 않고 거절 상태와 검토 기록을 저장한다. reviewed_by는 관리자 사용자 ID이고 reviewed_at은 검토 시각이다. 삭제는 별도 작업이며 삭제됨이라는 상태는 구현에 없다. 승인 완료 요청의 재시도는 뒤의 중복 요청 장에서 다룬다. 별도 공개 여부 열과 전체 감사 로그는 현재 구현에 없으므로 확장 설계로 분리한다.

5.3 제보 승인의 구현 흐름
서브타이틀: 관리자 화면에서 서버와 DB 함수를 거쳐 승인 결과 반영

이 장은 관리자 화면에서 Express와 DB 함수까지 이어지는 요청 경로를 설명한다. URL의 :id는 선택한 제보 ID가 들어갈 자리임을 본문에 명시한다. RPC는 Remote Procedure Call의 약자로 원격 기능 호출이다. 본문은 이 실습에서 API로 DB의 저장된 함수를 호출한다는 의미를 먼저 정의한다. 관리자 화면 승인 → POST /api/submissions/:id/approve → isAuthenticated와 requireAdmin → submissions.service.ts의 rpc → approve_foodmap_submission 함수의 관리자 및 제보 상태 확인과 승인 처리 → 맛집 결과 반환 순서다. 성공 후 클라이언트는 submissions·restaurants 쿼리를 무효화해 목록에 변경을 반영한다. 브라우저가 DB 함수를 직접 호출하거나 클라이언트가 검토자 ID를 신뢰 가능한 값으로 정하는 구조가 아니다. DB 함수의 세부 원자적 변경은 다음 장에서 설명한다.

5.4 승인 작업의 트랜잭션
서브타이틀: 맛집 등록과 제보 상태 변경의 전부 반영 또는 전부 취소

트랜잭션은 여러 DB 변경을 전부 반영하거나 전부 취소하는 단위다. 실제 approve_foodmap_submission 함수는 restaurants에 먼저 맛집을 생성한 다음 submissions의 승인 상태·검토자·시각을 변경한다. 같은 함수 실행의 DB 트랜잭션에서 오류가 발생하면 해당 작업의 변경을 취소한다. 별도 외부 API의 효과나 이미 끝난 이전 작업까지 취소한다는 의미가 아니다. 트랜잭션은 불완전한 반영 방지이며 중복 요청 처리는 별도 개념이다.

5.5 중복 승인 요청의 처리
서브타이틀: 승인을 다시 눌러도 맛집 추가 생성 방지

중복 요청은 버튼 재클릭이나 응답 유실 후 재시도처럼 같은 작업이 다시 전달되는 상황이다. 본문에서는 멱등성 용어를 제외하고 승인을 다시 눌러도 맛집을 추가 생성하지 않는 결과에 집중한다. 멱등성 정의는 보충 자료에서 다룬다. 실제 DB 함수는 pending이면 새 맛집을 생성하고 approved이면 연결된 기존 맛집을 반환하며 rejected이면 거부한다. 이미 승인했지만 연결 맛집이 삭제된 비정상 상태는 오류를 반환하므로 모든 approved 요청의 성공을 보장하지 않는다. FOR UPDATE 잠금과 source_submission_id UNIQUE가 동시 실행의 중복 방지를 보강한다. 일반 멱등성 키 저장소는 현재 구현이 아니며 보충 자료에만 둔다. 검토한 코드는 읽기 대조이며 실환경 DB 실행 결과가 아니다.

챕터 흐름 평가
본문 7장을 실제 제보·승인 흐름의 5장으로 통합. 정의 → 상태 → RPC 흐름 → 트랜잭션 → 중복 승인 순서.
공개 상태·감사 로그와 플랫폼 관리 권한은 현재 기능과 구분해 보충 자료로 분리. 잠금·격리 수준·멱등성 키는 심화 범위.
실제 클라이언트·Express·스키마를 읽어 대조. 실환경 DB 변경이나 로그인 실행 검증은 수행하지 않음.

06. 환경 분리와 서비스 운영
실습 설정과 빌드·배포·주소 연결·동작 확인

6.1 로컬 환경과 배포 환경
서브타이틀: 내 컴퓨터 실행과 외부 주소 제공의 구분

첫 도식에 Vercel=화면 제공, Render=Express 서버 실행, Supabase=사용자 인증·DB를 바로 표시한다. 실행 환경은 프로그램이 동작하는 장소와 설정이다. 로컬 환경에서는 학생의 컴퓨터에서 Vite 개발 화면과 Express 서버를 실행한다. 배포 환경에서는 Vercel이 화면 파일을 제공하고 Render가 Express를 실행한다. 브라우저 SDK는 Supabase Auth로 인증을 요청하고 업무 요청은 Express를 거쳐 Supabase DB로 처리한다. 로컬과 배포 환경에 같은 Supabase 프로젝트를 설정하면 인증 계정과 업무 데이터를 공유할 수 있다. 별도 검증 환경이나 환경별 DB가 자동 구성된다고 설명하지 않는다. 도식의 화살표는 업무 요청 경로의 요약이며 Auth 직접 통신은 챕터3에서 배운 경로다.

6.2 환경변수와 연결 설정
서브타이틀: 실행 위치에 맞춘 API·Supabase 연결값

환경변수는 코드 밖에서 전달하는 이름과 설정값이며 .env 파일은 로컬 값을 저장하는 파일이다. 클라이언트는 .env.local의 VITE_API_BASE_URL·VITE_SUPABASE_URL·VITE_SUPABASE_PUBLISHABLE_KEY를 Vite에서 읽는다. 서버는 dotenv/config로 .env를 읽고 SUPABASE_URL·SUPABASE_SECRET_KEY·CLIENT_URL을 사용한다. 배포 서비스의 환경변수는 로컬 파일과 별도로 등록한다. 클라이언트와 서버의 Supabase URL은 같은 프로젝트를 가리키고 키는 각 실행 주체에 맞는 종류를 사용한다. Secret key를 VITE_ 변수에 넣지 않는다. 키 유출 대응 심화는 다음 주 보안 강의 범위다.

6.3 빌드와 배포의 실행 흐름
서브타이틀: 화면 파일 생성과 API 서버 실행의 구분

빌드는 소스를 실행·제공할 파일로 변환하는 과정이고 dist는 빌드 결과 폴더다. npm run build는 각 프로젝트의 package.json에 정의한 명령으로 클라이언트는 Vite 정적 파일을 만들고 서버는 TypeScript를 JavaScript로 변환한다. 현재 서버 빌드에는 copy-data.ts 실행도 포함되며 본문은 주 흐름을 발췌한다. Vercel은 dist의 화면 파일을 제공하고 Render는 npm start로 node dist/server.js를 실행해 API 요청을 받는다. 개발에서는 npm run dev를 사용한다. 클라이언트 설정 변경은 개발 서버 재시작 또는 배포 재빌드, 서버 실행값 변경은 프로세스 재시작으로 반영한다. Supabase SQL은 DB에서 별도 실행하므로 Git 업로드나 빌드만으로 테이블·함수가 바뀌지 않는다.

6.4 배포 주소와 로그인 복귀 설정
서브타이틀: API 연결 주소와 인증 후 돌아올 주소의 구분

API 기본 주소는 업무 요청을 보낼 Express 주소이며 VITE_API_BASE_URL에는 본인의 Render HTTPS 기본 주소를 넣는다. api.jsx가 /api/... 경로를 붙이므로 기본 주소에 /api를 중복 추가하지 않는다. CLIENT_URL은 화면의 프로토콜·호스트·포트로 이뤄진 기본 주소이며 경로나 끝 슬래시 없이 Vercel 주소를 등록한다. Supabase Site URL은 배포 화면 기본 주소이고 Redirect URLs에는 해당 주소의 /auth/callback을 등록한다. authApi.js는 window.location.origin에 /auth/callback을 붙여 redirectTo로 보낸다. vercel.json의 rewrite는 직접 접근도 index.html로 연결한다. 외부 제공자에서 Supabase로 돌아오는 콜백과 Supabase에서 Vercel로 돌아오는 주소는 다르다. 이 장은 배포 설정 적용이며 OAuth 전체 흐름과 CORS 원리는 반복하지 않는다.

6.5 배포 후 동작 확인
서브타이틀: 서버 응답부터 로그인·제보·승인까지 확인

Network는 브라우저 개발자 도구의 요청 확인 탭으로 풀어 설명하며 로그는 서버 실행 기록과 구분한다. 상태 확인 요청 health check는 서버 응답 여부를 확인하는 요청이다. 현재 app.ts의 /health는 {status:ok}를 반환하고 Supabase를 조회하지 않으므로 이 성공만으로 DB·Auth·승인 정상 여부를 판단할 수 없다. 공개 맛집 조회로 업무 DB 요청을 확인하고 이메일·Google·네이버 로그인과 내 프로필 확인, 일반 사용자의 제보 및 관리자의 승인 후 맛집 반영을 점검한다. 새로고침·로그아웃·재로그인도 확인한다. 브라우저 Network는 요청 주소·HTTP 상태와 응답을, Render 로그는 서버 실행과 오류 기록을 확인하는 도구다. 별도 함수에 기록하지 않은 모든 요청이 서버 로그에 자동 남는다고 설명하지 않는다. p95와 실패율 차트·상관관계 분석은 보충 자료다. 실제 배포 실행 결과가 아닌 구현 코드와 실습서의 점검 경로를 도식화했다.

챕터 흐름 평가
본문 10장을 로컬·배포 환경 → 환경변수 → 빌드·배포 → 주소 설정 → 동작 확인의 5장으로 통합.
로컬과 배포가 같은 Supabase를 공유할 수 있는 실제 실습 구조. 별도 검증 환경·마이그레이션·백업·복원·지표 분석은 보충 자료. 보안 심화는 다음 주.
서버·클라이언트 소스와 실습서를 읽어 대조한 설명. 실환경 배포·로그인·DB 변경 실행 결과가 아님.
