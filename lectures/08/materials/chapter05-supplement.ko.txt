챕터 5 보충 자료 — 관리자 업무와 승인 처리 심화
2026-11-09 / 초심자 본문 5장의 추가 읽기 자료

1. 관리자 권한의 경계
FoodMap의 admin은 서비스 기능을 사용하는 역할이다. Supabase 프로젝트 설정이나 배포·비밀 키 관리 권한과 같은 뜻이 아니다. 현재 Express는 사용자 인증 후 profiles의 관리자 역할을 검사한다. 승인 DB 함수도 검토자가 활성 관리자임을 확인한다.

2. 처리 상태와 공개 상태의 분리 — 확장 설계
현재 실습은 pending·approved·rejected를 사용하며 승인 시 restaurants에 맛집을 생성한다. 별도 published·visible 열은 구현하지 않았다. 추후 승인한 맛집의 노출을 일시 중단하려면 승인 결과와 공개 여부를 별도로 설계할 수 있다. 이는 현재 기능 설명이 아닌 확장 아이디어다.

3. 동시 승인과 행 잠금 — 현재 구현의 심화
approve_foodmap_submission은 제보를 SELECT ... FOR UPDATE로 읽는다. 같은 제보를 동시에 승인할 때 처리 순서를 직렬화하고 다음 요청이 바뀐 상태를 확인하게 한다. restaurants.source_submission_id의 UNIQUE 제약도 제보 하나에 연결된 맛집의 중복 생성을 막는다. 트랜잭션의 전부 반영/취소만으로 모든 중복 실행 문제가 해결되는 것은 아니다. 잠금 대기·격리 수준·교착 상태는 이번 실습의 필수 학습 범위에서 제외한다.

4. 승인 재요청과 범용 멱등성 키
멱등성(idempotency)은 같은 작업을 반복해도 추가 효과가 없는 성질이다. 본문은 이 용어 대신 같은 제보의 승인을 다시 눌러도 맛집을 추가 생성하지 않는 결과를 중심으로 설명한다.
현재 실습은 제보 상태와 연결 맛집으로 재요청을 처리한다. approved이면 연결된 기존 맛집을 반환하고 새 맛집을 만들지 않는다. 승인 기록은 있으나 해당 맛집이 삭제되어 연결 결과가 없으면 오류다. rejected이면 승인하지 않는다.
요청별 멱등성 키를 별도 저장해 같은 키의 결과를 재사용하는 방법은 다른 업무에서 사용할 수 있는 확장 방식이다. 이 실습에는 별도 키 발급·결과 저장소가 없다. 키의 유효 기간·요청 내용 일치·동시 실행 처리도 별도 설계 대상이다.

5. 검토 기록과 감사 로그의 차이
현재 submissions의 reviewed_by·reviewed_at은 검토자 ID와 검토 시각을 남긴다. 모든 변경의 이전 값·이후 값·행동·결과를 누적 보존하는 전체 감사 로그는 구현하지 않았다. 필요하면 누가·언제·무엇을·어떻게 바꿨는지 기록하는 별도 로그를 추가하고 조회·변경 권한과 보존 기간을 설계한다. 비밀번호·토큰 원문은 기록하지 않는다.

6. 트랜잭션의 범위
현재 승인 함수의 맛집 생성과 제보 상태·검토 기록 변경은 하나의 DB 트랜잭션에서 처리한다. 함수 실행 중 오류가 나면 이번 작업의 변경을 취소한다. 이미 끝난 다른 작업, 브라우저의 알림, 별도 외부 API의 효과까지 자동 취소되는 것은 아니다.
