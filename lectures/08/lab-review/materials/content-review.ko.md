# 7주차 실습 리뷰 — README 개발 흐름 반영 검토

기준은 `pwd-week7` README와 실제 서버·클라이언트 구현이다. 사용자 평가에 따라 11장을 16장으로 재작성했다. 05 공용 디자인, 이전 두 실습 리뷰의 정의·세부 설명·코드·관찰 결과 대조 형식을 유지한다.

## 평가 사항의 반영

| 평가 사항 | 반영 |
| --- | --- |
| DB 권한이 맨 마지막에 등장 | 4장으로 이동, 테이블 생성 후 접근 권한을 준비하고 시드 진행 |
| 타입·환경변수 로딩 연결 누락 | 6장에 Row·Insert와 SDK의 Database 역할, 7장에 dotenv/config → process.env → SDK 연결 |
| 조회 후 변환 함수 설명 | 8장에 Model 변환을 먼저 준비하고 9장의 Service에서 사용 |
| 등록할 row의 준비 누락 | 10장에서 요청 필드·기본값·DB 열 이름으로 row 구성, 11장에서 insert에 전달 |
| 연결 점검이 재시작 확인 뒤에 등장 | 13장에서 로컬 검사·빌드→실제 DB 읽기→API 조회를 마친 뒤 14장에서 재시작 확인 |
| React 화면까지의 확인 누락 | 15장에 실제 getData·useQuery·목록 필터와 README의 Network·같은 ID 확인 기준 |
| DB 설정과 API 사용자 권한의 역할 혼재 | DB 설정은 4장, 로그인·관리자 검사 미구현과 API 호출자 권한은 16장 |

| 화면 | 개념·구조와 예제 대응 | 검토 판단 |
| --- | --- | --- |
| 2 | 저장 수명과 요청 구조, 메모리·DB 비교 | 클라이언트는 Express 호출. 제보·화면 좋아요는 localStorage로 구분 |
| 3 | 행·열·자료형·제약조건, CREATE TABLE 전체 | identity와 기본 키의 역할 구분. DEFAULT와 NOT NULL의 범위 유지 |
| 4 | DB 역할별 객체 권한, 실제 RLS·REVOKE·GRANT | service_role의 RLS 우회와 객체 권한 필요를 구분. 사용자 인증 구현을 선행 설명하지 않음 |
| 5 | 초기 데이터와 재설정, seed 조건·로컬 결과 | 함수 정의와 실행 구분, 기존 행 보존과 초기화 삭제 구분 |
| 6 | 조회 행과 입력 행의 타입, Row·Insert 선언 전체 | 필수 열 선택·ID 제외·선택 입력의 역할 설명. Database가 SDK에 구조를 알리지만 타입은 테이블을 생성하지 않음 |
| 7 | 서버 실행 설정의 전달, dotenv·getSupabase | 로컬 파일 로딩→환경변수→객체 준비 순서. 객체 준비와 실제 연결 성공을 구분 |
| 8 | 저장 필드와 응답 필드의 대응, fromDatabase | Service에서 사용하기 전에 변환 구조 준비. 기존 camelCase 계약 유지 |
| 9 | 준비한 SDK·Model을 사용하는 목록 요청 | app·Router·Controller·Service 관계와 res.json까지 한 요청으로 연결. 새로운 라우팅 이론 재설명 없음 |
| 10 | HTTP 입력을 DB 입력 행으로 구성 | 메뉴 형식 통일·필수 값 존재 확인·열 이름 변환·기본값·ID 생략과 실제 row 대응 |
| 11 | 준비된 행 삽입·저장 결과·201 응답 | insert 전에 row가 설명됨. SQL의 기본값 관찰과 Service의 기본값 보완을 구분 |
| 12 | 정상 요청의 실패 분기, 오류 변환 코드 | DB 반환 오류 503·필수 값 400·없는 대상 404. 환경변수 누락은 현재 일반 Error의 500 분기 |
| 13 | 구현 검증과 실제 연결 검증 | README Step 7→8 순서. 로컬 테스트와 실제 클라우드 읽기, /health와 DB 조회의 범위를 구분 |
| 14 | 같은 ID의 재시작 전후 비교 | 개발 서버 종료→이미 빌드한 서버 실행→등록→종료·재실행. 비교는 같은 DB의 같은 ID·전체 필드 |
| 15 | HTTP 응답이 React 조회 데이터로 연결 | Axios response.data는 응답 본문, useQuery 결과의 data.data는 맛집 배열. 실제 코드와 화면 확인 기준을 구분 |
| 16 | API 호출자의 사용자 권한 | 앞서 준비한 DB 권한과 별개. 현재 등록·초기화 경로의 로그인·관리자 검사 미구현을 설명 |

개발 준비·구현 순서와 요청 실행 순서를 구분했다. 타입·SDK·변환을 먼저 준비한 후 9장에서 한 요청이 이 코드를 사용하는 관계를 보여준다. 오류는 정상 흐름의 분기로 구현 뒤에서 복습하고, 실제 확인 절차는 별도 13장에서 시작한다. 프로젝트 생성·패키지 설치·배포 조작을 전부 반복하는 구성은 아니다.

각 개념은 코드 없이도 정의와 역할·관계를 읽을 수 있도록 설명했다. Router·Controller·Service·비동기는 앞선 강의에서 다룬 범위다. JSX·React Query·분류 필터는 기존 클라이언트 복습이며, 세션·JWT·인증 미들웨어 구현은 본 강의에 남긴다.

## 소스·실행 근거

- 서버 커밋 `9954b9715ce0fe12ca15ac35dcd802e95c9bece1`, 클라이언트 커밋 `6f8237fb43822576ad11970696c3779c6530b858`
- 실제 파일 발췌 16개, 행 범위·파일 해시·저장소별 커밋 보관
- TypeScript는 공용 Prettier 사용. SQL 권한 발췌는 비공백 토큰 일치를 확인하며 줄바꿈만 조정
- 같은 서버 커밋으로 최초 작성 때 수행한 Jest 28건·PGlite 6건·타입 검사와 SQL 실행 근거를 유지. 실습 소스 변경이 없어 원본 테스트·SQL 실행을 불필요하게 반복하지 않음
- 표시된 PGlite 결과는 로컬 SQL 근거. 13·15장의 클라우드·React 확인 기준을 실제 실행 성공으로 주장하지 않음

클라우드 API·원본 .env·운영 DB·배포를 읽거나 변경하지 않았다.
