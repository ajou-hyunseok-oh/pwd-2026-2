# 3주차 실습 안내: 상품 주문 기능 구현과 코드 리뷰

## 목적과 완성 모습

HTML·CSS가 완성된 문구점 페이지에서 TypeScript로 상품 선택, 수량 검증, 일반·회원 가격 계산을 연결한다. 핵심은 작성한 줄 수가 아니라 **주어진 코드를 읽고 값·타입·실행 흐름을 설명하는 능력**이다. 실습은 [슬라이드 구성안](week-03-slide-outline.ko.md)의 공통 예제와 41–52장을 따른다.

노트 2개를 주문하면 일반 가격 6,000원, 회원 가격 5,400원이 표시된다. 잘못된 입력은 요청 전에 거부하며, 모의 요청 실패 후에는 다시 시도할 수 있다. [프로젝트 실행 안내](../practice/README.md)를 먼저 읽는다.

## 강의 개념과 실습의 연결

| 강의 페이지 | 실습 코드/활동 | 설명할 내용 |
|---|---|---|
| 04–08, 20–21 | `order.ts` | 문자열 변환, 조건, 함수 입력·반환, 지역 변수 |
| 09–12, 31 | `policies.ts`, `ui.ts`, 읽기 코드 | 함수 값·콜백, 객체 참조, filter/map, 순수 계산 |
| 13–14, 30, 33, 35 | `main.ts`, `api.ts` | 이벤트 등록, await, try/catch/finally, 중복 제출 방지 |
| 15–19, 26–27 | 오류 재현·타입 실험·API 검증 | 타입 검사와 실행 검증의 범위, 타입 제거 |
| 22–25, 28–29 | `types.ts`, `createOrder` | 객체 계약, 유니온, narrowing, `Result<T>`, 모듈 |
| 36–37, 40 | 정책 함수를 인수로 전달 | Strategy와 단순 함수의 적용 기준 |
| 38–39 | 선택 Adapter 과제 | 외부 검증과 필드 변환의 책임 분리 |

역사, 프로토타입, 클래스, 프레임워크의 선언형·반응형 UI는 구현 필수 범위가 아니다. 이 프로젝트의 DOM 갱신은 명령형이며 React/Vue 반응형 코드로 설명하지 않는다.

## 단계별 활동

### 1. 오류 재현과 실행 예측

`reading/bugs.js`를 실행하기 전에 A–D 출력값 또는 예외를 [리뷰 기록지](../practice/review.md)에 적는다. 실행 후 문자열 덧셈, 속성 오타, 없는 상품, 참조 공유를 각각 설명한다. 오류를 무조건 타입 오류로 분류하지 않는다.

### 2. 제공 코드 읽기

`types.ts → order.ts → policies.ts → main.ts → ui.ts → api.ts` 순서로 읽는다. 주문 버튼에서 화면 결과까지 호출되는 함수를 연결하고, 입력이 `string`인 곳과 `number`인 곳을 표시한다. 노트 2개 회원 주문의 중간값을 손으로 추적한다.

- `Result<number>`와 `Result<Order>`에서 `data`의 타입은 어떻게 다른가?
- `result.ok`를 확인하기 전 `result.data`를 읽을 수 없는 이유는 무엇인가?
- 상품 목록에는 품절 상품이 보이지만 선택 목록에는 없는 이유는 무엇인가?
- `await`가 멈추는 범위는 어디이며 오류가 나도 `finally`가 필요한 이유는 무엇인가?

### 3. 수량 검증과 주문 계산: TODO 1–3

`parseQuantity`에서 빈 값, 공백, 숫자가 아닌 값, 무한대, 0, 음수, 소수, 재고 초과를 거부한다. `Number()` 변환과 조건 검사를 별도 단계로 둔다.

`calculateLineTotal`은 곱셈 결과를 반환한다. `createOrder`는 상품 검색 → 없음 검사 → 수량 검증 → 실패 반환 → 금액 계산 → 정책 적용 → 성공 반환 순서로 작성한다. 새 객체를 반환하고 원본 상품을 수정하지 않는다. 오류 문구는 이유가 드러나면 자유롭게 작성한다.

### 4. 타입 오류 수정과 할인 정책: TODO 4

`reading/type-errors.ts.txt`를 안내대로 복사하고 타입 검사 메시지를 읽는다. 문자열 인수와 오타를 수정하며 `find()` 결과는 존재 여부를 확인한다. 그 후 `npm run check`가 통과하도록 정리한다. 작은 JS 함수에 매개변수·반환 타입을 붙인 것이 TS 함수라는 점을 두 파일과 `dist/src/order.js`를 비교해 설명한다.

일반 정책을 읽고 회원 정책을 구현한다. 회원 정책은 `Math.floor(amount * 0.9)`와 같은 규칙으로 최종 금액을 반환해야 한다. 할인 선택에 따른 분기는 제공되어 있으며, 주문 함수는 정책 이름 대신 함수 자체를 받는다.

새 할인 정책을 추가한다면 변경할 파일을 설명한다. 실제 추가 구현은 선택이다.

### 5. 검증과 코드 리뷰

`npm run check`, `npm test`를 실행하고 기록지의 정상·실패·경계 시나리오를 확인한다. 자동 검증으로는 화면 상태와 버튼 복구를 확인할 수 없으므로 브라우저에서 요청 실패와 재시도를 직접 확인한다.

짝과 코드를 교환하고 다음을 설명한다: 입력/출력 계약, 실패하는 경로, 원본 변경 여부, 정책 교체 위치. 기능이 동작해도 설명할 수 없는 줄은 다시 읽는다.

### 6. 선택: Adapter와 외부 데이터

`api.ts`의 검증기는 제공한다. `adapters.ts`에서 `product_name → name`, `unit_price → price`를 변환하고 나머지 필드를 유지한다. `?fixture=valid`, `?fixture=missing`, `?fixture=wrong`을 각각 확인한다.

```sh
npm test -- --adapter
```

필드가 누락되거나 숫자가 문자열이면 Adapter 호출 전에 실패해야 한다. HTTP 상태 확인, JSON 필드 검증, 내부 형식 변환을 구분해 설명한다. 검증기 전체 구현은 요구하지 않는다.

## AI 활용과 제출 기준

AI 사용 전 실행 결과를 먼저 적는다. 이후 특정 줄의 설명이나 반례를 요청하고, 제안한 변경을 읽은 뒤 적용한다. 질문과 변경 전후, 직접 실행한 반례를 기록한다.

제출물은 소스·실행 안내·작성한 리뷰 기록지다. 평가 비중 제안은 코드 읽기와 설명 40%, 필수 기능 30%, 경계·실패 검증 20%, 수정 및 AI 활용 기록 10%다. AI를 사용하지 않았다면 직접 수행한 수정 과정을 기록한다. 선택 과제를 하지 않아도 필수 평가에서 감점하지 않는다. 마감·제출 위치는 별도 수업 공지로 정한다.
