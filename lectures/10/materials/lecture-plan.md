## AI 시대의 보안: 추가 학습 범위

- 2025년 9월 탐지된 AI 활용 사이버 첩보: [Anthropic 사건 보고](https://www.anthropic.com/news/disrupting-AI-espionage). 공격 과정에 AI를 활용한 실제 활동에 대한 제공자 분석이다.
- 2026년 4월 공개된 [Comment and Control 연구](https://oddguan.com/blog/comment-and-control/): 이슈·PR 등 외부 입력의 간접 프롬프트 인젝션과 CI 에이전트의 권한·비밀정보 노출을 통제된 환경에서 시연한 연구다. 실제 피해 규모가 확인된 사건으로 소개하지 않는다.
- 프롬프트 인젝션, 최소 권한, 출력 검증, 개인정보와 비밀정보, 공급망, 추적·비용 제한을 다룬다. [OWASP LLM Top 10 (2025)](https://genai.owasp.org/llm-top-10/) 참고.
- 푸드맵의 AI 제보 요약은 가상 기능이며, 사용자 제보가 에이전트의 지시로 승격되는 경계와 관리자 권한을 검토한다.

아래 인증·보안·운영 구성은 기존 PDF에서 이어지는 기초 범위다. 시간표는 AI 보안 구간을 포함해 재조정이 필요하다.

## 학습 목표

- 지침, 스킬, 명세, 하네스의 역할과 서로 연결되는 방식을 설명한다.
- 기존 캠퍼스 푸드맵에 인증을 추가하는 작업을 명세와 검증 조건으로 나눈다.
- 인증과 인가, 세션과 토큰, OAuth와 OpenID Connect의 역할을 구분한다.
- 주요 웹 공격의 경로와 대응을 설명하고 운영 시 비밀정보·세션·로그를 관리한다.

## 1. 9주차 복습: 푸드맵의 개발 작업 체계

기존 사례의 확인된 범위: React 클라이언트가 Express API를 호출하고 서버가 Supabase Data API를 통해 PostgreSQL의 `restaurants` 테이블에 접근한다. 7주차 기준 제보와 화면 좋아요는 브라우저 localStorage에 남아 있다. 인증 추가는 아래에서 제안하는 **새 작업**이며 기존 구현 사실이 아니다. 근거: [8주차 실습 리뷰](../../08/lab-review/index.html), [코드 기록](../../08/lab-review/materials/code-excerpts.json).

### 개념별 설명과 사례

| 개념 | 역할 | 푸드맵에 적용하는 예 |
| --- | --- | --- |
| 지침 | 저장소 작업 전반에 반복 적용할 규칙 | 기존 API 계약 확인, 비밀정보 커밋 금지, 변경 후 관련 검사 실행 |
| 스킬 | 특정 유형의 작업에 필요한 절차와 자료 | 인증 변경 시 라우트·권한·세션·테스트를 점검하는 재사용 절차 |
| 스펙 드리븐 개발 | 원하는 행동과 제약·수용 조건을 먼저 명세하고 구현과 검증을 연결 | 비로그인, 일반 사용자, 관리자별 요청 결과를 먼저 정의 |
| 하네스 | 에이전트 작업을 실행·관찰·검증하는 주변 환경 | 격리된 테스트 DB, 검사 명령, 결과 기록, 실패 시 수정 및 재검사 |

스킬은 절차이고 하네스는 실행 환경과 피드백을 포함한다. 명세는 무엇이 성공인지 정하며, 지침은 작업 전반의 제약을 제공한다. 실제 도구의 파일 탐색·우선순위와 스킬 실행 방식은 사용하는 도구의 문서를 따른다.

### 푸드맵 인증 작업의 예시 명세

- 목표: 맛집 목록은 공개하고, 맛집 제보는 로그인 사용자에게 허용하며, 제보 승인·거절은 관리자에게만 허용한다.
- 범위: 로그인 상태 확인, 보호된 요청의 서버 권한 검사, 로그아웃. 화면에서 버튼을 숨기는 것은 서버 권한 검사를 대신하지 않는다.
- 수용 조건: 비로그인 제보 요청은 거부, 일반 사용자의 승인 요청은 거부, 관리자의 승인 요청은 허용, 로그아웃된 세션의 보호 요청은 거부.
- 비기능 조건: 비밀정보는 저장소에 포함하지 않고 테스트와 운영의 자격증명을 분리한다. 로그인 자격증명과 세션 값은 로그에 기록하지 않는다.
- 명세에서 정할 사항: 사용자·제보 저장 모델, HTTP 응답 계약, 중복 제보 및 오류 처리, 관리자 부여 방법. 위 예시는 설계 출발점이며 기존 API 계약을 확인한 후 확정한다.

### 하네스 설계 사례

1. **준비**: 실제 서비스와 분리된 테스트 환경 및 테스트 계정 준비, 기존 API 계약과 DB 스키마 확인.
2. **작업**: 명세의 역할별 동작을 작은 작업으로 분해하고 각 변경의 영향 범위 기록.
3. **검증**: 정상 경로와 비로그인·권한 부족·로그아웃 후 요청을 자동 검사. 테스트 데이터는 격리하고 정리.
4. **피드백**: 실패한 조건과 실행 결과를 기록하고 수정 후 관련 검사를 다시 실행.
5. **완료 판단**: 명세별 검사 결과와 남은 위험을 사람이 확인. 검사 성공만으로 모든 보안 위험이 해결된 것으로 간주하지 않음.

## 2. 웹 서비스 인증과 권한

아래 순서는 제공된 PDF의 학습 흐름을 따르되 개념을 구분해 수업에 활용한다.

1. **인증 필요성**: HTTP 요청은 서로 독립적이므로 서버가 후속 요청의 사용자를 식별할 방법이 필요하다. 개인화, 사용자별 권한, 감사 기록에 활용한다.
2. **인증과 인가**: 인증은 사용자 신원 확인, 인가는 확인된 주체가 특정 작업을 할 수 있는지 판단하는 과정이다. 푸드맵의 일반 사용자 제보와 관리자 승인으로 비교한다.
3. **로그인 흐름**: 자격 증명 제출 → 서버 검증 → 세션 또는 토큰 발급 → 후속 요청 검증 → 로그아웃·만료. 비밀번호는 평문이 아니라 적절한 비밀번호 해시로 저장한다.
4. **쿠키**: 서버가 설정하고 브라우저가 범위·속성에 맞는 요청에 전송하는 값. 쿠키는 저장·전달 수단이며 세션 자체와 같지 않다.
5. **세션**: 서버가 상태를 저장하고 브라우저의 예측하기 어려운 세션 ID로 상태를 찾는다. 다중 서버는 공유 저장소가 필요할 수 있으며 로그아웃은 서버에서도 무효화한다.
6. **토큰과 JWT**: 토큰은 권한이나 신원 관련 정보를 전달할 수 있다. JWT는 헤더·페이로드·서명으로 구성될 수 있으며 인코딩은 암호화가 아니다. 서버는 서명과 발급자·대상·만료 등 필요한 조건을 검증한다.
7. **세션과 JWT 비교**: 서버 저장 상태, 수평 확장, 만료·폐기 방식과 탈취 위험을 비교한다. JWT라고 반드시 무상태인 것은 아니고 세션 ID와 토큰 모두 탈취되면 재사용될 수 있다.
8. **OAuth 2.0과 OpenID Connect**: OAuth는 권한 위임을 위한 프레임워크이며 OpenID Connect는 그 위의 인증 계층이다. 소셜 로그인은 제공자의 문서와 검증 절차를 따른다. access token만으로 임의로 사용자를 인증하지 않는다.

## 3. 웹 보안과 운영

| 주제 | 위험 또는 역할 | 수업에서 연결할 대응 |
| --- | --- | --- |
| XSS | 악성 스크립트가 다른 사용자의 브라우저에서 실행 | 출력 문맥에 맞는 이스케이프, 신뢰하지 않는 HTML 처리 제한, CSP 보조 적용 |
| CSRF | 로그인 사용자의 브라우저가 공격자가 의도한 요청을 전송 | 상태 변경 요청에 CSRF 방어, Origin 검사, SameSite를 보조 수단으로 사용 |
| SQL Injection | 입력값이 쿼리 구조를 변경 | 매개변수화된 쿼리, 최소 권한, 입력 검증 |
| 무차별 대입 | 반복 로그인 시도로 계정 탈취 | 시도 제한, 모니터링, 필요 시 추가 인증 |
| 경로 탐색 | 조작된 경로로 허용 범위 밖 파일 접근 | 허용된 식별자와 경로만 사용, 정규화 후 경계 확인, 최소 권한 |
| 비밀정보 | 유출된 키가 서비스 접근에 악용 | 환경별 분리, 저장소 제외, 노출 시 즉시 폐기·교체 및 영향 확인 |
| 쿠키·세션 | 세션 탈취 또는 과도한 유지 | HTTPS, Secure·HttpOnly·적절한 SameSite, 서버 만료와 로그아웃 무효화 |
| 로그·감시 | 사고 추적과 이상 징후 탐지 | 비밀번호·토큰 기록 금지, 최소한의 사건 기록, 접근·보존 정책과 경보 |

HttpOnly는 스크립트의 쿠키 직접 읽기를 제한하지만 XSS가 사용자 권한으로 요청을 보내는 것까지 막지는 않는다. SameSite는 CSRF 방어의 보조 수단이다. 토큰의 수명과 폐기 전략은 서비스 위험과 구조에 따라 정한다.

## 4. 푸드맵 설계 실습

**활동**: 팀별로 위 인증 예시 명세를 확장해 요청별 권한 표와 검증 계획을 작성한다.

| 요청 | 비로그인 | 일반 사용자 | 관리자 |
| --- | --- | --- | --- |
| 맛집 목록 조회 | 허용 | 허용 | 허용 |
| 맛집 제보 | 거부 | 허용 | 허용 |
| 제보 승인·거절 | 거부 | 거부 | 허용 |

1. 기존 푸드맵에서 서버와 클라이언트의 책임, 제보의 현재 저장 위치를 확인한다.
2. 제보 저장·사용자 식별·관리자 권한 부여를 위한 데이터와 API 변경을 명세한다.
3. 로그인·세션 유지·로그아웃의 흐름과 보호된 요청의 서버 검증 지점을 그린다.
4. 위 권한 표에 대한 정상·실패 사례와 테스트 환경을 정한다.
5. XSS, CSRF, 비밀정보 노출 중 한 가지를 선택해 발생 경로와 대응을 설명한다.

**제출물 제안**: 역할별 권한 표, 인증 흐름도, 수용 조건과 검증 목록, 위험·대응 각 1개 이상. 구현 과제의 마감·배포·제출 방식은 별도 확정이 필요하다. 원본 PDF의 2025년 마감일과 배포 URL은 이번 학기 확정 조건으로 사용하지 않는다.
